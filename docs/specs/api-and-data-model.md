# Spectio — headless integration, API and data model

Status: draft v0.1 · 2026-10-25 · author: Thomas Weber (with Claude)
Companion docs: [`synthesis.md`](synthesis.md) (architecture, §7bis and §7quinquies), [`ui-spec.md`](ui-spec.md) (screens), [`decisions/log.md`](../decisions/log.md) (decisions log).

## 0. Decisions in brief

1. **Headless first.** The server is an engine-agnostic launch-and-monitor service. The web UI, the CLI, the MCP server, the WES facade and embedded elements in other tools (LabID, portals) are all clients of the same public API. Nothing the UI does is private.
2. **Single-user is a configuration, not a different system.** One schema and one API for every deployment. A single-user install is a multi-user install with one user, one group and one project created at first start, and an authentication mode that maps local requests to that user.
3. **Everything belongs to a project.** Every tenant row has `project_id` and `created_by`; every list endpoint is filtered by the projects the caller can see. Adding users and groups later needs no schema migration, only data.
4. **Principals, not just users.** People, service accounts (LIMS, CI), AI agents, runners and the system itself are all principals with tokens and roles. Every decision and change records which principal made it.
5. **Extension points are plugins.** Engines, input resolvers (`labid://`, `s3://`, `drs://`…), output sinks, check providers, notifiers and identity providers are Python entry points, so an institute adds an integration without forking Spectio.

## 1. Deployment modes

| Mode | What runs | Typical use |
|---|---|---|
| **Personal** | `spectio serve` on a laptop or a login node, bound to `127.0.0.1`, auth mode `single` | One researcher, no setup |
| **Team server** | server + Postgres (or SQLite on local disk) + runners on clusters, auth mode `oidc` | A lab or core facility |
| **Headless** | same server with `--no-ui`; only API, WES, webhooks, MCP | Driven entirely by a LIMS, portal or CI |
| **Embedded** | team or headless server + Spectio elements inside another web app | LabID or an institute portal shows launch forms, run cards and reviews |

Runners always connect outward to a server; they never need inbound ports.

## 2. Integration patterns

### A. LIMS-driven run (LabID)
```mermaid
sequenceDiagram
  participant L as LabID (service account)
  participant S as Spectio server
  participant R as Runner (EMBL SLURM)
  L->>S: POST /api/v1/runs (workflow, params, samplesheet rows with labid:// inputs, external_refs, Idempotency-Key)
  S->>R: launch command
  R->>R: resolver plugin turns labid://dataset/456 into a path on EMBL storage
  R-->>S: engine events (nf-spectio plugin / Snakemake logger)
  S-->>L: webhook spectio.run.state_changed, spectio.gate.opened
  L->>S: GET /api/v1/gates/{id} (or the reviewer decides in the embedded review element)
  S-->>L: webhook spectio.run.completed
  S->>L: sink plugin publishes the Workflow Run RO-Crate and registers outputs as LabID datasets
```

### B. Standard client through WES
A portal or another WES client calls `POST /ga4gh/wes/v1/runs` with `workflow_type: NFL` or `SMK` (TRS descriptor types, which WES 1.1 accepts as instance-specific values, WES 1.1.0 OpenAPI `:753`; listed in `service-info.workflow_type_versions`). Spectio maps it to a native run in the caller's default project. Gates, pause and resume are available as WES extensions (`/ga4gh/wes/v1/runs/{id}/x-spectio/...`) and through the native API.

### C. Host UI with embedded elements
The host backend exchanges its service token for a short-lived **embed token** limited to one resource and a few actions, then renders `<spectio-launch-form>`, `<spectio-run-card>` or `<spectio-review>`. The elements talk to the Spectio API directly with that token and emit `postMessage` events (`spectio:run-launched`, `spectio:gate-decided`) to the host page.

### D. Observed or adopted CLI runs
A run started in a terminal with Spectio enabled is attached to the user's default project, or the project given by `SPECTIO_PROJECT`. It is the same run object as a UI or API launch.

### E. Event-driven automation
A robot or instrument subscribes to `spectio.gate.opened` for a gate type, does its work, and calls `POST /api/v1/gates/{id}/signals` with its service-account token. Policy decides whether that signal resolves the gate or only adds evidence.

## 3. Extension points (plugins)

Python entry points, one group per kind (`spectio.engine`, `spectio.notifier`, …), loaded on the server or the runner. The kinds (among them the task backend, pub/sub and event bridge), where each runs and their contracts are owned by [`architecture-plugins-and-packaging.md`](architecture-plugins-and-packaging.md) §2 and §3.6, together with discovery, settings, instances and scopes, versioning, conformance tests, frontend plugins, packaging and the `plugin_instances` table.

## 4. API design rules

- Base path `{root}/api/v1`, where `root` is empty for a standalone install and `/spectio` when co-hosted with depictio (`/depictio/api/v1`) behind one domain; JSON; resource-oriented; OpenAPI 3.1 published at `/api/v1/openapi.json`; generated Python and TypeScript SDKs.
- **IDs**: prefixed ULIDs (`run_01JB…`, `gate_01JB…`, `prj_01JB…`), sortable, safe in URLs, unique across the instance.
- **Tenancy**: every object returns `project_id`, `created_by` and `created_at`. Collections are top level (`/runs`, `/workflows`, `/gates`) and filtered by `?project=`; without it, the caller sees every project they can read. Create calls take `project_id`, defaulting to the caller's default project, so single-user clients never need to send it.
- **Ownership is data, not path**: no `/users/{id}/runs` paths, so moving a run between projects or adding users never changes URLs.
- **Lists**: cursor pagination (`?cursor=`, `limit` ≤ 200, `next` in the response), filters (`?state=running&workflow=wf_…&external_ref=labid:sample/123`), sort (`?sort=-created_at`), sparse fields (`?fields=`). Lists return no total. Whether an optional `total` (`?count=exact|estimate|none`) is affordable is decided by spike S-R7-4 ([R7](../reviews/R7-ui.md#proposed-spikes)); until then clients page with Next / Load more, never numbered pages or "of N". Headline counts and breakdowns come from the summary endpoints (§5). *(assumed — pending Thomas, inbox #30)*
- **Writes**: `Idempotency-Key` on every POST that creates or triggers something, kept 24 h: the server inserts the key first (`idempotency_keys`, §7), so two concurrent requests cannot both pass, and returns the stored response on a retry (scope and replay rules: next bullet); `ETag` / `If-Match` on gates, change sets, settings and the work-directory clean of a resumable run *(assumed — pending Thomas, inbox #30)* to prevent lost updates when two reviewers act at once; on a gate with a quorum each decision is a vote and does not compare-and-swap on the gate ETag, and change-set items carry their own version (§5, §7).
- **Idempotency keys are scoped to the caller.** A key is unique per (principal, or the owning group for a service account; HTTP method; route). The same key from another caller is a new request, never a replay. Replaying a key with a different body returns `409` (problem `idempotency-key-reused`, §4.1; exit code 5 in the CLI, [`cli-and-shared-libraries.md`](cli-and-shared-libraries.md) §2). A replay returns the stored result only if the caller still passes `can(read)` on it (§6). **Test:** tenant B reusing tenant A's key gets a new run or `409`, never A's run.
- **Long operations** (catalogue import, RO-Crate export, cleanup) return `202 Accepted` with an `Operation` resource (`/operations/{id}`). An `Operation` is the caller's view of a background task ([`admin-and-operations.md`](admin-and-operations.md) §3.1). *(assumed — pending Thomas, inbox #29)*
- **Errors**: RFC 9457 `application/problem+json` with a stable `type` URI and, for validation, a list of field errors.
- **Versioning**: during 0.x, `/api/v1` may break in a minor release, announced in the changelog ([`dev-environment-and-testing.md`](dev-environment-and-testing.md) §12); from 1.0.0, only additive changes within API v1, and breaking changes go to API v2; deprecations announced with `Deprecation` (RFC 9745) and `Sunset` (RFC 8594) headers.
- **Limits**: per-token rate limits with `RateLimit-*` headers; request size limits; files go through artefact endpoints, never in JSON bodies.

*Note 2026-10-30 (0.0.1 launch, P1 Task 17):* the 0.0.1 server adds two endpoints of its own, with no `workflows` catalogue, no `POST /workflows` and no `POST /runs:validate` ([P1](../plans/P1-walking-skeleton.md) Assumption 2).

- `GET /workflows:inspect?location=&revision=` reads a pipeline for the launch form, without running it, and returns `{location, revision, engine, engine_files, name, version, engine_version, engine_versions: {nextflow, snakemake}, schema, schema_source, profiles}`:
    - `location` is an absolute path to a directory the user's account can read, or a Git repository: an `owner/repo` name, taken as `https://github.com/owner/repo`, or an `https://` or `ssh://` URL, with a required `revision` (a tag, a branch or a commit). The repository is fetched once per revision into `<data dir>/pipelines/<host>/<path>/<revision>/`, under the rule of [Imports are untrusted input](#imports-are-untrusted-input): `git -c protocol.allow=never -c protocol.https.allow=always -c protocol.ssh.allow=always`, an argument list, no terminal; a URL with credentials, a path part `.` or `..`, a control character in the location or the revision, and a revision that starts with `-` are refused;
    - `engine_files` lists those of `main.nf`, `Snakefile` and `workflow/Snakefile` that exist; `engine` is the engine they point to, `null` when both or neither are there (UX-G2-04);
    - `name` and `version` are the Nextflow `manifest.name` and `manifest.version` read from `nextflow.config`, else the directory's or repository's name and `null`; Snakemake declares no version **[to be validated]**;
    - `engine_version` is the version of `engine` the server would launch with, `null` without a guess; `engine_versions` gives both engines', `null` for one that is missing (UX-296, UX-G2-04);
    - `schema_source` is `nextflow_schema.json`, `config.schema.yaml` (at the root or in `workflow/schemas/`), `inferred` (the types of the values of `config/config.yaml`) or `none`; `profiles` are the Nextflow profile names of `nextflow.config` (its `includeConfig` files are not read) or the Snakemake profiles `profiles/<name>/config.yaml`.
- `POST /runs` takes the 0.0.1 body `{workflow: {location, revision?, engine}, name?, profiles?: [str], params: {}}`, not the §5.2 body. It checks the location as inspect does, that the chosen engine's file exists (`422`, field `workflow.engine`), the profiles (one at most for Snakemake), and the parameters against the pipeline's schema (in the JSON Schema draft its `$schema` names, draft 7 when there is none; an `inferred` schema is not enforced). It then writes the run directory and its manifest, and in one transaction the `workflows` row (one per location, with one engine), a `workflow_versions` row, the run (`queued`, origin `ui`), its parameters (`run_inputs.kind = params`), launch 1 and a `launch` row in `runner_commands`. It answers `201` with the run and a `Location` header; the default name is `<workflow name>-<last 6 of the run ID>`.
- Both answer `422 validation-failed` with `errors: [{field, message}]`, where `field` is a dotted path into the request (`location`, `workflow.location`, `params.chunks`), not the `{pointer, code, detail}` of §4.1.
- Inspect reads a pipeline's files only through real directories and regular files inside the pipeline directory: a symlink, in the tree or out of it, counts as absent (dev-env §15.3 req. 13, the `O_NOFOLLOW` walk). So a symlinked `nextflow_schema.json`, `config.schema.yaml` or `config/config.yaml` gives `schema_source: none`, and `POST /runs` then checks no parameter; a symlinked `nextflow.config` gives no manifest name, version or profiles; a symlinked entry file is left out of `engine_files` (and `POST /runs` answers `422` on `workflow.engine`); a symlinked `profiles` directory, or a profile whose directory or `config.yaml` is a symlink, is not listed.
- Until sign-in (P1 Tasks 12 to 16), they are served only by a server whose environment is of kind `local`, and only on a machine that does not look like a cluster node or a shared one, as decided once at start (inbox #86 rule 1). ### Imports are untrusted input

`POST /workflows:import` and `POST /runs:import-crate` take content written by someone else (WorkflowHub, email, another instance). They: *(decided — Thomas, 2026-10-27, inbox #25)*
- **extract crates safely:** every entry is resolved inside the extraction directory, with no zip slip ([Snyk](https://security.snyk.io/research/zip-slip-vulnerability)), and with limits on total size, file count and compression ratio;
- **process JSON-LD with remote context loading off.** Remote `@context` retrieval is part of JSON-LD processing ([JSON-LD 1.1 API](https://www.w3.org/TR/json-ld11-api/#remote-document-and-context-retrieval)); whether the chosen library loads contexts by default is **[to be validated]**;
- **accept git URLs over `https` or `ssh` only.** `file://`, `ext::` and other transports are refused ([git `protocol.allow`](https://git-scm.com/docs/git-config#Documentation/git-config.txt-protocolallow));
- **never pre-fill a launch silently.** A launch pre-filled from a crate shows every non-default parameter, hidden ones included, and flags parameters that load code or config from elsewhere. Example: nf-core/rnaseq sets `custom_config_base` to a remote URL and calls `includeConfig "${params.custom_config_base}/nfcore_custom.config"` (`95dbcd9`, `nextflow.config:154,331`); `config_profile_url` is also listed by R5 **[to be validated]**.

Project imports between instances follow [`admin-and-operations.md`](admin-and-operations.md) §4.3. **Tests:** a zip-slip crate, an `ext::` git URL and a crate that names a remote JSON-LD context are refused or processed offline.

Every read is the confined walk of [dev-env §15.3](dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts) req. 13, in the routes' file pool with its 5 s wait; the headers are req. 13 ("Shown as text") and req. 14 (note of 2026-11-08). - **Facts of one results entry.** `GET /runs/{id}/results/stat/{path}` → `{root, path, name, type: "dir" | "file" | "link_outside", size, mtime}`, the listing's entry for that one path, with the listing's checks and problems. The preview page asks it first (facts, kind, size caps, the path the server answered for), so it never needs the parent listing.
- **Text of a results file.** `GET /runs/{id}/results/text/{path}` → `text/plain; charset=utf-8`, with the read contract of a job file (§5 note of 2026-10-31): without `Range`, the last `?tail=<bytes>` (64 KiB by default, 1 MiB at most); with one `Range: bytes=<first>-[<last>]`, at most 1 MiB, answered `206` with `Content-Range: bytes <first>-<last read>/<size>`, the total always given. A read ends at the last whole UTF-8 sequence inside the range, and `Content-Range` gives that real end, so the next read starts at its last byte + 1 and no character is split. An empty file is `200` with an empty body; a malformed range, or one that starts past the end of a file that is not empty, is `422 validation-failed` on `Range`. Bytes that are not UTF-8 are replaced, escape sequences and the characters of `FORMAT_CHARS` are removed (so the body can be shorter than the range), and a NUL byte in the first 8 KiB is `415 binary-file`. `path` is checked as for the raw route (`check_rel`: relative, no `.`, `..` or empty part, no `.spectio`, `.snakemake` or `.nextflow` part, a name the server serves), and the file is found by the listing's walk, a published link followed only into a task directory of the run's work directory. Problems as the raw route: `404 not-found` (no results directory, a run started from a terminal, or no such file), `422 file-not-allowed`, `415 binary-file`, `503 runner-offline`.
- **An image from the results.** `GET /runs/{id}/results/raw/{path}?as=image` serves the file as an image, for the preview's `<img>`. The rules apply in this order, each with its own `test_req14_image_*`:

    | Step | Condition | Answer |
    |---|---|---|
    | 1 | every check of the raw route (name, walk, the 1 GiB cap) | its problem |
    | 2 | `?download=true` | attachment |
    | 3 | `as` present with any value but `image` | `422 validation-failed` on `as` |
    | 4 | `as=image` on a name not ending in `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp` or `.svg` (any case) | `422 file-not-allowed` |
    | 5 | `as=image` without `Sec-Fetch-Dest: image` ([Fetch Metadata, `Sec-Fetch-Dest`](https://www.w3.org/TR/fetch-metadata/#sec-fetch-dest-header): a browser sends `image` for an `<img>` load, never for a navigation) | attachment, as today (1 GiB cap) |
    | 6 | with the header: the file is over 20 MiB (an SVG over 5 MiB) | `413 file-too-large` |
    | 7 | a raster type whose first chunk does not match its signature in the [MIME Sniffing standard, §6.1](https://mimesniff.spec.whatwg.org/#matching-an-image-type-pattern) (PNG `89 50 4E 47 0D 0A 1A 0A`, JPEG `FF D8 FF`, GIF `GIF87a` or `GIF89a`, WebP `RIFF` then `WEBPVP` at byte 8), or whose header declares more than 50 megapixels (PNG `IHDR`, GIF bytes 6 to 9, WebP `VP8`, `VP8L` or `VP8X`, JPEG the first `SOFn` in that chunk; none found is refused) | `422 file-not-allowed` ("not the image its name says", "image too large to decode") |
    | 8 | otherwise | the image, `Content-Type` `image/png`, `image/jpeg`, `image/gif`, `image/webp` or `image/svg+xml` |

  The check of step 7 is on the first chunk read, and that same chunk is sent as the first part of the body: no second open. It is advisory (it keeps a mislabelled file out of `<img>`); the safety against sniffing is `nosniff` and the CSP `sandbox`. `Sec-Fetch-Dest` decides only how a file is served, never whether: every check runs first. Both answers of the raw route carry `Vary: Sec-Fetch-Dest`. Browser decode limits beyond 50 megapixels are **[to be validated]**.
- **A Nextflow attempt's work directory.** Four routes, with `n` as in the Job files routes (the latest launch's attempt `n`):
    - `GET /tasks/{id}/attempts/{n}/workdir?path=<relative>` → `{root, path, exists, entries: [{name, type, size, mtime}], truncated}`, the Results listing without `reports`: one folder, at most 1000 entries, folders first, a folder's `size` `null`. `root` is the attempt's work directory, found as the Job files routes find it (from the runs root and the run ID, two levels below the run's work directory, `files/taskfiles.py` `_work_rel`), never from the stored path alone.
    - `GET /tasks/{id}/attempts/{n}/workdir/stat/{path}`, as the results `stat` route.
    - `GET /tasks/{id}/attempts/{n}/workdir/text/{path}`, as the results text route.
    - `GET /tasks/{id}/attempts/{n}/workdir/raw/{path}`, as the results raw route, with `as=image` and `download`, except that `.html` and `.htm` are always attachments: a work directory has no report viewer.

The safety rules of the page (CSP, decode caps, pinned libraries) are req. 19. What changes on the server: two new values of `as` on the raw route, a bounded `Range` on them, a read slot limit for them, and the refusal of script and worker loads on every raw route.

- **TIFF and OME-TIFF are read by byte ranges, through the page's own client.** geotiff.js asks a file's header, then its IFDs and the tiles or strips it needs, one `Range` request each: geotiff.js 2.1.3 `RemoteSource.fetchSlice` sends `Range: bytes=<offset>-<offset + length>`, one byte more than it needs, and refuses an answer that is not `206` unless `allowFullFile` is set (`dist-module/source/remote.js:109-146`); its `BlockedSource` reads 64 KiB blocks by default (`source/blockedsource.js:48`). The page does not give Viv a URL: Viv 0.23.0 would open it with geotiff.js `fromUrl(url, {headers, cacheSize: Infinity})` and its own fetches (`@vivjs/loaders` `dist/index.mjs:402-411`), out of reach of the page's caps (SEC-PRE-FU102-R1-01). The page opens the file with geotiff.js `fromCustomClient` (`dist-module/geotiff.js:697`) and a client of its own, pinned to that one URL, `/api/v1/runs/{id}/results/raw/{path}?as=tiff` (or the work directory's raw route), built from the `stat` route's `path`, never from a URL read from a file; the client counts and caps every request (Caps below). The page walks the IFDs itself, with the caps of req. 19 and a set of the offsets seen (an IFD seen twice ends the walk: a loop), then hands Viv the opened images: Viv exports `TiffPixelSource` (`dist/index.mjs:1318`), and which Viv entry point takes an opened GeoTIFF, or whether the page builds the pixel sources itself, is **[to be validated]** in FU-P3-102e. An OME-XML that names another file (a `TiffData` with a `UUID` `FileName` other than this file, or more than one file) is refused: Spectio reads one file per view.
- **OME-Zarr is a directory, read key by key.** A `.ome.zarr` folder is opened as a Zarr store whose root is the folder's raw URL; each key the reader asks (`.zattrs`, `.zgroup`, `.zarray`, `zarr.json`, then the chunk keys of the levels shown) is one request to `/api/v1/runs/{id}/results/raw/{folder}/{key}?as=zarr`, whole, or with one bounded `Range` for a shard of a Zarr v3 sharded array. The page uses its own store (`get` and `getRange`, the interface of `@zarrita/storage` 0.2.0 `FetchStore`, `dist/src/fetch.js:61-110`) given to Viv's `loadOmeZarrFromStore` (`@vivjs/loaders` 0.23.0 `dist/index.mjs:1256-1263`, `:1318`), not Viv's `loadOmeZarr`, which builds a `FetchStore` from a URL: the page's store builds every key below the folder (a key with an empty, `.` or `..` part, a `/` at its start, a `:`, `?` or `#` is never asked), counts and caps the requests, asks a suffix range as the `stat` route's size then a closed range (the server takes no suffix or open-ended range, and `FetchStore` would send a `HEAD`, which the raw route does not answer), and reads a `404` as an absent key (a chunk at its fill value, as Zarr reads it). *Note 2026-11-09, design of FU-P3-86, assumed — pending Thomas ([inbox #133](../reviews/inbox.md#133-assumed-environments-local-slurm-define-a-new-one-fu-p3-86); Thomas, login1 feedback, 2026-11-08: "environments (local, SLURM, define a new one)", in 0.0.1 by the [decision log](../decisions/log.md#2026-11-08-thomass-login1-feedback-five-features-join-001-engine-polling-unchanged-thomas); design entry: [decision log](../decisions/log.md#2026-11-09-environments-in-001-fu-p3-86-assumed); revised the same day after the independent pre-review R1, [record](../reviews/code/P3-fu86-spec.md#round-r1-independent)):* the store, the routes and the launch field behind the Environments screens of [ui-spec §4.8.1](ui-spec.md#481-environments-in-001). Whoever holds the session can already run code as the user through `POST /runs` (a pipeline is code), so the rules below are defence in depth against values that steer the engines, and protection of the file in the shared home.

**What exists before this note.** The executor is one value per server, `executor = "slurm" | "local"` in `spectio.toml`, set by `spectio init` (`--local` for local mode) and read by `spectio.config.Settings`. The runner builds every launch from it (`slurm=settings.slurm if settings.executor == "slurm"`, `spectio/runner/loop.py`), with the one `[slurm]` table (`partition`, `account`); the head script turns it into Nextflow's `.spectio/spectio.config` (`process.executor`, `process.queue`, `process.clusterOptions = '--account=…'`) or Snakemake's `--executor slurm` and `--default-resources` (`spectio/runner/headscript.py`). Per-run decisions read the server's kind too: the failure summary takes `on_slurm` from the `environments` row joined through `runs.environment_id` (`failure.py:823-827`, then `sacct` at `:887-892` and the reason at `:894`), `Accounting.from_settings` (`failure.py:316`) and the copied command (`resume.py:126`) from `settings.executor`, and `ensure_tenancy` rewrites the oldest `environments` row at each start (`bootstrap.py:61-65`). `GET /version` gives the server's `executor`, which the screens show as the run's executor too. `POST /runs` has no environment field, and the form ends "The executor, the login node and the run directory are fixed for this server: there is nothing to choose in 0.0.1" (ui-spec §4.6, UI parity B note).

**An environment** is a named set of typed launch defaults for one executor. It changes how the engine sends its tasks; it never changes where the head runs (the tmux session on the server's node, or the local launcher), the runs root, the listener or the Unix account.

| Field | Rule |
|---|---|
| `name` | `^[a-z][a-z0-9-]{0,31}\Z`, unique; the key in the URL and in the launch body. `local`, `slurm` (the built-ins) and `new` (the screen route `/environments/new`) are reserved: `422` on `name`, "slurm is a built-in name" |

A hand-written `slurm` entry on such a server is listed with `usable: false` and that reason; the file stays `ok` |
| `slurm` | with `executor = "slurm"` only, every key optional: `partition` and `account`, each one name matching `^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}\Z` in full (no list in 0.0.1); `time_min`, an integer 1 to 43,200 (the time of a job that asks for none); `mem_mib`, an integer 1 to 4,194,304 (its memory) |
| `local` | with `executor = "local"` only: `cpus`, an integer 1 to 256, and `mem_mib`, as above; the most the tasks may request at once (the user's cgroup stays the only hard cap) |
| `profiles` | optional, one default profile per engine: `nextflow` and `snakemake`, each one name matching `PROFILE` of `headscript.py` or null. They only prefill the Launch form's one Profile choice (UX-PRE-FU86-R1-01); the launch body's `profiles` decides |

- **Types are strict.** The model is pydantic in strict mode: an integer field takes a JSON integer only (not `true`, `"5"` or `5.0`), a string field a string only, and every pattern is matched in full (`fullmatch`, or `\Z`, never `$`, which accepts a final newline). `headscript.py` checks again, at the point of use, that each integer is `type(v) is int` in its bounds and each name matches, as it does for `launch_n` (SEC-PRE-FU86-R1-06).
- **Nothing else:** no free `clusterOptions`, no `qos`, GPUs or CPUs per task, no environment variables, `module load` lines, engine command, extra arguments or engine configuration file (Later list below). Every field is a name of a closed character set or an integer, so no value can carry shell text, an option, a path, `~` or `$`.

**Built-ins.** Two environments are always listed and cannot be edited or deleted (`409 environment-builtin`); Duplicate on the screens copies one into a new name:
- **`slurm`**, label "SLURM (from spectio init)", on a server set up with SLURM only: `partition` and `account` from `spectio.toml`'s `[slurm]`, no `time_min` or `mem_mib`. Its values get the patterns above; a `spectio.toml` value that does not match makes it `usable: false`, with the reason "partition in spectio.toml is not a valid name: run spectio init" (UX-PRE-FU86-R1-23).
- **`local`**, on every server, labelled "Login node" on a server set up with SLURM and "This machine" in local mode. On a SLURM server its tasks run on the login node, so it has `cpus = 2` and `mem_mib = 8192`: the EMBL login nodes cap each user at 8 cores and 128 GiB and their wiki discourages computation there ([login-node audit §7](../research/2026-11-08-embl-login-node-audit.md#7-login-node-policy)). In local mode it has no caps, as today.

The **default** environment is the built-in of the server's own kind (`slurm`, or `local` in local mode) until the user makes another one the default.

**Where definitions live.** In `environments.toml` in the data directory (in the shared home, next to `spectio.toml`), not in the database: the database is a node-local index that a purge or another login node rebuilds from the run directories (dev-env §15.3, Where data lives), so a definition kept only there would be lost. One server per user, so the file is per user. Its path comes from one function, `config_path().parent / "environments.toml"`, used by the routes, the runner and `spectio doctor` (`data_dir` and `$SPECTIO_CONFIG` can name different directories, `config.py:5-6`, `:67-68`); the only files Spectio writes in that directory for it are `environments.toml` and its temporary `.environments.toml.<hex>` (SEC-PRE-FU86-R1-08).
- **Format.** `default = "<name>"` (optional) and one `[environments.<name>]` table per environment, with the fields above (`[environments.<name>.slurm]`, `.local`, `.profiles`). Strict: an unknown key, a wrong type, a value outside its rule, or a `default` naming no environment (built-ins included) makes the whole file `invalid`. At most 64 KiB and 32 environments. The built-ins are not in the file.
- **Reads** (SEC-PRE-FU86-R1-04, -05, -11). The directory is opened with `O_DIRECTORY|O_NOFOLLOW` and checked with `fstat` (owned by the user or root, not writable by group or others); the file is opened relative to it (`openat`) with `O_RDONLY|O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC` (no symbolic link, no FIFO that blocks), checked with `fstat` (a regular file of the user, not writable by group or others), and read up to 64 KiB + 1 byte. `check_config` follows symbolic links (`config.py:46`, `:54`), so these opens replace it here. Every read runs in the bounded file pool with its timeout (req. 13), and the parsed result is cached by the file's identity (below), so a list costs one `fstat` when nothing changed. The file has five states:
    - `missing`: the built-ins only, normal;
    - `ok`;
    - `refused`: it fails the owner or mode checks, or is not a regular file, or an open of it or of its directory fails with `EACCES`, `EPERM`, `ELOOP` or `ENOTDIR`;
    - `invalid`: it does not parse, breaks a rule, or is over a cap. `tomllib` raises `RecursionError` on deep nesting (`"a=" + "[" * 30000 + "]" * 30000`, 60,002 bytes, on Python 3.13), so `RecursionError` and `ValueError` both give `invalid`, never a `500`. `detail` is the parser's message cut at its first quote or `(`, then its place, `(at line N, column M)` or `(at end of document)`, at most 200 characters, with control and format characters removed, never bytes of the file (*built 2026-11-09, FU-P3-86b to -86d*: a message that quoted a token loses it, `Expected ']'` becomes `Expected`);
    - `unreachable`: the file system did not answer within the pool's timeout, or an open, `fstat` or read of the file or of its directory failed with any other I/O error (`ESTALE`, `EIO` on NFS) (*built 2026-11-09, FU-P3-86b to -86d*).

  In every state but `ok`, only the built-ins are listed, with the state and its `detail`, and launches with a built-in still work. A launch naming a file environment while the file is `unreachable` gets `503 runner-offline`, as the file routes do; while it is `refused` or `invalid`, `422` on `environment`.
- **Writes** (SEC-PRE-FU86-R1-04, -08). One write at a time in the server (a process lock); under that lock: read and validate the file as above, check its identity, render the new text with `_toml_value` (`config.py`) and parse it back strictly, then write it through `write_file` on the directory's descriptor under `.environments.toml.<hex>` at 0600 (`O_CREAT|O_EXCL|O_NOFOLLOW`) and rename it into place (req. 5). The identity is `(st_dev, st_ino, st_size, st_mtime_ns)` and the SHA-256 of the bytes read; if it differs from the read the client edited from, `409 environments-file-changed` and nothing is written. A `refused`, `invalid` or `unreachable` file is never overwritten: writes get `409 environments-file-unusable` (`503` when unreachable) with the reason. An I/O error of the write itself (`ENOSPC`, `EDQUOT`, `EIO`) is a `503 runner-offline` with the reason, never a `500` (*built 2026-11-09, FU-P3-86b to -86d*). Comments in a hand-edited file are not kept by a write; the screens say so beside Save (inbox #133 choice 1).
    - **Accepted risk (0.0.1):** the lock is per server process. A hand edit, or a second server of the same user on another login node (req. 5's state file forbids one), that lands on NFS between the identity check and the rename is lost; there is no lock file. The window is a few milliseconds, the file has one writer in practice, and the user's edit is the one lost, not someone else's.
    - **A log line per write**: the route, the name, and the old and new values (no secret is in them) (SEC-PRE-FU86-R1-10).
- **The database is not the source of any run's environment** (SEC-PRE-FU86-R1-01). Each run row gets its own snapshot, a new `runs.environment` JSON column (§7): `{name, label, executor, slurm, local, state}` as resolved at launch (`state`: `recorded`, `not_recorded` or `not_readable`), written at launch and at rebuild from the manifest. Everything that depends on a run's executor reads that column, never `settings.executor` or an `environments` row: the failure summary's `on_slurm`, the `sacct` call and its "local" reason (`failure.py:823-894`), the `Accounting` decision to ask `sacct` (`failure.py:316`), the copied command (`resume.py:126`), Resume's payload and `GET /runs/{id}`. `runs.environment_id` keeps its foreign key to the single tenancy row, which `ensure_tenancy` updates by the built-in's name, not "the oldest row"; `environments.kind` and `config` are never used for a run.

**A run keeps what it ran with.** At launch the server validates the chosen environment and writes its values, as resolved, into the run's manifest `.spectio/run.json` (new optional field `environment: {name, label, executor, slurm, local}`), the run row's `runs.environment` and the launch command's payload; the runner validates the payload's snapshot again with the same strict model (`LaunchPayload` is lax today, `loop.py:266`) and builds the launch from it, never from the server's `executor`. So editing or deleting an environment changes no run. Copy to a new launch preselects the environment by name through the launch template (`GET /runs/{id}:launch-template` gains `environment`), with its current values, or the default with a notice when the name is gone. At rebuild the manifest's snapshot is read with the same validators (req. 10); a manifest from before this note has none (`not_recorded`); one that fails them is `not_readable`.

**Resume** applies the launch rules again to the parent's snapshot (SEC-PRE-FU86-R1-03), read from the parent's `runs.environment`, which came from its manifest through the validators:
- `recorded` and still allowed on this server: Resume runs with it, unchanged;
- a `slurm` snapshot on a server set up with `--local`: `422` on `environment`, "This run ran on SLURM; this server has no SLURM";
- a `local` snapshot without caps (from a local-mode server) on a SLURM server: Resume runs with the built-in `local` caps, and the Resume sheet says so;
- `not_recorded` (a run from before FU-P3-86): Resume runs on the built-in of the server's kind, and the sheet says "This run has no recorded environment: it resumes on the server's default (slurm)";
- `not_readable`: `422` on `environment`; Copy to a new launch is the way on.

**How values reach the engines** (the only places; each built by `headscript.py` from typed values, after the checks above):

| Executor | Nextflow (`.spectio/spectio.config`, a `-c` file) | Snakemake (arguments, one word each) |
|---|---|---|
| `slurm` | `process.executor = 'slurm'`; `process.queue = '<partition>'`; `process.clusterOptions = '--account=<account>'`; `process.time = '<time_min>m'`; `process.memory = '<mem_mib> MB'`; strings through `_groovy` (single-quoted, no interpolation) | `--executor slurm --slurm-keep-successful-logs --local-cores 2`; without a workflow profile, `--default-resources slurm_partition='<partition>' slurm_account='<account>' runtime=<time_min> mem_mb=<mem_mib>` and `--jobs`, as today |

- **Nextflow.** A `-c` file has the highest priority among configuration files, and a generic `process.*` setting has the lowest priority among process settings, so the pipeline's `withLabel` and `withName` selectors still win over the environment's time and memory, and a selector can still pick another executor ([Nextflow configuration](https://docs.seqera.io/nextflow/config), "Configuration file" and "Process selectors", read 2026-11-09). `executor.cpus` and `executor.memory` are "used only by the local executor and grid executors" ([executor scope](https://docs.seqera.io/nextflow/reference/config/executor), read 2026-11-09); the `$local` block scopes them to the local executor **[to be validated]** on Nextflow 25.x (SEC-PRE-FU86-R1-12). They cap what tasks may request, not what they use. An nf-core process that asks for more than the cap (`process_high`, 12 CPUs) may fail rather than wait **[to be validated]** on nf-core/rnaseq with the built-in `local` of a SLURM server. A pipeline that sets `clusterOptions` in a selector replaces the account, as today **[to be validated]** on nf-core/rnaseq.
- **Snakemake.** Each `--default-resources` value goes through `os.path.expanduser(os.path.expandvars(…))`, is then evaluated as a Python expression, and is kept as a string only on a `NameError` or `SyntaxError` (Snakemake 9.27.1, `snakemake/resources.py:801-825`). So Spectio passes partition and account as Python string literals (`slurm_partition='htc'`), which the patterns above keep free of quotes, backslashes, `~` and `$`; today's unquoted `slurm_partition=<value>` from `spectio.toml` changes with them (SEC-PRE-FU86-01). The SLURM plugin then builds the `sbatch` call as one shell string (`subprocess` with `shell=True`, `snakemake-executor-plugin-slurm` 2.8.0 `__init__.py:965`, `:1177`); it quotes account and partition (`:1655`, `:1729`) and runtime (`submit_string.py:116`) but not `--mem` (`submit_string.py:133`), which is why `mem_mib` is an integer only. It reads `runtime`, `mem_mb`, `slurm_account` and `slurm_partition` (`__init__.py:867-877`, `:1632-1638`, `:1684-1714`).
- **Snakemake concurrency on a login node** (SEC-PRE-FU86-R1-02). `--jobs` is an alias for `--cores` in local execution (`snakemake/cli.py:574-581`), and today `--cores` is left out when `extra_args` sets concurrency or a workflow profile is given (`headscript.py:153-155`), so the caps could be bypassed. For a `local` environment Spectio always passes `--cores <cpus>` last, after `extra_args` and with a profile too; that a later `--cores` wins over an earlier `--jobs` or a profile's `cores` is **[to be validated]** in a test of FU-P3-86c. Every `slurm` launch passes `--local-cores 2`, since local rules otherwise use every core of the login node (`cli.py:586`, "default: number of CPU cores of the host"). With a workflow profile, the profile still owns the SLURM resources (CR-P3T09-06, unchanged); the form says so (ui-spec §4.8.1).

- measured: `cpu_percent`, `cpu_eff`, `peak_rss_bytes`, `peak_vmem_bytes`, `mem_eff`, `realtime_s`, `time_eff`, `wait_s`, `rchar_bytes`, `wchar_bytes`, `read_bytes`, `write_bytes`; ratios as 0.63 for 63 %, never clamped (schedulers §3.6); a value the source does not give is null.

Why a table and not columns on `attempts` or the `attempts.resources` JSON: the across-runs filters need indexes on typed values over many runs, and `attempts` stays the engine's record. `attempts.resources` is unchanged; the `sacct` cache (`sacct.json`, §7 note 2026-11-01) stays the cache, and this table holds the values Spectio took from it, so the across-runs page needs no call. Size: about 200 bytes a row, 20 MB for 100,000 attempts **[to be validated]** on SQLite. Rows of runs from before the migration are filled once by the migration from `attempts.resources` (Nextflow's six values, Snakemake's request) and `sacct.json`, with no `sacct` call.

**Indexes** (in §7 with the migration): `(ended_at)`; `(process_or_rule, ended_at)`; `(pipeline, process_or_rule, ended_at)`; `(partition, ended_at)`; `(run_id)`; `(owner_id, ended_at)` where multi-user.

**`GET /runs/{id}/performance`** (session, the run's read right):
- Query: `process=` (repeatable, at most 50), `metrics=` (comma list of the measured columns above; default all), `points=true|false` (default `true`), `attempts=last|all` (default `last`: each task's last attempt, as §3.6's aggregate).
- Answer: `{run_id, measured, pending_accounting, processes: [{process_or_rule, stage_id, pipeline_order, n, measured, sources: {<source>: n}, requested: <the §5 efficiency `requested`>, stats: {<metric>: {n, min, q1, median, q3, max, mean} | null}, waste: [{metric: "mem_eff" | "cpu_eff", below: 0.25, jobs: n}]}], points: {items: [{task_id, attempt, process_or_rule, tag, partition, source, <metric>: value}], truncated: bool, stride: n}}`. `pending_accounting` counts the attempts whose `sacct` answer is still awaited (§3.6 timing step 3); the screen says the numbers may change.
- Quartiles by linear interpolation between the closest ranks (the method of `numpy.percentile`'s default) **[to be validated]** against Nextflow's report on one run, computed on read over every measured attempt, never over the capped points.
- Caps: `points.items` at most 2,000 per process and 20,000 per answer; above, every `stride`-th attempt in task order, `truncated: true`. A run with more than 200 processes answers the first 200 by `pipeline_order` and `processes_truncated: true`.
- The waste line is §3.6's, one rule for the Run detail aside and this tab.

**`GET /performance:summary`** (across runs; session; the caller's visible runs, §6):
- Filters: `since`, `until` (ISO 8601 date-times, UTC; default the last 30 days; at most 366 days apart, else `422` on `until`), `pipeline`, `pipeline_version`, `process` (repeatable, at most 20), `partition` (repeatable), `environment` (repeatable), `engine` (`nextflow`, `snakemake`), `state` (the attempt's: `succeeded` default, `failed`, `all`), `run_state` (repeatable), `user` (only where multi-user, §6; `me` default; ignored in single-user mode), `attempts=last|all`. A filter on `ended_at`.
- `group_by=process|partition|pipeline|run|day|week` (one or two, e.g. `process,day` for a trend), `metrics=` as above.
- Answer: `{groups: [{key: {process_or_rule?, partition?, …, period_start?}, runs, n, stats: {<metric>: {n, min, q1, median, q3, max, mean}}}], truncated, scanned}`. At most 500 groups (`truncated: true` above, largest `n` first); at most 1,000,000 rows scanned, else `422 range-too-wide` with the count, so the screen asks for a narrower range. `day` and `week` periods are in UTC; the screen shows local time.
- **`GET /performance/attempts`**: the same filters, the rows of `attempt_metrics` joined to the run's name, paged as every list (`{items, next}`, 50 a page, at most 500), sort `-ended_at` (default), `cpu_eff`, `mem_eff`, `-peak_rss_bytes`, `-realtime_s`, `-wait_s`.
- **`GET /performance/facets`**: the distinct `pipeline`, `pipeline_version`, `process_or_rule`, `partition`, `environment_id` and `engine` values in the range, at most 500 each, for the filter menus.

## 6. Identity, tenancy and permissions

Sign-in methods, sessions, tokens, magic links, share links and pipeline provisioning are specified in [`authentication-and-access.md`](authentication-and-access.md). This section owns principals, tenancy and roles.

### Model
- **Principal**: anything that can act. `kind ∈ {user, service, agent, runner, system}`. Users are people; service accounts are integrations (LIMS, CI, robots); agents are AI agents (with model and version recorded on each action); runners are Spectio processes on compute environments; `system` is Spectio itself.
- **Group**: a lab, team or facility. Flat in v1, with an optional `parent_id` for later hierarchy. Memberships carry a role: `member`, `admin` or `pi` (principal investigator, as in depictio); groups synced from the identity provider are flagged `sso_managed`.
- **Project**: the unit of ownership and sharing. Owned by one group. Visibility `private` (grants only), `group` (all members of the owning group) or `instance` (everyone can read).
- **Grant**: `(project, principal or group, role)`, role ∈ `viewer < launcher < reviewer < editor < owner`. `viewer`, `editor` and `owner` mean exactly what they mean in depictio; `launcher` and `reviewer` are Spectio-only steps between viewer and editor (§13).
- **Environment grant**: which projects or groups may launch on an environment. Clusters and their credentials belong to groups, not to users.

### Roles on a project
| Action | viewer | launcher | reviewer | editor | owner |
|---|---|---|---|---|---|
| See runs, logs, artefacts | ✓ | ✓ | ✓ | ✓ | ✓ |
| Launch, relaunch, cancel own runs | | ✓ | ✓ | ✓ | ✓ |
| Decide gates (when the gate policy names them) | | | ✓ | ✓ | ✓ |
| Cancel anyone's runs, edit workflow manifests | | | | ✓ | ✓ |
| Manage grants, webhooks, service accounts, delete | | | | | ✓ |

Gate policies in `spectio.yml` name principals or groups (`humans: [group:rnaseq-core]`, `agents: propose`); the decision endpoint checks both the role and the policy.

### Tokens and scopes
Personal tokens, service-account tokens and agent tokens share one format (`spk_<kind>_<random>`, stored hashed), with scopes (`runs:read`, `runs:launch`, `gates:decide`, `gates:propose`, `artifacts:read`, `admin`), an expiry, and an optional project restriction. Runner credentials are separate: a one-time registration token becomes a rotating runner credential bound to one environment.

### Single-user mode
- `auth.mode: single` (the default for `spectio serve`). At first start Spectio creates: the instance, a user named after the OS account, a group `personal`, a project `default` owned by that group, and owner rights for the user.
- Requests from `127.0.0.1` / a Unix socket without a token are treated as that user. Not in 0.0.1: there, every request needs the token from a one-time link (revised 2026-10-27, [`dev-environment-and-testing.md`](dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts) §15.3). Any remote access (another machine, a runner, an integration) still needs a token, created in Profile › Tokens or with `spectio token create`.
- The UI hides the project switcher and sharing controls while there is a single project and user; all API fields are still present.

### Moving to multi-user (no migration)
`spectio auth enable oidc --issuer … --client-id …` (EMBL SSO; LS Login for external collaborators), then link the existing local user to their OIDC identity, invite users, create groups and grant projects. Optional later: LDAP, SCIM group sync, and a CLI device authorization flow for `spectio login`. SAML 2.0 is supported as well as OIDC, because depictio uses SAML (§13).

### Enforcement
One policy function `can(principal, action, resource)` in the service layer, used by the REST API, WES, MCP and the UI's server-rendered data alike. List queries join on `visible_projects(principal)`. With Postgres, row-level security on `project_id` can be added as defence in depth. Every write appends to the audit log.

## 7. Database schema

Portable across SQLite (WAL, local disk, with the WAL-reset fix, rule below) and Postgres: ULID text primary keys, UTC timestamps, JSON in `TEXT` (SQLite JSON1) / `JSONB` (Postgres) through the ORM type, `CHECK` constraints instead of enums, no SQLite-only features. Search uses exact and prefix matches on indexed keys only (IDs, external refs, names, tags), and task search is scoped to one run; tasks reach 10⁷–10⁸ rows a year, where `LIKE '%q%'` does not scale. Full-text search is engine-specific (FTS5 in SQLite, `tsvector` or `pg_trgm` in Postgres), so it comes only as an optional adapter per engine, allowed by name. Every tenant table has `project_id`, `created_by` (principal) and `created_at`; mutable ones add `updated_at` and `deleted_at` (soft delete).

**SQLite version rule.** The SQLite library Python loads (`sqlite3.sqlite_version`, not a system `sqlite3` binary) must carry the WAL-reset fix: ≥ 3.51.3, or ≥ 3.50.7 / ≥ 3.44.6 in those series ([sqlite.org/wal.html](https://www.sqlite.org/wal.html) §11, read 2026-10-26). The server checks it at start.

### 7.1 Run and gate state machines

This section owns the run and gate state enums and their WES mapping. *(assumed — pending Thomas, inbox #29)*

1. **Run states.** `runs.state` ∈ {`queued`, `running`, `pausing`, `paused`, `awaiting_review`, `cancelling`, `succeeded`, `failed`, `cancelled`}, lower snake case, enforced by a `CHECK` constraint.
2. **Run transitions** and their trigger:
    - `queued` → `running`: the runner reports the head process started, or the first engine event arrives;
    - `queued` → `failed`: the runner reports that the launch could not start; `runs.failure = {class, message}` *(assumed — pending Thomas, inbox #40)*;
    - `running` → `awaiting_review`: a gate opens at the end of a stage (`spectio.gate.opened`);
    - `awaiting_review` → `running`: decision `approve`, `apply` or `go_back` starts the next launch (`spectio.gate.decided`);
    - `awaiting_review` → `cancelled`: decision `stop`;
    - `running` → `succeeded` / `failed`, by a server rule *(assumed — pending Thomas, inbox #32)*. Engine completion and failure events move `launches.head_state` only; the server moves `runs.state` using the stage plan:
        - when the last planned launch succeeds, `running` → `succeeded`; `spectio.run.completed` is emitted only then;
        - at a stage boundary the run stays `running` with flag `evaluating_gate` until the gate row is written, then becomes `awaiting_review` (or is auto-approved and the next launch is queued, [`checking-scenarios.md`](checking-scenarios.md) §12.4); an error while evaluating checks opens the gate with verdict `error`;
        - an engine failure in any launch gives `failed`. `failed` is terminal: Resume and Relaunch create a child run (`parent_run_id`), and modes `resume` and `rerun_from` reuse the parent's `launch_dir` (§5.1);
    - `running` → `failed`: the runner reports the head exited (`launches.exited_at` set) and no engine terminal event arrives within a configured delay after spool replay; `failure_class` is `engine_fault` (non-zero exit) or `head_lost`, and in-flight tasks get a `failed` attempt of class `head_lost` *(assumed — pending Thomas, inbox #40)*;
        - *Note 2026-11-08 (G7):* once a Nextflow launch's `launches.head_state` is `succeeded` or `failed` (its `onFlowComplete` ingested), the delay does not apply: the runner reports the head's end after one last spool read (events such as `onFlowError` can follow `onFlowComplete`: the captured spool `tests/fixtures/engine-events/nextflow-26.10.4_plugin_toolerr.spool.jsonl` lines 292-293, Nextflow 26.10.4, and `engine-bridges/nf-spectio/src/spectio/SpectioPlugin.groovy:114`), with its exit code, no grace and no failure, so `launches.exit_code` and `exited_at` are set at the next head watch. Code: `RunnerLoop._report` in `spectio.runner.loop`, `LaunchRef.engine_ended` in `spectio.runner.types`;
    - `running` → `succeeded` / `failed` on Snakemake: no engine event ends a Snakemake launch, so its head's exit code does: 0 gives `succeeded`, any other code `failed` with `runs.failure` (§7); open attempts become `aborted` first (§7.2). The rule above does not apply: a known exit code wins over a `head_lost` or `engine_fault` failure in the same head report, and only an unknown exit code gives `head_lost`; `launch_error` still fails the run. The runner applies the head report only after it has ingested the launch's last spool batch, because job events after the run's end are only logged (§8.2) *(assumed — P3 Task 5, pending Thomas, [inbox #81](../reviews/inbox.md#81-assumed-the-snakemake-mapping-and-four-review-rounds))*;
    - `queued`, `running`, `awaiting_review` or `paused` → `cancelling`: a cancel request; `cancelling` → `cancelled`: the runner reports the head process ended;
    - `running` → `pausing` → `paused`, and `paused` → `running`: pause and resume (which verbs lead there is open, inbox #16).

    Every transition emits `spectio.run.state_changed` with the new value.
3. **Gate states.** `gates.state` ∈ {`open`, `decided`, `expired`, `superseded`}: `open` → `decided` (a decision is recorded); `open` → `expired` (the policy timeout passes and `on_timeout` applies); `open` → `superseded` (the run is cancelled, or a relaunch from an earlier stage replaces the gate). Timeouts are persisted (`gates.timeout_at`) and evaluated by a sweep. A gate whose `timeout_at` passed while the server was down gets a grace period after boot of three heartbeat intervals (as in [`admin-and-operations.md`](admin-and-operations.md) §3.2) before `on_timeout` applies; the decision records `applied after restart`. An automatic approval is recorded as a decision with `decisions.actor_kind = service` ([`checking-scenarios.md`](checking-scenarios.md) §12.4) *(decided — Thomas, 2026-10-27, inbox #33)*.
4. **Not states.** "Head silent" and "runner offline" are flags on the run (`runs.flags`); waiting for an external signal is a condition of an open gate.
5. **WES 1.1.0 mapping.**

### 7.2 Task and attempt states

This section owns the task and attempt state enums.
- `attempts.state` ∈ {`pending`, `submitted`, `running`, `succeeded`, `failed`, `cached`, `stored`, `aborted`}, plus `attempts.ignored` (boolean: a failure the engine ignored, Nextflow `errorStrategy 'ignore'`).
- `tasks.state` is the state of its last attempt, or `not_scheduled` when the engine planned the task but never created an attempt. "Retried" is not a state: the UI shows it for a task whose last attempt has n > 1.
- States only move forward: `pending` < `submitted` < `running` < {`succeeded`, `failed`, `cached`, `stored`, `aborted`}; a late event of a lower rank is kept in the log but does not change the state (§8.2).
- `aborted` is the end of an attempt that the engine stopped, or never ran, because of another failure. When a launch ends, the projector moves every attempt still `pending`, `submitted` or `running` to `aborted`; a task with no attempt stays `not_scheduled`. An `aborted` attempt is not a failure: it has no `failure_class` and does not count as failed. When the head is lost instead, §7.1 applies (`failed`, class `head_lost`). Seen in spike T2: after a fatal error, a task got `onTaskPending` and nothing after (26.10.4), and a running task ended `ABORTED` in Tower (25.10.9) ([T2 note](../research/spike-engine-events-2026-10-28.md#differences-with-the-specs), row 9). *(assumed — pending Thomas, inbox #56)*
- Engine mapping, Nextflow (`nf-spectio`):
    - `onTaskPending`, `onTaskSubmit` and `onTaskStart` give `pending`, `submitted` and `running`;
    - `onTaskComplete` gives the state from the trace record's `status`: `COMPLETED` → `succeeded`, `FAILED` → `failed` (with `ignored` set when `errorAction` is `IGNORE`, not seen in spike T2 **[to be validated]**), `ABORTED` → `aborted` (spike T2 saw `ABORTED` in Tower, and once in the trace record of its own plugin: `COMPARE` `treatB_vs_ctrl` in the 25.10.9 toolerr capture, `tests/fixtures/engine-events/nextflow-25.10.9_plugin_toolerr.spool.jsonl:288`; `nf-spectio` sends it too: in two runs of its tool-error test (`nf_failed_run` in `test_bridge_nextflow.py`) on Nextflow 26.10.4, one `onTaskComplete` of `COMPARE` `treatB_vs_ctrl` carried trace `status` `ABORTED` with `exitStatus` and `exit` null (P3 Task 6, read 2026-10-30, [P3-M1](../progress/W5/P3-M1.md#task-6-nf-spectio-writes-the-spool_1)); it depends on timing, on whether `treatB_vs_ctrl` is still running when `COMPARE` `treatA_vs_ctrl` fails, so it is not seen on every run: in a third run, `treatB_vs_ctrl` ended `COMPLETED` and no `ABORTED` was sent). | `spectio.environment.capacity_low` | an environment's quota is above 90 %, or maintenance starts within 24 h *(assumed — pending Thomas, inbox #29)* | `spectio.environment.capacity_low.json` |
| `spectio.ext.<plugin>.*` | a plugin's own events ([`architecture-plugins-and-packaging.md`](architecture-plugins-and-packaging.md) §3.4); the plugin declares their `data` schema, exported with its settings schema in `spectio-plugin.json` (architecture §4) | declared by the plugin in `spectio-plugin.json` |

This table is the complete catalogue. Every type goes to webhooks and SSE unless marked SSE only. Engine-native events are logged in the same `events` table under `spectio.engine.*` with a `seq`; they are internal, read through `GET /events?run=`, and never delivered to webhooks. Heartbeats are not logged. `spectio.run.completed` and `.failed` are emitted after the `spectio.run.state_changed` they follow. *(assumed — pending Thomas, inbox #38)*

Delivery: at least once, from the event log written in the same transaction as the change. Each subscriber (webhook, notifier, sink, bridge) has its own cursor over the log, so a slow subscriber (such as the depictio hand-off) never delays another. An ordered subscriber is delivered in `spectiosequence` order and blocks only per (subscriber, run); a subscriber pauses after N consecutive failures until an admin resumes it ([`admin-and-operations.md`](admin-and-operations.md) §3.3). Delivery rows are written only for failed attempts. HMAC-SHA256 signature in `Spectio-Signature` with a timestamp; the signing secret is generated by Spectio, shown once at creation and stored through the secret backend (`webhooks.secret_ref`, §7), never as a hash, because an HMAC needs the plaintext; rotation keeps the old secret for 24 h and sends both signatures during the overlap; exponential retry for 24 h; redelivery from the API. **Test:** a database dump contains no webhook secret.

**Who receives which event.** *(decided — Thomas, 2026-10-27, inbox #13)*
- Every event carries a project (`spectioproject`) or, for runner and environment events (`spectio.runner.offline`, `.online`, and scheduler events such as `spectio.environment.capacity_low`, [`schedulers-and-monitoring.md`](schedulers-and-monitoring.md) §8), an environment (`spectioenvironment`). An event with neither is not published.
- Project events go to principals who can read the project. Environment events go to principals with a grant on the environment.
- **SSE and `GET /events`** filter each event at fan-out against an authorisation cache, not only when the stream opens. A "grants changed" pub/sub message invalidates the cache. A stream whose principal loses access, or whose token or session is revoked, ends within 30 s.
- **Search** (`GET /search`) is a union of the per-type list queries, each joined on `visible_projects()` (§6), never an unfiltered index. Counts, facets and autocomplete are computed after that filter.
- **Embedded elements** stream with `fetch()` and an `Authorization` header, or with a single-use stream ticket valid for 60 s. A bearer token never goes in a query string, because the browser's `EventSource` cannot send headers ([WHATWG HTML](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-eventsource-interface)).
- **Tests:** two-tenant search and SSE fixtures; revoking a grant during a stream closes it; no `token=` appears in access logs.

### 8.1 Event pipeline

1. Ingest validates the batch, appends it to `events` and acknowledges.
2. One projector, on a dedicated writer thread or process with one write connection, builds `runs`, `tasks` and the other projections from the log.
3. SSE reads the projections (§8.3).

Heavy background tasks (RO-Crate export, backup, check evaluation) run in a subprocess pool, even in the Python bundle, so they never block the event loop that serves the UI and SSE. Under back-pressure, ingest answers `429` with `Retry-After` (bridge side: [`architecture-plugins-and-packaging.md`](architecture-plugins-and-packaging.md) §13.2). *(assumed — pending Thomas, inbox #28)*

Why: `sqlite3` calls are synchronous; measured in R4, 200 000 events take 7.2 s of CPU with Pydantic plus SQLAlchemy Core, so a 100 000-event burst on the request path stalls the loop for seconds, and slower acknowledgements make the bridges time out and retry. Every new projection would otherwise add cost to the ingest hot path.

**Projection checkpoint and recovery.** The projector stores `runs.projected_seq`, updated in the same transaction as the projection rows. On boot it projects every run with `projected_seq < last_seq` before serving it as fresh (boot order: [`architecture-plugins-and-packaging.md`](architecture-plugins-and-packaging.md) §7.2). Until it has caught up, the run is returned with `recovering: true`, and state-changing verbs on it return `409 run-state-conflict` (§5) *(assumed — pending Thomas, inbox #40)*. Side effects use deterministic IDs, for example a gate keyed on (run_id, stage_id, launch n), so re-projection is a no-op.

### 8.2 Ordering, cursors and clocks

- **Per-run sequence.** `seq` is allocated under the run row lock (`UPDATE runs SET last_seq = last_seq + n RETURNING last_seq`), so within a run commit order equals `seq` order, without gaps or duplicates.
- **Resuming streams.** A single-run stream resumes with `Last-Event-ID` = the run's `seq`. A stream that covers many runs (Overview, Review queue, `/events` without `run=`) resumes by snapshot then tail: on reconnect the client refetches the runs it shows through REST, then subscribes from now. There is no global cursor: on Postgres, concurrent writers commit a `bigserial` out of order, and a reader resuming from `id > N` would silently skip rows with lower IDs that commit later.
- **Producers and source order.** Every event carries `source` (engine bridge, scheduler observer, live check) and `source_seq`, monotonic per (run, launch, producer): a bridge's counter starts again in each launch's head process (2026-10-29, api §14.1).
- **State lattice.** Projections never move a terminal state back. The run lattice applies per run; launch outcomes live on `launches`; a child run never reopens its parent *(assumed — pending Thomas, inbox #32)*. For tasks the lattice applies per attempt, in the rank order of §7.2; a retry creates a new attempt *(assumed — pending Thomas, inbox #40)*. A repeated engine flow completion for the same launch is logged but changes nothing: the first one sets `launches.head_state`, and a second one neither changes `head_state` or `exited_at` nor emits a second `spectio.run.*` event. Nextflow 25.10.9 sent `onFlowComplete` twice in one failed run ([T2 note](../research/spike-engine-events-2026-10-28.md#differences-with-the-specs), row 6). Only the engine sets task success, while the scheduler observer adds `failure_class` and usage. Retried batches arrive out of order and spooled events arrive minutes late ([`architecture-plugins-and-packaging.md`](architecture-plugins-and-packaging.md) §13.1), so arrival order alone would let an attempt go back from `succeeded` to `running`, or let a scheduler job state (`sacct` `COMPLETED`) mark a task done before the engine has decided on a retry. Engine status values (Nextflow `COMPLETED`) are engine vocabulary mapped through §7.2, distinct from scheduler job states.
- The arrival `seq` stays the SSE cursor only.
- **Clocks.** Events store `engine_time` (the producer's clock) and `received_at` (the server's). Order only by `seq` and `source_seq`, never by ULID or `time` across hosts (ULIDs embed the clock of the host that mints them, §4); compute durations from one clock source; freshness checks ('head silent', 'runner offline') and gate timeouts always use server receive time.

### 8.3 Live streams (SSE)

- The server sends at most one coalesced delta per run per second: counters per process and state, and the IDs of changed rows; clients refetch what they show.
- Raw task events go only to a client that has that task open.
- A browser opens one `EventSource`, shared by its tabs ([`ui-spec.md`](ui-spec.md) §7).
- Each server process caps its SSE clients; clients reconnect with jitter.
- Team servers serve the UI over HTTP/2 ([`architecture-plugins-and-packaging.md`](architecture-plugins-and-packaging.md) §7.2). *(assumed — pending Thomas, inbox #28)*

Why: at 1–10 k events/s for one run, applying every event in every watching tab freezes it; over HTTP/1.1 a browser allows only 6 SSE connections ([MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)); with an HPA, every rollout or scale-down reconnects every stream at once.

Note 2026-10-28: 0.0.1 keeps live refresh over SSE, rather than polling, for the runs list and the run detail *(decided — Thomas, 2026-10-28; [decision log](../decisions/log.md#2026-10-28-001-live-refresh-over-sse-sqlite-as-a-rebuildable-index))*. One stream per browser, behind the session cookie ([`dev-environment-and-testing.md`](dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts) §15.3 req. 2 and 3).

Note 2026-10-30 (0.0.1 stream, P1 Task 18):

- **In-process.** After each commit, the writer thread hands the runs and tasks the commit changed to the stream, which only records them. A new run counts as a change. Once a second, one pump on the event loop sends one `spectio.run.delta` per changed run.
- **Frames:** a strict subset of §8.5, `{run_id, seq_through, counts, changed: {tasks}}`, with no `id:` line and no `Last-Event-ID` replay; a client refetches on reconnect. `: keep-alive` opens each stream and follows 15 s without a frame.
- **Slow clients.** Each client has a queue of 64 frames; a client that falls behind is dropped and its stream ends.
- **Cap.** At most 32 open connections per process, else `429 rate-limited`. A connection holds its slot from the check to the end of its response, also once dropped, so opens that arrive together cannot pass the cap.
- **Not yet:** the session of req. 2 (P1 Task 16), a filter per subscriber (every subscriber gets every run's delta, one Unix user in 0.0.1), and a size bound on `changed.tasks` (follow-up FU-P3-20).

### 8.4 Event retention and raw payloads

While a run is active, every event keeps its full raw payload next to the normalised columns. Once the run is terminal and a configurable number of days has passed, a cleanup job moves the raw payloads into one compressed file per run (`events-<run>.jsonl.zst`) in the file store and keeps only the normalised rows. The raw payload kept per task is the terminal one. Backups copy these archives as files, not rows ([`admin-and-operations.md`](admin-and-operations.md) §4.3). *(assumed — pending Thomas, inbox #28)*

Why: about 0.7–0.9 GB per 100 000-task run (measured in R4: 733 MB per 500 000 events) and about 1 TB a year on a team server unpruned (estimate); Nextflow `TraceRecord.FIELDS` has 45 fields, including `script`, `env` and `workdir` (`modules/nextflow/src/main/groovy/nextflow/trace/TraceRecord.groovy:69-112`, `114f1fe`), repeated on every lifecycle event, and `env` may contain secrets.

### 8.5 Stream frames

`GET /events/stream` sends SSE frames whose `event:` is the CloudEvents type and whose `data:` is the envelope. `id:` is the run `seq` and is set only on logged events. With `Last-Event-ID` the server replays logged events after that seq, then sends a fresh `spectio.run.delta`. `spectio.run.delta` (coalesced, §8.3): `{run_id, seq_through, counts: {<process>: {<state>: n}}, changed: {tasks: [], stages: [], gates: []}}`. Raw task events go to `GET /events/stream?run=<id>&task=<id>`. Filters: `run`, `project`, `type`. *(assumed — pending Thomas, inbox #38)*

### 13.3 Run → dashboard hand-off
depictio already knows how to build a project from a pipeline's results (versioned templates for 32 nf-core pipelines, 41 templates in all, counted with `find depictio/projects/nf-core -name template.yaml` at depictio `0d1aa0a`; `depictio ingest --pipeline-id --triggered-by --attach-run --user --provenance-file --result-json`). `--pipeline-id` needs an exact shipped template: it accepts only an exact version, `latest` or no version, and exits 1 with no fallback otherwise (`depictio/cli/cli/commands/run.py:1384-1400`, `cli/utils/templates.py:131,214-257`). The rule "closest shipped version not newer than the run" applies only to auto-detection without `--pipeline-id` (`templates.py:291-313`), and `--compose` cannot rescue the call (`run.py:1464-1468`). So `template: auto` never passes `--pipeline-id`: Spectio lets depictio detect the template from the run directory (closest not newer, then compose), or passes an explicit `--template <id>` that it resolved beforehand (request 14 in [`depictio-ecosystem-reuse.md`](depictio-ecosystem-reuse.md) §3). Spectio drives that path:
```yaml
# spectio.yml (or the workflow's settings in Spectio)
depictio:
  on: completed            # or gate:<id> · stage:<n>
  template: auto           # detected by depictio from the run directory; or an explicit template id, e.g. nf-core/rnaseq/3.26.0
  project: per_run         # default: one depictio project per Spectio run (QC dashboards); or linked: the project linked to this Spectio project
  attach_run: false        # with project: linked, add this run to it (file-based collections only)
```
The `depictio:` key is part of the `spectio.yml` schema ([`checking-scenarios.md`](checking-scenarios.md) §12); this section owns what the hand-off does. *(assumed — pending Thomas, inbox #29)*

**One depictio project per Spectio run.** *(decided — Thomas, 2026-10-27, inbox #22)* With `--attach-run`, the project is found by `--project` (a name, not an ID) or by the template's own name, and collections that a recipe computes still read the project's first run only (depictio `0d1aa0a`: `depictio/cli/cli/commands/run.py:2918-2939`). A flat run is named after its directory (`flat_run_tag = os.path.basename(os.path.normpath(location))`, `cli/utils/scan.py:798-825`), two outdirs both named `results` clash and stop the ingestion (`run.py:966-975`), and `--result-json` returns no run ID or run tag (`run.py:157-177`). So QC dashboards use one depictio project per Spectio run, and `attach_run` serves file-based collections only, until depictio adds a `--run-tag` option and builds recipe collections from every attached run (requests 15 and 16 in [`depictio-ecosystem-reuse.md`](depictio-ecosystem-reuse.md) §3).

1. On the trigger, the **runner** (which sits next to the results) runs `depictio-cli ingest <outdir> --pipeline-id <org>/<name>/<version> --triggered-by spectio --attach-run --user <owner email> --provenance-file <run summary or RO-Crate> --result-json <file>`, with a short-lived credential from the server.
2. The server stores the returned project and dashboard links on the run, shows **Open in depictio** in Run detail and emits `spectio.run.dashboard_ready`.
3. For runs Spectio launches, depictio's own Nextflow `onComplete` trigger is turned off (`--depictio_enabled false`) to avoid ingesting twice. For Snakemake, Spectio provides the trigger depictio lacks.
4. **Refresh without the CLI.** depictio already has a server-side ingestion call: `POST /depictio/api/v1/projects/ingestion/trigger/{project_id}` starts a `project.ingest` job (depictio `0d1aa0a`: `depictio/api/v1/endpoints/projects_endpoints/routes.py:659-760`). It is off by default (`DEPICTIO_INGESTION_BROWSER_TRIGGER`), confined to `DEPICTIO_INGESTION_ALLOWED_DATA_ROOTS`, needs editor rights on the project, and returns 409 when the server cannot read the locations. It only re-ingests an existing project's locations: it cannot create a project or add a run. When depictio reads the same storage, the server uses it to refresh a gate-time project (`on: gate:<id>`) at completion; creating a project or adding a run still goes through the CLI of step 1.
5. **Decisions travel as data.** Gate decisions and filter artifacts (cell keep lists, bin lists, excluded samples) are not provenance. The runner writes `spectio/spectio_checks.tsv` and `spectio/spectio_decisions.tsv` (the decision tables of §13.6) into the ingested directory. They become data collections through a template overlay (`--project-config-path`), or through `--compose --include 'spectio/*.tsv'` when composing (`depictio/cli/cli/commands/run.py:3055-3072`), with joins declared on the item key (§13.6 rule 2). `--provenance-file` carries only short scalars: the Spectio run URL (`spectio_run_url`), gate IDs and decision counts. depictio lists its entries under "User provided" in the project's run-provenance report, cuts each value at 500 characters (`_PROVENANCE_VALUE_MAX`) and stores it once per project, not per run (`run.py:2951-2962`; `cli/utils/templates.py:1003,1053-1065,1149-1162`; `depictio/models/models/templates.py:368,400-412`), so it can carry neither a keep list nor an RO-Crate (request 6 in [`depictio-ecosystem-reuse.md`](depictio-ecosystem-reuse.md) §3).
6. **Which `depictio-cli`.** Wherever the ingestion runs (step 1; where it runs and with which credential waits for inbox #22), the sink first reads the depictio server version from `GET /depictio/api/v1/utils/status`, then uses, in this order: a site-configured `depictio_cli_executable`; the image `ghcr.io/depictio/depictio-cli:<server version>` through Apptainer or Docker (depictio `build-images.yaml:14-16`, `docker-images/Dockerfile.cli:103`); `uvx depictio-cli==<server version>`. The route taken and the version are recorded in the run's hand-off record, and `spectio doctor` reports which route resolves. depictio's base install is about 0.9 GB ([`depictio-cli-packaging.md`](../research/depictio-cli-packaging.md) §3.1), far above the runner's 80 MB ([`cli-and-shared-libraries.md`](cli-and-shared-libraries.md) §6), so it is never added to the runner.

Rules:
1. **Same computation.** A check that has a catalogue binding uses it. The runner runs the recipe on the partial outputs at gate time, and the hand-off of §13.3 ingests the same tables. Spectio never re-implements a recipe that the catalogue has.

5. **Live checks** ([`checking-scenarios.md`](checking-scenarios.md) §11) cannot use catalogue outputs that read the final `multiqc.parquet`; they use per-file bindings until depictio has per-file recipes.

### 14.1 Driven runs (0.0.1)

Written 2026-10-29 (P1 Task 1, [decision log](../decisions/log.md#2026-10-29-api-14-driven-run-part-written-inbox-36-a)). In 0.0.1 the bridges only append to a spool in the launch directory; the runner inside `spectio serve` reads it from the shared file system and nothing posts over the network ([`dev-environment-and-testing.md`](dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts) §15.3 req. 6; architecture §13.1). The numbers are *(assumed — pending Thomas, inbox #28)* (P1 Assumption 12); `spectio_sdk.events` implements this section and its tests are `packages/spectio-sdk/tests/test_spool_events.py`.

**Files.** A driven bridge reads `SPECTIO_RUN_ID`, `SPECTIO_LAUNCH_N` and `SPECTIO_SPOOL_DIR` (`<launch dir>/.spectio/events/`) from the head script, and writes `<producer>-<launch>-<nnnn>.jsonl` there: `<producer>` is the bridge name of the envelope, `<launch>` the launch number, `<nnnn>` a four-digit index from `0001`. The reader accepts exactly `(nf-spectio|snakemake-logger-spectio)-<launch>-<nnnn>.jsonl`, with `<launch>` 1 to 19 digits and no leading zero, and `<nnnn>` four digits other than `0000` (`SPOOL_FILE_NAME` in `spectio_sdk.events`). The naming for runs started from a terminal is architecture §13.8. *Note 2026-11-07 ([P3 Task 25](../progress/W5/P3-M6.md#task-25-pointer-file-in-both-bridges-the-server-finds-and-shows-the-run)):* the 0.0.1 reader accepts it for a `cli-observed` run: `<run ID>-(nf-spectio|snakemake-logger-spectio)-<nnnn>.jsonl`, with `<nnnn>` four digits other than `0000` (`TERMINAL_SPOOL_FILE_NAME` in `spectio_sdk.events`), and only the files named for the run ID of its pointer. For a run Spectio launched, and for another run's name, such a file is still counted `bad_name`. Files are UTF-8 and append-only, one JSON object per line, each line ended by `\n`; a last line without its `\n` is still being written, and the reader waits for it until it passes `MAX_LINE_BYTES`. Readers take the files in name order.

| Bound | Value | Who applies it |
|---|---|---|
| `MAX_LINE_BYTES`: one line, without its `\n` | 65 536 bytes | writer: never writes a longer line; reader: drops a longer one |
| `ROTATE_BYTES` | 33 554 432 bytes (32 MiB) | writer: opens `<nnnn + 1>` when the next line would take the file past it |
| `MAX_FILE_BYTES` | 67 108 864 bytes (64 MiB) | reader: ignores everything past it in one file |
| `MAX_SPOOL_FILES` | 1024 files | reader: the spool files of one launch it takes; the others are counted `too_many_files` |
| `MAX_DIR_ENTRIES` | 16 384 entries (16 × `MAX_SPOOL_FILES`) | reader: the directory entries one read looks at in `events/` |
| `MAX_BAD_NAMES` | 64 names | reader: names outside the grammar counted one by one as `bad_name`; later ones count `too_many_files` |
| `MAX_READ_BYTES` | 2 097 152 bytes (2 MiB) | reader: the bytes one read takes from the files, skipped bytes included (the default of `max_bytes`) |
| `max_lines` | 5000 lines | reader: the lines one read returns or drops (the default) |
| `MAX_EVENT_NODES` | 4096 JSON values | reader: the values in one event's `data`, `data` itself included |
| `MAX_EVENT_DEPTH` | 32 levels | reader: the nesting of `data`, which is level 1 |
| pre-parse bound | more than 2 × (4096 + 16) = 8224 of `[`, `{` and `,` in one line | reader: drops the line as `too_complex` before parsing it; commas inside strings count too, so it refuses only far past `MAX_EVENT_NODES` |

The first three bounds are P1 Assumption 12 (inbox #28). The reader's bounds after them were set in the P3 Task 3 review ([record](../reviews/code/P3-t03.md)) *(assumed — pending Thomas, [inbox #76](../reviews/inbox.md#76-assumed-the-spool-readers-bounds-and-private-directories))*. `MAX_SPOOL_FILES`, `MAX_EVENT_NODES` and `MAX_EVENT_DEPTH` are in `spectio_sdk.events`; the others are in `spectio.runner.spool`.

**The Nextflow writer.** *Written 2026-10-30, from the code and review of P1 Task 6 ([record](../reviews/code/P3-t06.md)); the writer is `SpoolWriter` in `engine-bridges/nf-spectio/src/spectio/SpectioPlugin.groovy`, its tests `packages/spectio/tests/test_bridge_nextflow.py` (marked `engines`).* How it fails and stops is architecture §13.3.

- **Silent unless driven.** With none of the three variables set, `nf-spectio` does nothing. With one missing or invalid (`SPECTIO_RUN_ID` not `run_` and a ULID, `SPECTIO_LAUNCH_N` not 1 to 19 digits with no leading zero, `SPECTIO_SPOOL_DIR` empty), it prints one line on stderr, writes nothing, and the run goes on.
- **New files only.** It creates `events` 0700 and each spool file with an exclusive create at 0600, at the next index whose name does not exist yet; it never appends to a file another writer made. Every open refuses a symbolic link. After index 9999 it writes nothing more.
- **Lines.** `seq` runs from 1 without gaps within the launch. A line over `MAX_LINE_BYTES` is not written, and `bridge.err` says so.
- **A failed write does not rotate.** The file is truncated back to its last full line, so no partial line stays behind and the size count stays exact; the writer keeps the file and moves to a new one only when that file is gone or the next line passes `ROTATE_BYTES`. A quota or a full disk therefore costs no spool files; under a per-file limit (EFBIG), the events after it are lost for the rest of the launch *(assumed — P3 Task 6, pending Thomas, [inbox #82](../reviews/inbox.md#82-assumed-what-nf-spectio-sends-how-it-fails-and-its-nextflow-range) rule 2)*.
- **Not yet confined.** The 0.0.1 writer follows a symbolic link in the path to `events`, checks no owner or mode of `.spectio` or `events`, and opens by path. That is safe in a driven run's 0700 run directory ([dev-env §15.3](dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts) req. 5), not in a group-writable launch directory: req. 12's descriptor-relative writes come with P1 Task 25, before runs started from a terminal (SEC-P3T06-03).

**The Snakemake writer.** *Written 2026-11-01, from the code and review of P1 Task 7 ([record](../reviews/code/P3-t7.md)) (assumed — pending Thomas, [inbox #97](../reviews/inbox.md#97-assumed-what-the-snakemake-logger-plugin-sends-how-it-fails-and-its-interface-range-p3-task-7) rules 2 and 3). The writer is `Spool` in `engine-bridges/snakemake-logger-plugin-spectio/snakemake_logger_plugin_spectio/__init__.py`; its tests are that project's `tests/test_plugin.py`.* How it fails is covered in architecture §13.3.

- **Silent unless driven.** The rules are the Nextflow writer's: with none of the three variables set, nothing happens. With one missing or invalid (`SPECTIO_SPOOL_DIR` must be absolute), the plugin prints one stderr line and writes nothing.
- **Confined `events`.** It creates `events` at 0700. It opens it with `O_DIRECTORY|O_NOFOLLOW` and refuses it unless the directory belongs to the user with no group or other bits. A refused directory writes no event of the launch, and `bridge.err` says why. Each spool file is created relative to that descriptor: an exclusive create at 0600 with `O_NOFOLLOW`, at the next index whose name does not exist yet.
- **A failed create keeps its index.** Only success or an existing name moves the index on, so `EACCES` or `EDQUOT` cost the event, not an index (CR-P3T7-01). After index 9999 it writes nothing more.
- **Lines.** It makes one `write(2)` per line on an `O_APPEND` descriptor. `seq` runs from 1 without gaps. The next file is opened before a line would take the current one past `ROTATE_BYTES`. When a line passes `MAX_LINE_BYTES`, a `job_info` or `job_error` is sent again with `input` and `output` emptied. Otherwise the line is dropped and `bridge.err` says so.
- **A failed write does not rotate.** The file is cut back to its last full line, as for the Nextflow writer.
- **Values are bounded before the line is built.** A string is cut at 4096 characters, a list or a map at 512 items. A value nested deeper than 8 levels becomes its text. These bounds are the plugin's own and are new numbers *(assumed — inbox #97 rule 2)*.
- **Allow-listed at the source.** Each type's builder reads only the keys of the table below. `slurm_extra` is dropped from `resources`, and `reason` is cut after the `Params have changed` label, before the line is written. The server applies both again when it parses the line. An event that lacks a key its model requires (`job_info`'s `jobid` or `rule_name`, `job_finished`'s `job_id`, `job_error`'s `jobid`, `progress`'s `done` or `total`) is sent as `snakemake.log` with its level only.
- **`bridge.err`** is opened by path, with `O_NOFOLLOW` and `O_NONBLOCK`. It is written only when it is a regular file, at most 100 lines; otherwise the line goes to stderr. Its owner and mode are not checked, so a file that already exists keeps its mode (SEC-P3T7-01, inbox #97 rule 3).

**Envelope.** Every line is an object with exactly these keys; any other key makes the line invalid. Unknown keys *inside* `data` are ignored instead (allow-lists, below), so a newer bridge still parses.

The other executor plugins pinned in `dev/snakemake.lock.txt` (`slurm-jobstep` 0.6.1, `kubernetes` 0.5.1) read named resource keys only and pass no raw flags: `slurm-jobstep` reads `mpi`, `cpus_per_task`, `cpus_per_gpu`, a GPU count and a node count ([`__init__.py:144`](https://github.com/snakemake/snakemake-executor-plugin-slurm-jobstep/blob/v0.6.1/snakemake_executor_plugin_slurm_jobstep/__init__.py#L144), [`:275-346`](https://github.com/snakemake/snakemake-executor-plugin-slurm-jobstep/blob/v0.6.1/snakemake_executor_plugin_slurm_jobstep/__init__.py#L275-L346), tag `v0.6.1`, commit `c09349d`); `kubernetes` reads `machine_type`, `gpu`, `gpu_manufacturer`, `scale`, `_cores`, `mem_mb` and `disk_mb` ([`__init__.py:167-218`](https://github.com/snakemake/snakemake-executor-plugin-kubernetes/blob/v0.5.1/snakemake_executor_plugin_kubernetes/__init__.py#L167-L218), [`:318-371`](https://github.com/snakemake/snakemake-executor-plugin-kubernetes/blob/v0.5.1/snakemake_executor_plugin_kubernetes/__init__.py#L318-L371), tag `v0.5.1`, commit `d5f720e`); both read 2026-10-30, after `security-reviewer`'s reading in P3 Task 5's review; whether later plugins pass raw flags under other `*_extra` key names is **[to be validated]**, and no test would catch a new one. Other Snakemake events (group jobs, for example) are not in the list, so they are dropped as unknown; whether 0.0.1's runs emit any is **[to be validated]**.

**Dropped and counted, never executed.** Each line is untrusted input (dev-env §15.3 req. 6). The reader validates the envelope, then the type's allow-list. A line or a file that fails a check is dropped and counted by reason, and the next one is read. The counters are stored with the reader's cursor (P1 Assumption 11). Nothing in an event is executed or evaluated; paths in events are untrusted and are used only as names confined under a run root ([dev-env §15.3](dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts) req. 13). *Reader rules below written 2026-10-30, from the code and review of P1 Task 3 (CR-P3T3-05, SEC-P3T3-07); the reader is `spectio.runner.spool.read_spool`, its tests `packages/spectio/tests/test_spool_reader.py`.*

- **Confinement.** The caller checks the launch directory and the path to it (req. 10): the runner loop (P1 Task 9) and the boot rebuild (P1 Task 11). The reader opens `<launch dir>/.spectio`, then `events` relative to it, each with `O_DIRECTORY|O_NOFOLLOW`, and checks each with `fstat`: owned by the user, no group or other bits, as req. 10 checks a run directory. Whoever creates them must therefore create them at 0700; otherwise every read raises `PermissionError`. Each spool file is opened by name relative to the `events` descriptor, never by path: `lstat` first (a symlink or a FIFO is never opened), then `O_RDONLY|O_NOFOLLOW|O_NONBLOCK`, then `fstat` again. It must be a regular file of the user, not writable by group or others. A directory or file swapped for a symlink after a check is never followed.
- **Which files.** Only names of the grammar above, for the launch being read. Another launch's files are ignored and not counted. At most `MAX_SPOOL_FILES` files and `MAX_DIR_ENTRIES` directory entries are taken, in name order. A file already in the cursor is read even when a cut listing misses it.
- **Each read** returns at most `max_lines` lines and takes at most `max_bytes` bytes. One read is cheap even on hostile files: the security reviewer measured a worst read of 0.86 s and a traced peak of 11.1 MiB, against 788 MiB for 500 lines before the byte budget ([record](../reviews/code/P3-t03.md)).

| Reason | Counted | When |
|---|---|---|
| `invalid` | per line | not JSON, the envelope fails, the type is unknown, or `data` fails its allow-list model |
| `too_complex` | per line | `data` holds more than `MAX_EVENT_NODES` values or is deeper than `MAX_EVENT_DEPTH`, or the line passes the pre-parse bound |
| `line_too_large` | per line | longer than `MAX_LINE_BYTES`; an unended line is counted once, as soon as it passes the cap, and reading goes on after its `\n` |
| `wrong_run` | per line | `run` is not the run being read |
| `wrong_launch` | per line | `launch` is not the launch being read |
| `file_too_large` | once per file | the file passes `MAX_FILE_BYTES`; counted after the lines before the cap are read |
| `symlink` | once per file | the spool file is a symbolic link, also one swapped in after the `lstat` |
| `not_regular` | once per file | a directory, FIFO, socket or device |
| `foreign_owner` | once per file | owned by another user |
| `writable_by_others` | once per file | writable by group or others |
| `unreadable` | once per file | an operation on the file (lstat, open, fstat, read) fails with `EACCES` or `ENXIO` |
| `bad_name` | once per name | a name in `events/` outside the grammar, up to `MAX_BAD_NAMES` |
| `too_many_files` | by its high-water mark | names past `MAX_SPOOL_FILES` or `MAX_BAD_NAMES`, or a listing cut at `MAX_DIR_ENTRIES`; only an increase over the most seen is counted |
| `bad_cursor` | once per cursor entry | a cursor key that is neither a `#` key nor a spool file name of this launch (dropped), or a value out of range (reset: the file is refused, a count set to 0) |
| `read_error` | on each read | any other `OSError` on a file; the file is retried by the next read |
| `spool_refused` | on each read | `.spectio` or `events` is refused or cannot be opened, read through `try_read_spool`, which returns an empty batch with the cursor unchanged instead of raising; the next read tries again *(assumed — P3 Task 4; counting every read is open, CR-P3T04-05, for P1 Task 9)* |
| `projection_error` | per event | counted by `ingest`, not the reader: the event passed the checks above, but projecting it raised. Its log row and projection are rolled back, the error is logged with its traceback, and the next event is projected. A database `OperationalError` is not counted: the whole batch rolls back and the cursor stays *(assumed — P3 Task 4, pending Thomas, [inbox #78](../reviews/inbox.md#78-assumed-the-projectors-rules-and-a-fifth-review-round))* |
| `path_outside_run` | per path | counted by `ingest`: a work directory (Nextflow) or a log path (Snakemake) that does not resolve under a root of the run (§15.3 req. 13); the path is not stored, the rest of the event is *(assumed — P1 Task 28, pending Thomas, [inbox #94](../reviews/inbox.md#94-assumed-each-jobs-files-as-built-p3-task-28))* |
| `bad_native_id` | per event | counted by `ingest`: an executor job ID that is not one (`[A-Za-z0-9][A-Za-z0-9_.:@-]{0,127}`); it is not stored *(assumed — P1 Task 28, pending Thomas, [inbox #94](../reviews/inbox.md#94-assumed-each-jobs-files-as-built-p3-task-28))* |

Not counted: a file gone since the listing (skipped), and another launch's file. `read_spool` stops and raises instead in three cases (its caller uses `try_read_spool`, which counts the first two as `spool_refused`): `PermissionError` when `.spectio` or `events` is not a private directory of the user; `OSError` when either is a symlink or not a directory; `ValueError` when `max_lines` is under 1 or `max_bytes` cannot hold one line. When `.spectio` or `events` is missing, the read returns an empty batch: nothing is written yet.

**The cursor.** A read returns `SpoolBatch(events, cursor, drops)`; the caller stores the three in one transaction. The cursor maps each spool file name to the bytes read from it (0 to `MAX_FILE_BYTES`), or to `REFUSED` (−1): the file is never read again and its drop is already counted, which is how a file-level drop is counted once. Keys that start with `#` are the reader's own:

- `#` and the first 16 hex characters of the SHA-256 of a name outside the grammar, mapped to `REFUSED`; the name itself is never stored;
- `#excess`, the most names found with no slot, already counted as `too_many_files`.

The cursor that comes in is checked first, and anything the reader would not write is counted `bad_cursor`.

**What a user sees.** A Snakemake event with more than about 4096 values in its `data` is dropped as `too_complex`: for example the `snakemake.rulegraph` of a very large workflow, or the `snakemake.job_info` of a gather rule with thousands of inputs. The run then lacks that event, and its drop count shows it. Whether real large workflows reach this cap is **[to be validated against real large workflows]**.
