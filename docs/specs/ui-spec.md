# Spectio — UI and information architecture spec

Status: draft v0.2 · 2026-10-25 · author: Thomas Weber (with Claude)
Scope: web UI of Spectio (formerly drafted as Ductio / Perspectio). Companion docs: [`synthesis.md`](synthesis.md) (architecture), [`decisions/log.md`](../decisions/log.md) (decisions log), `spectio-tokens.css` (design tokens).

## 1. Principles

1. **Same family as depictio.** Reuse depictio's app shell, theme mechanics, components and list patterns (table / rows toggle) *(assumed — pending Thomas, inbox #29)*. Spectio differs in brand colours (Dawn palette) and emblem, not in interaction model. See §9.
2. **No terminal for end users.** Everything an end user does — register a workflow, launch, monitor, review, relaunch, debug — is possible from the browser. The CLI remains for experts and automation.
3. **State is explicit.** A run's state is always shown as icon + word + context ("Awaiting review · stage 2 of 4 · 12 min"), never as a colour alone. The same holds for every other state: check verdicts, runners, health (§3.3).
4. **Humans, AI agents and systems are first-class actors.** Every decision shows who made it (person, AI agent with model/version, or external system).
6. **Words.** The Spectio process installed on a compute environment is a **runner** (like a self-hosted CI runner). **Agent** always means an AI agent. A **stage** is a named group of processes or rules; a **gate** is a stop point at the end of a stage.
5. **Engine-agnostic surface, engine-aware details.** Lists look the same for Nextflow and Snakemake; detail panels expose engine specifics (nf-core schema, Snakemake checkpoints, etc.).

## 3. Status system

### 3.1 Run states

| Value | State | Icon | Colour | Meaning |
|---|---|---|---|---|
| `queued` | Queued | clock | ink 400 | Accepted, waiting for a runner or the scheduler |
| `running` | Running | play (animated ring) | blue `#3B82F6` | Engine running |
| `awaiting_review` | Awaiting review | hand / flag | amber `#D9890B` | Stopped at a gate; a decision is required |
| `pausing` | Pausing | pause, animated ring | violet `#8B5CF6` | Stopping as requested; becomes Paused |
| `paused` | Paused | pause | violet `#8B5CF6` | Stopped on request, resumable |
| `succeeded` | Succeeded | check | green `#1F9D63` | Completed |
| `failed` | Failed | cross | red `#DC3B3B` | Engine or task failure; Resume creates a new run *(assumed — pending Thomas, inbox #32)*. With failure class `head_lost`: "Engine stopped while Spectio was down · Resume" *(assumed — pending Thomas, inbox #40)* |
| `cancelling` | Cancelling | slash, animated ring | ink 500 | Cancel requested; the head process is stopping |
| `cancelled` | Cancelled | slash | ink 500 | Stopped by a user or a policy |

The values are the run-state enum of [`api-and-data-model.md`](api-and-data-model.md) §7.1, which owns them and their WES mapping. A gate `stop` shows as Cancelled. Head silent and Runner offline are flags shown next to the state, not states ([`api-and-data-model.md`](api-and-data-model.md) §7.1). *(assumed — pending Thomas, inbox #29)*

Rendering rules (replaces the current pill badges):
- In tables: a 4 px **state rail** on the left edge of the row, plus icon + state word in the State column, plus a context line ("stage 2 of 4 · 12 min ago").
- In cards: the state rail runs along the top edge of the card; icon + word in the header.
- Hover / focus on any state shows a tooltip with the last event and timestamp.
- Task labels come from the states of [`api-and-data-model.md`](api-and-data-model.md) §7.2: pending, submitted, running, succeeded, failed, cached, stored, aborted, not scheduled; "Aborted" is an attempt the engine stopped, or never ran, because of another failure: it is not shown as a failure and does not count in the failed total *(assumed — pending Thomas, inbox #56)*; "failed (ignored)" is `failed` with `ignored`; "retried" is shown on a task whose last attempt has n > 1. Cached and Stored are distinct looks, for `cached` and `stored`.

### 3.2 Stage gauge (the emblem as a progress indicator)

The emblem's half-disc is reused as a compact **stage gauge**: one sector per declared or detected stage (1 to 8, §5.1). Workflows without stages get 4 sectors = quarters of task progress, measured against `tasks_expected` when `tasks_expected_source` is `engine_plan` and against the known tasks otherwise ([`api-and-data-model.md`](api-and-data-model.md) §7 `runs`). *(assumed — pending Thomas, inbox #38)*

| Sector look | Meaning | `run_stages.state` |
|---|---|---|
| Solid brand colour (indigo → violet → coral → amber, in order) | Stage completed | `completed` |
| Brand colour, light tint (300) | Stage running | `running` |
| Amber outline + notch | Stage finished, gate awaiting review | `awaiting_review` |
| Solid red | Stage failed | `failed` |
| Grey hatched (ink 200) | Stage skipped / fully cached | `skipped` |
| Light grey (ink 100) | Stage not started | `not_started` |

Each look maps to one value of the stage-state enum ([`api-and-data-model.md`](api-and-data-model.md) §7 `run_stages`). *(assumed — pending Thomas, inbox #40)*

A legend is available from any gauge (hover / tap) and in Help. In the relaunch stage strip, stages reused from cache use animated hatching.

### 3.3 System states

States outside runs (runners, observers, model endpoints, storage, tasks, health checks, plugins) reuse the run-state tokens of §3.1. No family gets its own palette, red stays for hard failures, and every state shows icon + word.

| Run-state token | System states mapped to it |
|---|---|
| `running` | active, in progress, retrying |
| `succeeded` | healthy, online, verified |
| `review` | notice, draining, degraded, pending verification |
| `failed` | offline, failed to load, dead |
| `cancelled` | disabled |

The Legend also shows: scheduler job states and failure classes in Spectio words (red only for failures; a finished job reads Succeeded, not "Completed"); check verdicts (pass / warn / fail); pre-start states (Starts now, Waits for a slot, Queued · quota) with the clock icon, never the Running play icon; origin and level chips (UI / API / CLI / Batch; Observed / Adopted, §6). State words are exactly those of §3.1 ("Awaiting review", "Succeeded") and of its task-state list ("pending").

Check verdicts have distinct icons: check for pass, triangle for warn, octagon-x for fail. Text always says the severity ("6 / 8 pass · 1 warning · 1 failing"; in a value column "fail · 3 outliers"), never only a colour (WCAG 2.1 SC 1.4.1, https://www.w3.org/TR/WCAG21/#use-of-color).

### 3.4 Colour use and contrast

Text reaches 4.5:1 against its background (WCAG 2.1 SC 1.4.3, https://www.w3.org/TR/WCAG21/#contrast-minimum); switch tracks, icons and other non-text controls reach 3:1 (SC 1.4.11, https://www.w3.org/TR/WCAG21/#non-text-contrast). Primary buttons use `--sp-accent` (`#7750D4`, 5.41:1 with white). Section colours are for tints and icons only, never button fills. An amber fill (the Review badge, a warning action) uses `--sp-state-review-fg` (`#8F5806`, 5.89:1); otherwise run-state colours stay out of the brand. Switch tracks use `--sp-ink-400`. Helper text uses `--sp-text-faint` or `--sp-ink-500`; on the `#F7F7FB` surface use `--sp-ink-500`, since `#6E7287` gives 4.45:1 there. Adjacent segments of a bar are separated by a 1 px divider. Ratios as recomputed in review R7 with the WCAG 2.x formula.

### 4.4 Run detail
Header: run name, state line, gauge, actions by state (table below). When the runner is offline or live data is stale, the header shows that state and its actions follow §11 (for example "Queue pause · applies on reconnect"). The short run id shown is the last 6 characters of the ULID; `created_by` resolves through `GET /me` and user reads.

| State | Header actions |
|---|---|
| Queued | Cancel · Copy to a new launch |
| Running | Cancel (Pause after stage is shown only once `:pause` exists, inbox #16) |
| Awaiting review | Review (opens the gate) · Relaunch… · Cancel |
| Paused | Continue · Relaunch… · Cancel |
| Failed | Resume as new run · Relaunch… |
| Succeeded | Relaunch… |
| Cancelled | Relaunch… |
| Observed (CLI) | None besides Copy to a new launch, with the adopt banner of §6 (no relaunch); an Adopted run follows its state's row |

Copy to a new launch is under More in every state. Pause and an immediate stop follow the open question of inbox #16 (SR-018).

Relaunch… at a gate records the decision `stop` with reason `relaunched` (the run becomes `cancelled`, `cancel_reason = relaunched`), then calls `POST /runs/{id}:relaunch` with mode `rerun_from` (the gated stage by default) and the parameter overrides from the dialog (§4.6); see [`api-and-data-model.md`](api-and-data-model.md) §5 and §7. Resume on a failed run creates a child run; the failed run stays terminal. *(assumed — pending Thomas, inbox #32)*

The Failed header shows `runs.failure.message` and its class, and links to the failing task (`runs.failure.task_id`, [`api-and-data-model.md`](api-and-data-model.md) §7). *(assumed — pending Thomas, inbox #40)*

Tabs:
1. **Summary** — stages timeline, key numbers, last events.

*Note 2026-10-28 (0.0.1 stages and processes):* this note owns how the 0.0.1 run detail shows stages (Thomas, 2026-10-28: "les 2 dans 0.0.1", both; [decision log](../decisions/log.md#2026-10-28-001-has-four-screens-home-kept)); the plan, the API note and the boards link here.
- **What it shows.** The stages of `GET /runs/{id}/stages` in position order, each with its state word and icon, "n of m tasks", a source badge, Declared or Detected (display only), opening to its processes (Nextflow) or rules (Snakemake) in first-seen order; the processes that belong to no stage are under "Not in a stage". The header of a run with stages reads "n of m stages done · k running" ("3 of 8 stages done · 4 running"). With no stage, the run detail shows the flat processes or rules list and the line "No stages for this pipeline: processes as the engine reports them." Where stages come from, which process falls in no stage, and the stored stage state: §5.1 and §5.1.1; this note owns only how they are shown.
- **State word.** A stage shows the word of its `run_stages.state` (§5.1.1, "Order and state"), by the mapping below. A process or rule has no stored state; its word comes from its task counts (Pending includes Submitted): **Pending** while no task has started (succeeded + cached + running + failed = 0); **Running** once a task has started and not every known task has finished; **Done** when every known task succeeded or was cached; **Failed** when a task failed on its last attempt. A stage is Done only when every one of its processes or rules is Done. On an ended run: **Stopped** for a stage, process or rule that had started and not finished when the run ended, whether by Cancel or because the engine stopped after another stage failed; it is not a failure of its own, so a failed run shows Failed only where a task failed on its last attempt (UX-320). **Not run** for one that never started.
- **Words for `run_stages.state`** ([`api-and-data-model.md`](api-and-data-model.md) §7): `not_started` → Pending, `running` → Running, `completed` → Done, `failed` → Failed when one of the stage's own tasks failed on its last attempt, otherwise Stopped (neither §7 nor §5.1.1 has a state for an interrupted stage), `skipped` → Not run. `awaiting_review` is not shown in 0.0.1, which has no gates.
- **Process identity.** A Nextflow process is keyed by its fully qualified name, the name `nf-spectio` reports and the trace's `process` field (`NFCORE_RNASEQ:RNASEQ:QUANTIFY_PSEUDO_ALIGNMENT:SALMON_QUANT`; source in §5.1.1); a Snakemake rule by its name. `/processes` items use that key, and their `stage_id` ties them to `/stages`. The UI shows the last segment, with the full name as the accessible name; when two processes of one stage share a last segment, each shows the shortest part of its parent scope that tells them apart ("UCSC_BEDCLIP · forward" for `…BEDGRAPH_BEDCLIP_BEDGRAPHTOBIGWIG_FORWARD:UCSC_BEDCLIP`). Every process of a stage is listed, also one with no task yet, which reads "0 tasks yet"; the process filter of the Tasks table lists the items of `/processes`, with their count.
- **Open sections** (UX-318). Every titled section is a heading with a toggle button (`aria-expanded`, `aria-controls`); stage rows open with `<details>`. Open by default: Stages, the running stage, Why it failed, and every launch group with a required, changed or invalid field. On a refused submit, the group of the first invalid field opens and focus moves to that field. Which sections are open is remembered per screen in the browser's storage, a convenience only.

### 4.5 Review
**Review views.** Every gate is items × checks × evidence × decisions ([`checking-scenarios.md`](checking-scenarios.md)). The detail page opens on Summary, then the view that fits the item kind and scale: **item table** (a few items: samples, MS runs, predictions, grouped samples), **distributions & thresholds** (massive: cells, spots, features), **spatial grid** (wells, slides, tiles), **candidate list** (many: bins, candidate variants, structures), **report reader** (MultiQC and any HTML report, sandboxed). Examples on the canvas: Review (plate, spatial grid), ReviewCoverage (grouped samples), ReviewReport (item table + report reader), ReviewCells (distributions), ReviewCandidates (MAG bins).

### 5.1 Stages, gates and `spectio.yml`
Where stages come from, in order, per run: (1) declared in `spectio.yml`, in the workflow repository or attached in Spectio as a **lab overlay** for a pipeline you do not own (nf-core/rnaseq declares none; the rnaseq stages in the mockups come from such an overlay); (2) detected from structure, display only, no gates: Nextflow subworkflows below the pipeline's wrapper scopes, read from the fully qualified process names (`NFCORE_RNASEQ:RNASEQ:ALIGN_STAR:STAR_ALIGN` → "Align star"), and Snakemake rule files included by the main Snakefile; rules in §5.1.1; (3) none: the gauge shows task quarters; resume and restart still work, rerun-from-stage does not.

*Note 2026-10-28 (Thomas, [decision log](../decisions/log.md#2026-10-28-001-shows-stages-declared-or-detected-and-the-processes-or-rules-list)):* the run detail shows both the stages and the processes (Nextflow) or rules (Snakemake). Each process or rule takes the stage whose `match` matches it (`tasks.stage_id`, [`api-and-data-model.md`](api-and-data-model.md) §7); names with `tasks.stage_id` null form an unassigned group. How stages, the list and that group are shown is owned by §4.4. 0.0.1 has sources (1), as files, and (2), display only; the [stage-detection spike](../research/spike-stage-detection-2026-10-28.md) replaced "top-level subworkflows" and "module prefixes and checkpoints" with the rules of §5.1.1.

The `spectio.yml` keys (`workflow`, `stages`, `gates`, `reports`, `launch`, `ui`, `depictio`) are specified in [`checking-scenarios.md`](checking-scenarios.md) §12. *(assumed — pending Thomas, inbox #29)*

How a gate stops the engine without forking:
- Nextflow — a generated config sets `ext.when = false` on the processes of later stages (nf-core modules declare `when: task.ext.when == null || task.ext.when`: nf-core/tools `0af7543`, `nf_core/module-template/main.nf:75-76`; local processes without it are not stopped **[to be validated]** in spike T2), so the run ends after the gated stage; Continue relaunches with `-resume` and without the override. This is proven only on synthetic pipelines so far ([spike note](../research/spike-synthetic-pipelines-2026-10-26.md), finding 7); real pipelines are checked on nf-core/rnaseq and sarek ([`dev-environment-and-testing.md`](dev-environment-and-testing.md) §3). **Pipeline requirements** for a Nextflow gate: every process of a later stage honours `ext.when` (nf-core modules do; local or non-nf-core processes need a `when:` that reads it); no downstream `collect`, `join`, `ifEmpty` or `mix` fails or keeps the run going when the skipped processes emit nothing; completion hooks and summaries tolerate the missing outputs. When the requirements check fails, the launch form shows "gates unavailable" with the reason. *(assumed — pending Thomas, inbox #28)*
- Snakemake — `--until` the last rules of the stage; Continue drops `--until`; rerun from a stage uses `--forcerun`.

The mechanism is owned by [`checking-scenarios.md`](checking-scenarios.md) §12.

### 5.1.1 Detected stages

Added 2026-10-28 from the [stage-detection spike](../research/spike-stage-detection-2026-10-28.md) ([decision log](../decisions/log.md#2026-10-28-001-shows-stages-declared-or-detected-and-the-processes-or-rules-list)). A detected stage is for display only: it has no gate, no `ext.when` or `--until` override and no rerun from a stage. Its name is the technical name, humanised; a lab overlay is the way to good names, and the only way to split a subworkflow into two stages. *(assumed — pending Thomas, inbox #68)*

**Where detection runs.** On the server, from what the bridges already send, so a run Spectio launched and a run started from a terminal (§6) get the same stages:
- **Nextflow.** `nf-spectio` sends one `onProcessCreate` per process with its fully qualified name, in script order, all before `onFlowBegin` and before the first task (Nextflow 26.10.4: the name is built in `BindableDef.groovy:41-49`; the hooks in `TraceObserverV2.groovy:62`; the order also checked on 25.10.9 by the note's fact-check; [spike note](../research/spike-stage-detection-2026-10-28.md#nextflow-where-the-stage-information-is)). The server detects once, on that list, at the run's first `onFlowBegin`. A process left out by a Groovy `if` is never created and is absent; a process turned off by `when:` or `ext.when` is created, gets no task, and its stage can end `skipped`.
- **Snakemake.** The logger gets a rule name per job (`job_info`), never the rule's file (Snakemake 9.27.1, `jobs.py:1072-1075`). The server reads the rule files from the main Snakefile named in `workflow_started` (`snakefile_main`, `workflow.py:289-305`), as the user who owns the run. For a run it launches, Spectio also runs `snakemake --list-rules` with the run's configuration and drops the rules that configuration does not define (conditional `include:`s). Checkpoints hide most of the DAG at start; they do not mark stages.

**Nextflow rules.**
1. **Wrapper scopes.** Skip the leading scopes that every process shares (`NFCORE_RNASEQ`), then the pipeline scope: the scope named after `manifest.name` (`nf-core/rnaseq` → `RNASEQ`), or, with no manifest name, the child scope that holds more than half of the processes. The children of these scopes are the candidates.
2. **Groups.** Each child subworkflow is a group. Processes called directly form one group per run of consecutive direct calls in the same parent scope.
3. **Aliases.** Neighbouring subworkflows whose names differ only in their last word (`…_FORWARD`, `…_REVERSE`) merge.
4. **Lone processes.** A group of one direct process joins its neighbour in the same parent scope, the previous one, else the next; `MULTIQC` stays its own stage, named "Report".
5. **Cap.** While there are more than 8 groups (the gauge holds 1 to 8 sectors, §3.2), merge the neighbouring pair with the fewest processes, inside one parent scope while such a pair exists, never the Report.
6. **Names.** The subworkflow names humanised (`PREPARE_GENOME` → "Prepare genome"), joined with " + " when merged; a group of direct process calls is named after its processes, humanised and joined with ", " ("Cat fastq, Fastqc, Trimgalore"); the subworkflow's `meta.yml` `description`, when present, is the stage description.
7. **None.** No subworkflow at all, or fewer than 2 groups: no detected stages, and the run shows its processes only.

**Snakemake rules.**
1. **Groups.** Follow every `include:` with a literal path from the main Snakefile, in source order, depth first. Each rule file that defines rules is a group; the files under one sub-directory of `rules/` are one group.
2. **Final targets.** The main Snakefile's own rules (usually `all`) are the last group, "Final targets".
3. **Cap and names.** At most 8 groups, merged as for Nextflow, never Final targets; names are the file or directory stems humanised.
4. **None.** A single rule file: no detected stages. Rules found in no file (a computed `include:` path, a `module`) are in no stage (`tasks.stage_id` null).

**Order and state.** Stages keep the detection order: creation order (the source order) for Nextflow; for Snakemake, the topological order of the start rule graph for the rules it holds, then include order. A stage is `running` from its first task, `completed` when all its processes have ended (`onProcessTerminate`) or its rules have no job left, `failed` when the run fails on one of its tasks, and `skipped` when it ended with no task. A Snakemake stage behind a checkpoint stays `not_started` until its first job.

**Examples** (spike, pinned versions; fixtures in `tests/pipelines/real/stages/`): nf-core/rnaseq 3.27.0, 67 processes → 8 stages; nf-core/sarek 3.11.0, 48 → 8; nf-core/methylseq 4.2.0, 13 → 4; mosaicatcher-pipeline v2.5.1, 101 rules → 8; the synthetic pipelines of [dev-env §10.1](dev-environment-and-testing.md) → none. The four example lab overlays in the same folder are the 0.0.1 documentation of declared stages.

*Note 2026-10-31, 0.0.1 as built ([P3 Task 27](../progress/W5/P3-M7.md), `spectio_server/stages/`, `spectio/runner/headscript.py`; assumed — pending Thomas, [inbox #93](../reviews/inbox.md#93-assumed-the-001-stages-as-built-p3-task-27)):* the rules above are built, with these differences and details. Which source applies, and the overlay rules, are in the [checking-scenarios §12.7 note](checking-scenarios.md#127-overlays) of the same date.
- **Snakemake order is include order.** Stages follow the rule files in include order (depth first, a file before the files it includes), the main Snakefile's rules last as "Final targets"; the topological order of the start rule graph is not used in 0.0.1 (CR-P3T27-07).
- **The listing.** For a Snakemake run it launches, the head runs `snakemake --snakefile … --directory … --configfile .spectio/params.json <extra arguments> --list-rules` under `timeout --foreground 120`, into `.spectio/rules.txt` (mode 0600), before the engine. Its stderr is dropped. If it fails or takes longer, there is no file, one line on the head's stderr, and the engine starts; the server then takes every rule it reads in the rule files. A Cancel during the listing ends the head with exit 143 before the engine starts. Each line of `rules.txt` that is a rule name, alone or followed by ` (docstring)`, is a rule.
- **What the server reads.** Rule files: regular files under the main Snakefile's directory once symlinks are resolved, at most 200 of 1 MiB; a FIFO or a device is refused without blocking; a `snakefile_main` from `workflow_started` outside the run's pipeline directory gives no detected stages. Nextflow `meta.yml`: `subworkflows/nf-core/<scope>/meta.yml`, then `subworkflows/local/<scope>/meta.yml`, for at most 200 scopes, at most 64 KiB, its `description` with whitespace collapsed, at most 2,000 characters.
- **The processes or rules list.** Its order is the order the server first saw each name: Nextflow's `onProcessCreate`; for Snakemake, at the freeze, the rules of the detected stages, then those of `rules.txt` (or of the rule files), each once; then any name first seen on a task. A name first seen after the freeze has no stage (`stage_id` null).
- **State.** As above, with: a Snakemake stage has ended when it has at least one task and each of its rules has as many jobs done (`succeeded`, `cached`, `stored`) as Snakemake's last `run_info` planned; a stage that had ended goes back to `running` when more jobs come past a checkpoint. On a run that ended, a stage with no started task is `skipped`; one under way when the run stopped is `failed` (shown Stopped, [§4.4](#44-run-detail)). A stage's `started_at` and `ended_at` take the time of the last event of the batch that moved it (CR-P3T27-11, open).

### 5.2 Checkpoints, conditional execution and temporary outputs

Added 2026-11-07 (Thomas, 2026-11-07, "prends en considération checkpoints rule & execution conditionnelle dans snake & nf ; temp files également", [decision log](../decisions/log.md#2026-11-07-checkpoints-conditional-and-skipped-jobs-temp-outputs-and-slurm-efficiency-per-job-and-per-rule-thomas)). What each engine gives is in the [research note](../research/dag-temp-slurm-efficiency-2026-11-07.md) §2 to §5; the events in [`api-and-data-model.md`](api-and-data-model.md) §14.1 (note of the same date); the plan in [P1 Tasks 33 to 35](../plans/P1-walking-skeleton.md#m9-dag-temp-outputs-and-efficiency). How the processes or rules list and the job files drawer look stays owned by §4.4; this section owns what the engine-specific states mean.

*Note 2026-11-07:* this section replaces the two bullets at the top of §5 where they differ: Nextflow tasks filtered by `when:` are never reported to observers (Nextflow 26.10.4, `TaskProcessor.groovy:1986-1997`), so Spectio cannot show them as "not scheduled"; and Snakemake temporary files are known only when they are removed (rule 6).

**Process and rule states.** Each process (Nextflow) or rule (Snakemake) of the list has a status computed by the server (`/processes` `status`), distinct from **Pending**, which means "jobs are planned and none has started":
1. **Waiting for a checkpoint** (`awaiting_checkpoint`, Snakemake). A defined rule with no planned job while a checkpoint of the run has not finished: its jobs may appear when the DAG is updated. Shown "Waiting for checkpoint <rule>", with the checkpoint's name when there is one open.
2. **Not needed** (`not_needed`, Snakemake). A defined rule (from `.spectio/rules.txt` or the rule files, §5.1.1) that is in neither the rule graph, nor `run_info`, nor any `job_info`, with no checkpoint open: the targets, an input function or `branch()` left it out. Shown "Not needed in this run", greyed but listed, after the others.
3. **Up to date** (`up_to_date`, Snakemake). In the rule graph, with no job to run (absent from `run_info`): its outputs already exist. Shown "Up to date".
4. **No task** (`no_tasks`, Nextflow). `onProcessTerminate` came with no task between it and `onProcessCreate`: `when:` was false for every input, `ext.when` (a gate, §5.1) or `process.when` turned it off, or its input channel was empty. Shown "No task (condition or empty input)". Spectio cannot say which: Nextflow sends no event for a filtered task. Under a gate, the gate's own words win ("Skipped by the gate").
5. **Absent** (Nextflow). A process left out by a Groovy `if` is never created and is not listed. The list's foot says "Processes the script does not call in this run are not listed." A static read of the script is later.

The stage states of §5.1.1 do not change: `not_started`, `running`, `completed`, `skipped`, `failed`.

**Checkpoints.**
- A rule is a checkpoint from its first `job_info` with `is_checkpoint` true, or earlier from a `checkpoint <name>:` line of the rule files the server already reads (§5.1.1). Its row shows a text chip "Checkpoint".
- While a checkpoint job is planned or running, the run header's task count reads "at least <n> jobs" and the progress bar is hatched past the known part, never animated; the Summary adds "The DAG grows after checkpoint <rule>: more jobs may come." When the checkpoint ends and the DAG is updated (`snakemake.dag_updated`), the last events line says "DAG updated after checkpoint <rule>: <old> → <new> jobs" from the next `progress` total, and rules move from Waiting for a checkpoint to Pending.
- `run_info` per-rule counts are not re-sent after a checkpoint, so a rule's "done / total" uses the jobs seen when the rule is behind a checkpoint, marked "at least".
- With nothing to run ("Nothing to be done"), every rule is Up to date and the run reads "Nothing to run: all outputs are up to date".

**Temporary and protected outputs (Snakemake).**
- The job files drawer gains an **Outputs** tab after the log tabs: each output of the job's `job_info`, with its state: "present", "not yet" (the job has not ended), "absent" (the job ended and the file is not there) or "deleted by Snakemake (temporary)" when a `snakemake.temp_removed` named it, with the time. A `protected()` output shows "write-protected" once `snakemake.protected` named it. A checkpoint target written `<TBD>` by Snakemake shows "decided after the checkpoint".
- Before deletion an output is not known to be temporary: Snakemake's events do not carry the `temp()` flag. Spectio does not guess it.
- A run with `--notemp` shows no deletion; the run's facts say "Temporary files kept (--notemp)" when the command line has it.
- The Summary's Results section is unchanged: Snakemake removes temporary files from the launch directory, not from results.

**Temporary files (Nextflow).**
- Nextflow has no per-output temporary marker. When `cleanup = true` (sent by `nf-spectio` at `onFlowCreate`), the run's facts say "Work directory cleaned after success (cleanup = true)", and after a successful run each job's files drawer opens on "This job's work directory was removed by `cleanup = true`" with the listing state `deleted_after_success` of §4.4. A failed, cancelled or aborted run is not cleaned (Nextflow 26.10.4, `Session.groovy:1375-1410`).

**Boards to update** (not changed by this section): LiteRunDetail, LiteRunDetailSnakemake, MLiteRunDetail (process and rule states, the Checkpoint chip, "at least <n> jobs"), LiteTaskFiles, MLiteTaskFilesSheet, LiteTaskFilesStates (Outputs tab, cleanup line).

Enabling it:
- Nextflow: the plugin `nf-spectio`, added by `NXF_PLUGINS_DEFAULT=nf-spectio@<ver>`: the one-shot prefix; `spectio login` offers the export as opt-in ([architecture §13.8](architecture-plugins-and-packaging.md#138-runs-started-from-a-terminal)). - Snakemake: `--logger <existing> spectio`, set once by `spectio login` (`engine snakemake profile --install`) *(assumed — pending Thomas, inbox #28)*: Spectio appends itself to the loggers already set on the command line or in a profile, so panoptes, snkmt or FlowO keep working ([`architecture-plugins-and-packaging.md`](architecture-plugins-and-packaging.md) §2).
- There is no `spectio run nextflow|snakemake` wrapper: `spectio login` is the one-time engine setup. *(assumed — pending Thomas, inbox #28)*

Three levels, decided automatically and shown on the run:

| Level | Condition | What the UI allows |
|---|---|---|
| **Observed** | Events arrive, but no runner can reach the launch directory | Full monitoring (states, tasks, logs streamed by the engine plugin). No relaunch; a banner explains how to adopt the run |
| **Adopted** | A runner running as the same user on that host can read the launch directory | Everything an UI-launched run has: resume, rerun from stage, cancel, review gates |
| **Registered workflow** | Any CLI run | The workflow is auto-added to **Workflows → Discovered** (not the curated catalog), keyed by repository + revision (Nextflow manifest / `commitId`; Snakemake git remote + Snakefile hash). One click **Promote to catalog** adds stages manifest, defaults and permissions |

Defaults: auto-registration as *Discovered* is on; an admin can switch it off (pure monitor-only). Parameters, command line, config and software versions captured from the run are kept, so a later "Copy to a new launch" can pre-fill the launch form.

## 11. Component states

Every pattern of §10.2 has these states. *(assumed — pending Thomas, inbox #29)*

| State | What it shows |
|---|---|
| Empty | Nothing to show; says why and the next step |
| Loading | A skeleton of the final layout: skeleton rows for tables and skeleton cards (header kept, grey gauges); never a bare "0" |
| Error | What failed, Retry, and the request ID: an error panel that maps the RFC 9457 problem `type` (catalogue: [`api-and-data-model.md`](api-and-data-model.md) §4.1) to a sentence; an API-error toast for a failed action; a full-page "Spectio is unreachable" |
| Permission | View only; the action is disabled with its reason |
| n/a | A value that cannot be computed, such as a check whose file is missing; shown as "n/a" with the reason |

**Live data.** Each state is shown with an icon and a word, never colour alone:
- *Live*.
- *Reconnecting*: "Reconnecting… data as of 10:41:08", Retry; SSE resumes with `Last-Event-ID` (api §5).
- *Stale*: an observer layer timed out or was switched off ("squeue timed out · next try in 4 min", "`sinfo` stale since 13:40, back-off 10 min", `observer.capacity: off` shown as "disabled by site policy"; [`schedulers-and-monitoring.md`](schedulers-and-monitoring.md) §3.2).
- *Head silent*: "No event from nf-spectio for 6 min · head job 48213351 still RUNNING · checking the head log" (schedulers §7).
- *Runner offline*: run actions become "Queue pause · applies on reconnect" with the reason and a link to Runner offline (§4.8); storage and capacity show "last measured 14:02 · on hold".
- *Catching up after restart*: a banner on a run while the API marks it `recovering: true`; its state-changing actions are disabled with that reason (boot order: [architecture §7.2](architecture-plugins-and-packaging.md)). *(assumed — pending Thomas, inbox #40)*

Live / Reconnecting in the footer is computed by the client from its SSE connection, not reported by the server (a stopped server cannot report itself). *(decided — Thomas, 2026-10-27, inbox #35)*

Actions that cannot take effect now are relabelled or disabled with their reason, and decision screens show the age of their data, so nobody pauses, cancels or approves on stale numbers without seeing it.

**Phone.** A status strip under the top bar with Live / "Reconnecting… last update 10:42" / Offline (actions disabled with the reason), on Run detail and Review detail.

The Legend board carries a "Live data" row (live, stale, reconnecting, head silent).
