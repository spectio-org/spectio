## What the step does

- **The symptom was not reproduced.** The cause on login1 is **[to be validated]**. The step first named a stale index (the database directory outlives a change of `runs_root`, and `rebuild_index` only adds rows). That does not explain a file that exists at the path the UI shows, so inbox #125 asks Thomas for checks on login1 and on the serve host (`/scratch` is often node-local).
- **`run_root`** (`files/taskfiles.py`) answers `410 log-cleaned` only when the runs root exists and is the runs root the run was recorded under. Otherwise it raises `Unreachable`, served as the new problem `409 run-dir-unreachable`. The two are told apart without opening anything: `os.path.realpath` of the recorded root against the runs root, so a symlinked `/scratch` matches.
- **Both details name the directory tried** (`tried <runs root>/<run>/launch`): a server-side path under the user's own runs root.
- **One helper**, `recorded_root(launch_dir, origin)`: the launch directory's grandparent, `None` for a `cli-observed` run (its launch directory is the user's own project, not under a runs root). `api/logs.py` and `api/taskfiles.py` both use it.
- **Job-file routes**: `AttemptFiles` carries `recorded_root`; every `run_root` call of the listing and the read goes through `_root(attempt, part)`; a Nextflow work directory that does not fit the current runs root is `Unreachable` when the run was recorded under another one (not `404`, not `410`). `in_pool` maps `Unreachable` to the problem for every file route.
- **Unchanged:** the confined, `O_NOFOLLOW`, private (`0700`) reads.
- **Tests:** `test_read.py` (the Logs route: gone with the runs root there, a missing runs root, another runs root, a runs root through a symlink) and `test_taskfiles_api.py` (missing runs root, other runs root, Nextflow work directory under another runs root, and a `cli-observed` run).
