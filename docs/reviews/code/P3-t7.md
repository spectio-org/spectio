## Findings

The finding texts are summarised from the round summaries and the fix commit's message. CR-P3T7-03 (r2) and SEC-P3T7-01 (r2) are one problem, found by both reviewers.

| Id | Severity | Finding | Status |
|---|---|---|---|
| CR-P3T7-01 (r1) | minor | `Spool._next` used up a file index on every create error that is not `EEXIST`, unlike `nf-spectio`. If creates keep failing (`EACCES`, or an inode quota on HPC scratch, `EDQUOT`), the index climbs by one per event. After 9999 events the writer stops for the rest of the launch, even once the quota is freed. | fixed in `b945971`: the writer tries `index + 1` and advances only on success or on `FileExistsError` (`test_failed_create_keeps_the_index`: two refused creates, then the third event lands in `-0001`) |
| CR-P3T7-02 (r1) | minor | `job_info.reason` was written to the spool unchanged apart from the 4096-character cut, including the "Params have changed since last execution" detail, which quotes param values (SEC-P3T1-08). A param built from `os.environ` puts a secret from the environment into a spool event. The server cuts it on read; the plugin already removes `slurm_extra` at the source for the same reason (SEC-P3T1-11). | fixed in `b945971`: `_job_info` cuts `reason` after the marker, as `spectio_sdk.events` does (`test_job_info_reason_params_detail_cut`) |
| CR-P3T7-03 (r1) | minor | `test_recorded_fixture_current` compares only event types and key names. The fixture's values can drift from a fresh run unnoticed, and `test_smk_real_plugin` relies on them: threads, `mem_mb`, `runtime`, benchmark, log. | **open**, follow-up FU-P3-34 |
| CR-P3T7-04 (r1) | minor | simplify: the `to_events` docstring breaks its last sentence in the middle. | **open**, FU-P3-34; `code-simplifier` left it, as only reformatting |
| SEC-P3T7-01 (r1) | minor | `bridge.err` is appended to whatever regular file already sits at `<spool parent>/bridge.err`. Its owner, mode and link count are not checked, and the 0600 applies only when the plugin creates it. A probe on an existing 0644 file kept 0644 and appended the error text, and error texts can quote record content (`record not written: …`). `events/` itself gets an owner and mode check. | **open**, assumed: [inbox #97](../inbox.md#97-assumed-what-the-snakemake-logger-plugin-sends-how-it-fails-and-its-interface-range-p3-task-7) rule 3; FU-P3-34 |
| SEC-P3T7-02 (r1) | minor | `snakemake.slurm_submitted` is parsed from the message of any record without an event. Workflow code that logs matching text through Snakemake's logger can forge a SLURM job ID and log path for any `jobid`. A probe with `Job 3 has been submitted with SLURM jobid 99 (log: /home/u/.ssh/id_rsa).` returned that path. Mitigations: the projector keeps a log path only inside the launch directory (req. 13), and `native_id()` validates the job ID. A forged `native_id` on an open attempt is still kept, and would become a target once a later task cancels or queries by `native_id`. | **open**, assumed: inbox #97 rule 4 |
| SEC-P3T7-03 (r1) | minor | `test_interface_lowest_1x` runs `uv run --no-project --isolated --with snakemake-interface-logger-plugins==1.1.0` in CI. That resolves 1.1.0 and its dependencies from PyPI at test time, with no lock and no hashes, then runs them. [dev-env §1](../../specs/dev-environment-and-testing.md#1-toolchain-pinned-in-devversionsenv) asks for hash-locked Snakemake plugins. The token is read-only and no secret is exposed. The existing `uv tool install snakemake==…` step has the same gap. | **open**, FU-P3-34; [dev-env §11](../../specs/dev-environment-and-testing.md#11-ci-workflows) says so |
| SEC-P3T7-04 (r1) | minor | No test covers the "never slows the run" half of the robustness requirement. The writes run on Snakemake's `QueueListener` thread (an unbounded `Queue(-1)`), and `queue_listener.stop()` joins that thread after the queue drains. A spool on a stalled shared file system therefore holds Snakemake's exit as long as `os.write` blocks: the head's exit code, and the runner's view of the end, wait for it. | **open**, assumed: inbox #97 rule 5; [architecture §13.3](../../specs/architecture-plugins-and-packaging.md#133-failure-semantics-and-heartbeat) says so |
| CR-P3T7-03 (r2) / SEC-P3T7-01 (r2) | minor | The plugin's copy of the marker, `_PARAMS_CHANGED`, must stay equal to `spectio_sdk.events._PARAMS_CHANGED`, and only a comment says so. If the SDK text changes, the cut at the source stops matching with no test failing. The server still cuts, so nothing reaches the server; the param values would reach the 0600 spool again. | **open**, FU-P3-34: a test that compares the two (the test project already depends on `spectio-sdk`) |
