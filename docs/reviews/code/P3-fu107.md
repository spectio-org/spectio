## What the step does

Two causes, found by the worker in the installed Snakemake 9.27.1.

- **The Summary table was alphabetical.** At the freeze, Snakemake rules took their position from `.spectio/rules.txt` (`stages/freeze.py`, `_snakemake`). The head writes that file from `snakemake --list-rules`, which sorts by name: `for rule in sorted(rules, key=lambda r: r.name)` in `Workflow.list_rules`, `snakemake/workflow.py:734-740`. `doc-writer` read these lines in the 9.27.1 wheel. `/processes` returned the rows in position order.
- **`align` came last.** Since FU-P3-90 (#182), `_pipeline_order` put every rule absent from the `nodes` of all rule graphs after every graph rule, even a rule that already had jobs. On the demo run `align` joins the DAG after the `split` checkpoint, so it is in no graph.

The fix:

- **`stages/freeze.py`, `_snakemake`.** The rules come in the rule files' order. `rules.txt` only says which rules belong; a rule it lists that the parsed files do not hold is appended.
- **`api/runs_read.py`, `list_processes`.** For Snakemake the items are in first-seen order: the rules by their first task, then the rules with no job in position order. This is the definition in api §5, "the order of the task IDs". Nextflow keeps its `onProcessCreate` position, which is already first-seen.
- **`api/runs_read.py`, `_pipeline_order(names, graphs, seen)`.** A rule with a job counts as a graph rule with no links, so its first job places it: `align` now follows `split`. A rule in no graph and with no job still goes last, as [inbox #126](../inbox.md#126-assumed-where-a-rule-that-is-in-no-rule-graph-is-listed-fu-p3-90) chose. The docstring changed, so the OpenAPI snapshot was regenerated.
- **Test (`test_process_status.py`).** New `test_rules_in_first_seen_order`. It writes `rules.txt` sorted by name, as Snakemake does, and checks that before any job the list is in Snakefile order. After jobs for `make_reads`, `split` and `align` it checks the list `[make_reads, split, align, all, merge, report, unused]` and the pipeline order `[make_reads, split, align, merge, report, all, unused]`. `smk_run` gains a `rules=` parameter. The FU-P3-90 test (`test_pipeline_order_rule_missing_from_rulegraph`) is unchanged: its `align` has no job, so "last" is still right.
