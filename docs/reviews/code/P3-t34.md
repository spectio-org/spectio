**What the checks prove and do not prove.**

- The two `sacct` rules of round 4 rest on two facts about real output, both **[to be validated]** on `slurm-mini`: that `sacct` prints a job's step rows after the job's line, and that without `--duplicates` it prints one job line per ID. If steps came first, CPU and memory would be empty (values missing, not wrong). The man page supports the second only in part: by default only the most recent record of an ID is shown, but "records left in the RESIZING state by a resize operation are also shown by default" ([`sacct(1)`, `-D, --duplicates`](https://slurm.schedmd.com/sacct.html), read 2026-11-07). See SEC-P3T34-06 (r4).
- Not run: the check on `slurm-mini` (P1 Task 22 is not built, and this host has no Docker daemon). The `sacct` output in the tests is synthetic.
- Benchmark reads were checked with fakes of the file pool and of `Measures.claim` and `release`, not on a slow file system. Whether thousands of benchmarks on GPFS or Lustre outlast `READ_TIMEOUT_S` is **[to be validated]**.
