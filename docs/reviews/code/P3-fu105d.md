## Choices where api §5.5 is silent (the smallest thing)

- **Who may read.** As every run route in 0.0.2: the session, Host and Origin middleware, then `run_row` (`404 not-found` when unknown, malformed or deleted). There is no project scoping and no share link in 0.0.2, so a run of another project reads as `GET /runs/{id}` does (200); the rows are read by `run_id`, not by `attempt_metrics.project_id`, so a stale `project_id` after a move hides nothing (SEC-P3FU105A-06). The across-runs `project_id IN visible_projects` rule is 105e's.
- **`metrics=`**: one comma-separated parameter (as `group_by=process,day`), the wire names are the twelve measured columns; default `cpu_eff` (the CPU tab is first in ui-spec §4.12); an unknown name or more than 4 is `422` on `metrics`.
- **`process=`**: more than 20 values or a value over 256 characters is `422` on `process`; a name that matches nothing is not an error.
- **`processes`**: every process or rule the run knows (as `/processes`), in `pipeline_order`, a process with no row has `n: 0` and null stats; `measured` follows §3.6 (a CPU or memory efficiency), `requested` is `efficiency.aggregate`'s over the counted rows, `jobs` is §3.6's over the tasks (done / max(tasks, planned)).
- **Top-level counts** are over the whole run, whatever `process=` says: `total` the counted rows, `measured` those with a CPU or memory efficiency, `cached` the tasks in `cached` or `stored`.
- **Statistics**: q1, median, q3 and mean rounded to 4 places as §3.6's ratios; min and max as stored; `min_task`/`max_task` the first attempt in task order with that value.
- **Waste lines**: over the counted rows (with the default `attempts=last` that is §3.6's aggregate); a line is listed only from 3 jobs, so the rule sits in one place.
- **Stride**: one stride for the answer, the smallest that keeps every process at 2,000 points and the answer at 20,000; each process takes its attempts 0, stride, 2 stride… in task order (`task_id`, `launch_n`, `n`). `points=false` answers `points: null`.
- **`pending_accounting`** (CR-P3FU105D-01): on a SLURM run (`on_slurm`) with accounting enabled, the rows of every attempt (not only those `attempts=` counts) whose job `Accounting.waiting` still holds: the jobs asked and not answered, a follow-up included, a job given up not; every job with an ID while the run's end-of-run sweep is due or running. No `sacct` call. An ended run whose `metrics_sacct_at` is null and that the boot fill may still reach (`metrics.FillProgress`) counts every row with a job ID whose source is not `sacct`.
- **The cache.** The spec asks for it ("cached once its `pending_accounting` is 0"). An ended run (`TERMINAL`) with nothing pending is kept, keyed by run and query, at most 32 answers and 200,000 points and processes in all (least recently used dropped first). An entry holds a stamp read before its rows: the run's commit stamp (`Cache.changed`, from the writer's `on_commit`: projector events, the benchmark read) and `runs.metrics_sacct_at` (set by the fill and by 105c's `_update` on every application), so a change committed during a read is never cached as new. 4,096 run stamps are kept; a forgotten run takes the last forgotten stamp, which never equals an older one.
- **Load** (SEC-P3FU105D-01): the run's `attempt_metrics` count is checked before any row is read, `422 range-too-wide` with `count` above 200,000; every read runs under the SQLite progress handler, 5 s **[to be validated]**, past which the answer is `422 range-too-wide`. A deleted run's rows are already deleted with it (105a).

## Assumptions

- 105c's sweep keeps setting `metrics_sacct_at` on each application (its `_update` does on PR #274); if it stops, the sweep must call `note_change` for the cache to drop its answer.
- The writer is the only path that changes `attempt_metrics` while the server runs; a rebuild happens at boot, before any answer is cached.
