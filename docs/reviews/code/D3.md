### SEC-D3-01 · major · PyPI and npm dependency trees were neither locked nor hash-checked

- **Where:** `dev/bootstrap.sh` (Snakemake and Playwright installs); the spec claim "every download is checked"
- **Evidence:** dozens of transitive packages were resolved fresh on each cold run, as root, in the cloud setup script and in CI.
- **Problem:** a compromised dependency would run as root with repository credentials nearby, and the spec stated a control the code did not have.
- **Proposal:** a hash-locked requirements file installed with `--require-hashes`, a `package-lock.json` installed with `npm ci`, and a spec naming the remaining unhashed downloads.
- **Found by:** security-reviewer
- **Status:** applied (`e7f5dc6`). `dev/snakemake.lock.txt` (72 packages, every one with `--hash=sha256:`) goes into a venv named after the lock with `uv pip sync --require-hashes`; `dev/npm/package-lock.json` goes in with `npm ci`. A tampered hash was refused (`Hash mismatch`, exit 1). §1 "Checked downloads" names the two downloads not hashed by us: the uv-managed CPython **[to be validated]** and Playwright's Chromium.

### SEC-D3-02 · minor · Running as root, tar kept the archive's owners

- **Where:** `dev/bootstrap.sh`, `install_tar`
- **Evidence:** GNU tar keeps stored uids and gids by default when run as root.
- **Problem:** on a shared host, a matching uid could replace `node` or `helm`.
- **Proposal:** `--no-same-owner --no-same-permissions`.
- **Found by:** security-reviewer
- **Status:** applied (`e7f5dc6`).

### SEC-D3-03 · minor · The doctor runs images by tag after checking them by digest

- **Where:** `dev/doctor.sh` (hello-world, sind config, kind `--image`, the Job image)
- **Evidence:** `ensure_image` checks the digest, then the tools start the image by `name:tag`.
- **Problem:** something could retag the image between the check and the run.
- **Proposal:** run by digest where the tool accepts it.
- **Found by:** security-reviewer
- **Status:** rejected (the reviewer accepted the reason in round 2). An image pulled from `mirror.gcr.io` carries only a mirror reference, so `name@sha256:…` would bypass the mirror and pull from Docker Hub, which rate-limits (spike D2). Retagging needs control of the Docker daemon, which is already root.
