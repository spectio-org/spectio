## What was built

- `spectio_server/api/performance_across.py`: `GET /performance:summary`, `/performance/attempts` and `/performance/facets` (api §5.5), the shared filters (`asked`, `Filters`, `where`), the statements of each route, the row-count check, the `Gate` of the `429` limits. The statistics are 105d's `performance.stats`; the time budget is 105d's `performance.budget` (it now names what was not read).
- `api/models.py`: `PerformanceSummary`, `PerformanceAttempts`, `PerformanceFacets` and their parts; the OpenAPI snapshot gains the three paths and their schemas only.
- `api/problems.py`: a `Problem` may carry headers (the `429`'s `Retry-After`).
- `failure._last_attempt` takes the task column it correlates with (default `tasks.id`, no behaviour change), so `attempts=last` reads `attempt_metrics.task_id`.
- `performance._filter` takes the field it names in a `422` (default `process`, no behaviour change).
- Migration `0016_attempt_metrics_pipeline`: an index `(project_id, pipeline, ended_at)`. The query-plan test showed SQLite's planner taking `(project_id, ended_at)` for `pipeline=` without `process=`: in the four-column index of 105a, `process_or_rule` sits between `pipeline` and `ended_at`. The other four filters use 105a's indexes.

## Choices where api §5.5 is silent (the smallest thing)

- **Who may read.** The session, Host and Origin middleware, as every route. 0.0.2 has no token, share-link or embed session, so a request without the session cookie is `401` (`test_perf_tenancy_share_link`); the `403 forbidden` of a share link comes with share links. `visible_projects(principal)` in single-user mode: the principal is the oldest (`store.runs.first`, as every write of 0.0.1); its groups are those of the projects it created (`ensure_tenancy`'s `personal`); its projects are those of its groups. Every statement, the count included, filters `attempt_metrics.project_id IN` those projects. A moved run is visible by the `project_id` the move writes in its transaction (api §4, SEC-P3FU105A-06: no move route exists yet); a deleted run has no row (105a).
- **The principal of the `429` limit.** One user in 0.0.2: a signed-in session stands for the principal, so one query per session and two per server; `Retry-After: 5` (the budget).
- **`range`, `since`, `until`.** `until` defaults to now, `since` to `until` less `range`, so `since` or `until` alone works. Over 366 days is `422 validation-failed` on `until` (api §5.5; inbox #139 choice 6a says `range-too-wide`, the spec's wording is kept); `since` not before `until` is `422` on `until`; a time without an offset is `422` on its field.
- **`user=`.** Only where multi-user (§6): in 0.0.2 no owner filter unless asked; `me` is the principal, a `usr_` ID filters `owner_id` within the visible projects; anything else is `422` on `user`.
- **`environment=`** is the `environments.name` of the run's environment row (`local`, `slurm`), among the environments of the caller's groups; another group's name matches nothing. The facet answers `{id, name}`, the name "another environment" for an environment of another group.
- **`group_by`** defaults to `process`; at most 2 keys, at most one of them a period; `hour` only within 48 h. The key members are `process_or_rule`, `partition`, `pipeline`, `run_id`, `period_start` (the start of the hour, day or ISO week, from Monday, in `tz`, with its offset). `tz` is a name of `zoneinfo.available_timezones()` or `UTC`.
- **Streaming.** The rows come in `ORDER BY` the group columns then `ended_at`, so each group, a period included, comes together; one group's rows are in memory at a time; 500 groups at most are kept, largest `n` first, ties in that order.
- **`scanned`** and the row-count check count the rows in the filters before `attempts=last` (an upper bound read on the index; the last-attempt condition is a lookup per row). `totals.jobs` counts the rows after it.
- **The row-count check** runs on all three routes, `422 range-too-wide` with `count` over 1,000,000; every statement of a request shares one 5 s budget **[to be validated]**.
- **`/performance/attempts`.** Every column but `owner_id`, `project_id` and `environment_id`, with `run_name`; keyset paging on the sort key and `attempt_id`; a null sorts last (coalesced past every value); the cursor holds the sort values only, the project filter is applied again on every page.
- **`/performance/facets`.** Each facet over every attempt in the filters but its own (no `attempts=last`), nulls left out, sorted, at most 500; `truncated` names the facets cut.
- **The 1.2-million-row test** writes the rows with one recursive CTE per 200,000 rows through a plain `sqlite3` connection, no tasks or attempts (nothing past the count reads them), and drops the four filter indexes the counts do not read, to keep the file and the WAL small (about 7 s here). No slow marker exists in the repository, so it runs with the rest.

## Assumptions

- A future project move updates `attempt_metrics.project_id` in its transaction (api §4); the routes filter on it alone.
- The oldest principal is the server's user (single-user mode), as `insert_run` assumes.
