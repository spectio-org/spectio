[api §14.1](../../specs/api-and-data-model.md#141-driven-runs-001) (note 2026-11-07) says "true when any process sets `clusterOptions`". The worker stated the gap; it was not in a follow-up, an inbox entry or the spec | **open** for the code, FU-P3-52. The gap is now written in the api §14.1 as-built note and in [inbox #115](../inbox.md#115-assumed-dag-updates-temporary-outputs-and-the-slurm-request-as-built-p3-task-33) rule 1 |

### security-reviewer

| Id | Severity | Finding | Status |
|---|---|---|---|
| SEC-P3T33-01 | minor | The Snakemake side sends no flag that `slurm_extra` was set. The bridge drops the key (`resources.pop("slurm_extra", None)`) and the server drops it again, so nothing in the spool says it was set. But [api §5](../../specs/api-and-data-model.md#5-endpoint-catalogue-api-v1) (note 2026-11-07) and Task 34's `test_slurm_request_smk` ("`slurm_extra` set -> `custom_options` true, no text") need that fact. Task 34's file list does not include the plugin, so its builder may be tempted to loosen the drop to get the flag back | **open**, [inbox #115](../inbox.md#115-assumed-dag-updates-temporary-outputs-and-the-slurm-request-as-built-p3-task-33) rule 2, FU-P3-52 |
| SEC-P3T33-02 | minor | `clusterOptionsSet` misses a `clusterOptions` directive written inside a process in the script, because only `session.config.process` is walked at `onFlowCreate`. The flag can be false while `sbatch` got custom options, and the UI would then present the trace request as the whole story. An integrity gap, not a leak: no text is sent | **open**, same as CR-P3T33-01 |
| SEC-P3T33-03 | minor | `SnakemakeOutputPath.path` is a bare `str` on the server side. Spool lines are untrusted input ([dev-env §15.3](../../specs/dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts) req. 6), yet nothing bounds the path below the 64 KiB line cap, refuses C0 or DEL control characters (`[^\n]` lets `\r` and ESC through) or enforces "relative to the launch directory". Anyone who can make Snakemake log an untyped info text can forge `temp_removed` or `protected` for any path: the Snakefile author, through `logger.info(...)` in `onstart` or `run:` code, or a hand-written spool. The workflow author owns the run, so the impact is a mislabelled output state. The only control is the check against the outputs of a `job_info`, which api §14.1 assigns to Task 34 | **open**, assigned to Task 34 ([inbox #115](../inbox.md#115-assumed-dag-updates-temporary-outputs-and-the-slurm-request-as-built-p3-task-33) rule 4), FU-P3-52 |
| SEC-P3T33-04 | minor | The dedup set holds up to 65536 full paths of up to about 4070 characters, roughly 270 MB in the worst case, inside the user's Snakemake head on a shared login node. Realistic paths are about 10 MB, but the bound is in items, not bytes. A memory blow-up here would turn "a lost event, not a lost run" into a lost run | **open**, same as CR-P3T33-03 |

SEC-P3T33-03 does not change what the bridge sends: the path is sent as Snakemake wrote it. It changes what Task 34 must do with it: keep a path only if it is, byte for byte, one of the outputs of a `job_info` of the run, and bound it and refuse control characters before any other use.
