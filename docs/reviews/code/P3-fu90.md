## What the step does

- **Server (`api/runs_read.py`).** `_rulegraph()` becomes `_rulegraphs()`: every `spectio.engine.snakemake.rulegraph` event of the run, oldest first, and an empty list for Nextflow (the query lost its `.limit(1)`). `_pipeline_order(names, graphs)` collects the rule names from every graph's `nodes` and merges every graph's `links`. Only the rules named in some graph are sorted topologically, ties by the list's order. A cycle's rules come after the other graph rules. The rules in no graph come last, in the list's order. With no graph at all the order is the list's order, as before. `_run_facts` still reads the last graph (`graphs[-1]`), so process statuses do not change.
- **What the bridge stores.** The worker read the installed Snakemake 9.27.1: it logs one rule graph per invocation, in `_build_dag` after `update_checkpoint_dependencies` (`snakemake/workflow.py:1274-1279`; `log_rulegraph` at `:1222-1272`), and none after a later checkpoint re-evaluation. The plan assumed a new graph after each re-evaluation; for 9.27.1 that does not hold. The logger plugin forwards each graph as is (`engine-bridges/snakemake-logger-plugin-spectio/snakemake_logger_plugin_spectio/__init__.py:178-180`). So the merge of several graphs matters only for a run with several invocations, and the fallback "after all graph rules" is what fixes the demo run: `align` now comes after the nine graph rules, `all` included. The T2 fixture `snakemake-9.27.1_checkpoint_flaky_retry.spool.jsonl` has the same shape (one graph, nine nodes, no `align`).
- **Tests (`test_process_status.py`).** One new test, `test_pipeline_order_rule_missing_from_rulegraph`: a first graph without `align` (it comes after the graph rules), then a second graph that places `align` between `split` and `merge` (the merged links place it). Two tests changed their expected result with the rule: no links (the graph rules first, in Snakefile order, then `align` and `unused`) and a cycle (the cycle's rules after the other graph rules, before the rules in no graph).

## Findings

Status is what `doc-writer` found at `0dd9ee2d` plus the docs commit.

| Id | Severity | Finding | Status |
|---|---|---|---|
| CR-P3FU90-01 | minor | The docstring of `test_pipeline_order_follows_rulegraph_links` still says "a rule outside the graph keeps its place among the ties" (`test_process_status.py:246`). Under the new rule that is false: `unused` is in no graph's `nodes`, so it comes after every graph rule and is not a root among the ties. The assertion (`[*chain, "unused"]`) passes only because both rules put `unused` last. | open: a one-line docstring fix, listed in FU-P3-92 |
| SEC-P3FU90-01 | minor | `GET /runs/{id}/processes` now reads and decodes every `snakemake.rulegraph` event of the run on each request; the old query had `.limit(1)`. The number of graph events per run has no limit of its own. The spool caps are `MAX_LINE_BYTES` 64 KiB per event, `MAX_FILE_BYTES` 64 MiB per file and `MAX_SPOOL_FILES` 1024 per launch (`spectio_sdk/events.py:24-28`), summed over every launch of the run. Each run-detail frame reads the route again, so a spool full of rule graph events makes each request read and parse up to gigabytes of JSON and blocks the single-user server. Anything that can append to the spool can write such a spool: the user's own head, a job under the same uid, or, for a cli-observed run, whoever can write the launch directory, which [dev-env §15.3](../../specs/dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts) req. 12 treats as untrusted. The store is an index with one server per user, so the impact is availability only. No §15.3 control is missing: req. 6 caps ingest, not this read-side amplification. | open: follow-up FU-P3-92 (see below) |
