## What the step does

- **The routes** (`api/results.py` `raw_response`; `api/workdir.py` passes the same arguments). The results and work-directory raw routes take `as=tiff` and `as=zarr` and a documented `Range` header. The steps run in the order of the table:
    - 1: the route's own checks first. The 1 GiB cap is lifted only for `as=tiff` with `Sec-Fetch-Dest: empty` and a `Range`, and not with `?download=true`.
    - 2: `?download=true` is an attachment, the `Range` ignored.
    - 3: any other `as` value is `422 validation-failed` on `as`.
    - 4: `as=tiff` needs a `.tif` or `.tiff` name, any case.
    - 5: `as=zarr` needs a Zarr key below the first `.ome.zarr` part (`_zarr_key`): middle parts `_KEY_PART`, the last part a metadata name or a chunk part. `.zmetadata` is refused.
    - 6: without `Sec-Fetch-Dest: empty`, the attachment as before.
    - 7: a Zarr key over 16 MiB is `413 file-too-large`.
    - 8: one closed `bytes=<first>-<last>` of at most 8 MiB + 1 byte that starts before the end of the file (`_closed_range`). Open-ended, suffix, multiple and malformed ranges are `422 validation-failed` on `Range`, and so is a TIFF read with no range.
    - 10: the first 4 bytes of a TIFF are a TIFF or BigTIFF header, in either byte order (`TIFF_HEADS`).
    - 11: `206` with `Content-Range`, the last byte capped at the end of the file, or `200` for a whole Zarr key; `application/octet-stream`, `Accept-Ranges: bytes`, no `Content-Disposition`, the shared headers, the CSP `sandbox` and `Vary: Sec-Fetch-Dest`.
- **What the server reads** (`files/results.py` `open_raw(where, rel, cap, head)`). `cap=None` is no cap; `head` is the number of bytes read at the first opening: 4 for `as=tiff`, 0 for a Zarr range, a full chunk otherwise. The range is then read from its own first byte by `_chunks`, which replaces the old inner generator; each chunk goes through `read_chunk` with its identity check.
- **Middle-part links.** Refused by the walk already (`O_NOFOLLOW` gives `ELOOP`, which becomes `422`); a test shows it, and no code changed.
- **OpenAPI snapshot.** Both raw routes list the `as` enum (`image`, `tiff`, `zarr`) and a documented `range` header.
- **Tests** (`tests/api/test_imaging.py`, 15, all passing). One `test_req14_imaging_*` per row of the table, then: the read-amplification test (a 64 KiB range in the middle of a 4 MiB file reads at most 64 KiB + 4 bytes; a Zarr range reads exactly its range), a 2 GiB sparse file (its TIFF range `206`, a plain raw read `413`), a range across the chunk seam, a file replaced in the middle of a range (aborts, on the real server), a key below a linked `.ome.zarr` folder (refused), and in a work directory `.zattrs` refused while `zarr.json` and a TIFF range are served. A literal `..` cannot be sent through the test client, which drops it; `..` is tested on `_zarr_key` directly and `%2e%2e` over the route.
- **Not in this step**, as the task said: step 0 (script and worker loads) and step 9 (the read slots), the CSP change, and the session and cross-site tests on both `as` values. The plan gives them to FU-P3-102b.
