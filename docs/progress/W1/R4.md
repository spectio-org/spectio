## Findings and open questions

**The five findings that matter most** (the review file explains the choice):

1. [CH-001 · blocker](../../reviews/R4-constraints.md#ch-001-blocker-the-recommended-head-job-puts-the-engine-and-its-event-bridge-on-a-compute-node-where-outbound-network-is-often-blocked): the recommended SLURM head job runs the engine and its event bridge on a compute node, where outbound network is often filtered.
    - synthesis §10 (l.396) says the network risk is "not the compute nodes", but a head job runs on one.
    - The only fallback, a server-side forwarder, contradicts "the server never mounts storage" (checking §11.1).
    - Proposal: the bridge writes a spool in the launch directory and the runner forwards it; the runner does all network-dependent preparation on the login node, so the head runs offline.
2. [CH-006 · major](../../reviews/R4-constraints.md#ch-006-major-nf-spectio-failure-semantics-are-unspecified-and-a-break-in-the-beta-interface-would-be-silent): `nf-spectio` depends on `TraceObserverV2`, which is `@Beta` and first appears in Nextflow 25.04. Nextflow swallows observer errors at debug level, so an interface break silently stops all events. No spec states a minimum Nextflow version, and synthesis still carries the `nf-tower` "aborts the run" sentence.
3. [CH-007](../../reviews/R4-constraints.md#ch-007-major-runner-commands-have-no-table-three-transports-and-no-idempotent-launch) and [CH-003](../../reviews/R4-constraints.md#ch-003-major-continue-or-relaunch-can-start-while-the-previous-head-is-still-finishing) · major: duplicate head jobs.
    - There is no commands table, no lease and no idempotent launch. A runner that crashes after `sbatch` and before its acknowledgement starts a second head job in the same launch directory.
    - Continue or relaunch can race the previous JVM, which still holds the cache lock.
    - Proposal: `launches` and `runner_commands` tables, a `CONTINUE_REQUESTED` state, and adopting an existing job by its name.
4. [CH-004 · major](../../reviews/R4-constraints.md#ch-004-major-no-scale-model-and-no-performance-budgets-in-any-spec): no scale model and no performance budgets. The Runs list needs per-run counters the schema lacks, and the graph endpoint has no granularity for 100 000 tasks. Proposal: api §15 budgets and a tier-5 benchmark.
5. [CH-011 · major](../../reviews/R4-constraints.md#ch-011-major-the-event-log-grows-without-bound-and-raw-nextflow-trace-records-carry-script-and-env): the append-only event log keeps raw Nextflow trace records, including `script` and `env`. That costs about 0.7–0.9 GB per 100 000-task run and may leak secrets. The size drives backup time ([CH-022](../../reviews/R4-constraints.md#ch-022-major-logical-json-lines-backups-do-not-scale-need-one-snapshot-and-have-no-rpo-or-rto)) and migration time (CH-023). Proposal: archive raw payloads after a run ends, and send `script` and `env` at most once.

**What the numbers say** (from the file's summary): raw SQLite write speed is not the limit. About 27 k events/s per stream was measured, against a peak need in the low thousands per second. The risks are long write locks, storage growth, the single event loop, ordering and delivery rules, and what HPC sites allow.
