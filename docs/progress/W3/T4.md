## What changed

The [spike t4-ci](../../research/spike-t4-ci-2026-10-28.md) covered T4's scope; this step keeps what it proved and drops the rest.

- **Cluster profiles,** [dev-environment §4.2](../../specs/dev-environment-and-testing.md#42-kubernetes-with-kind):
    - `dev/k8s/cluster.sh up mini|kueue`, `down mini|kueue`. `k8s-mini` is one kind node; `k8s-kueue` is a control plane and 2 workers, with Kueue `KUEUE_VERSION`. Both get the namespace `spectio-work` with a `ResourceQuota`, and its `default` ServiceAccount does not mount a token in pods (`dev/k8s/base.yaml`).
    - Kueue comes from the release's `manifests.yaml`, checked against `KUEUE_MANIFEST_SHA256`. It is set up with two ClusterQueues and two LocalQueues (`dev/k8s/kueue-queues.yaml`); the script fails if they are missing after the retries, and waits until the visibility API answers.
    - The tools come from `dev/bootstrap.sh`, at the pins of `dev/versions.env`. The task image is read from the `k8s` profile of the synthetic pipeline and pre-pulled on each node.
    - The repository is mounted into every node at its own path, so that task pods can see the pipeline and its work directory under `.scenarios/` (newly gitignored).
- **`dev/versions.env`:** two new pins:
    - `KUEUE_MANIFEST_SHA256`, computed, because no checksum is published;
    - `NF_K8S_25_10_VERSION=1.2.3`.
- **Scenarios,** `tests/k8s/scenarios.sh`. Each scenario fails on an unexpected outcome.
    - `failures`: one OOMKilled pod, a Job and a Pod over their deadline, and a Job whose pod exits 3.
    - `nf25` and `nf26`: the synthetic pipeline with `-profile test,k8s` plus `tests/k8s/kind.config`. Each runs twice under the head's own token: a happy run that must exit 0, and a tool-error run that must exit 1. No API call may be refused (403). Each grant that neither run used is listed as `unused-grants` (`tests/k8s/api_calls.py`). The task pod must have no `kube-api-access-*` volume, and the head's ServiceAccount must be denied the calls of the deny list.
    - `kueue-wait`: one Workload admitted and two waiting, with their visibility positions.
    - `runner`: the runner's work done with its own token, then the deny list plus `create pods`, which must all be denied.
    - The ServiceAccount kubeconfigs are written to a private temporary directory outside the repository (task pods mount the repository), and never hold the admin key.
- **RBAC,** `tests/k8s/rbac.yaml`: the replacement Roles, which differ from §4 (see [Findings](#findings-and-open-questions)).
- **CI,** `.github/workflows/pipelines-k8s.yml`, two parallel jobs:
    - `mini`: `failures nf25`;
    - `kueue`: `kueue-wait nf26 runner`.

    It runs on a push to any branch that touches its paths, nightly, and on manual dispatch. It has `permissions: contents: read`, no secrets, a 30-minute timeout, actions pinned by SHA, and no `${{ }}` in `run:`. Its fixtures go to the artifacts `k8s-fixtures-mini` and `k8s-fixtures-kueue`. Like `dev-env.yml`, `ci.yml` does not call it, so it is not part of `ci-ok`.

## How to test

On a machine whose Docker runs on cgroup v2 (not a Claude Code cloud session), from the repository root:

```bash
bash dev/bootstrap.sh && bash dev/k8s/cluster.sh up kueue && \
  for s in kueue-wait nf26 runner failures nf25; do bash tests/k8s/scenarios.sh "$s" || break; done
```

Each scenario prints a `RESULT` line and exits 1 on an unexpected outcome. Fixtures land in `.scenarios/k8s/fixtures/`. `bash dev/k8s/cluster.sh down kueue` removes the cluster. In CI, push a change under `tests/k8s/`, or dispatch `pipelines-k8s.yml` once it is on `main`.

## Findings and open questions

**Differences with the specs,** for TRIAGE3; the specs are not edited. The insufficiency of the §4 Roles was measured in spike runs [40662141233](https://github.com/weber8thomas/spectio/actions/runs/40662141233) and [40663207755](https://github.com/weber8thomas/spectio/actions/runs/40663207755). `scenarios.sh` tests the replacement Roles of `tests/k8s/rbac.yaml`: T4 runs show them sufficient (0 refusals, 403) and, for the two heads, minimal (`unused-grants=[]`). The runner Role's minimality is not measured, because there is no runner code yet: `persistentvolumeclaims: get` and `watch` on pods, events and Workloads are granted and never used, and the visibility rule is narrowed to `get`, against `get, list, watch` in §4.

1. **Nextflow 26.10 engine-head Role** ([schedulers §4](../../specs/schedulers-and-monitoring.md#4-kubernetes-in-detail)): not sufficient and over-broad; [note, Findings](../../research/spike-t4-ci-2026-10-28.md#findings-for-triage-specs-not-edited) item 1.
2. **Nextflow 25.10 engine-head Role** (§4): lacks `pods/status: get`; closes "25.10 needing `pods: create`"; note item 1.
3. **Runner Role** (§4): lacks `workloads.kueue.x-k8s.io: get, list, watch`; note item 2.
4. **Nextflow 25.10 needs `nf-k8s` named** (§4 and the `k8s` profile); note item 3.
5. **"Queued" comes from the visibility API, not from Workload conditions** (§4). The visibility API listed a pending Workload whose `QuotaReserved=False` condition came late or never:
    - run 40672184666: `job-fx-kq-1` had only `PodsReady=False/WaitForStart`, at position 0;
    - run 40669626241: `job-fx-kq-3` had only `PodsReady=False/WaitForStart`, at position 1;
    - run 40668895003: the second pending Workload had no `QuotaReserved=False` after 2 minutes.
6. **An OOM kill produces no event**, only `state.terminated` in the pod; note item 4.
7. **The head can get a 404 on `jobs/status`** when it reads a Job that it is deleting. That is not a permission refusal, so a check must not count it as one.
8. **The "Required checks" paragraph** ([dev-environment §11](../../specs/dev-environment-and-testing.md#11-ci-workflows)) says the pipeline workflows are reusable workflows that `ci.yml` calls. `pipelines-k8s.yml` is standalone (push with a path filter, nightly, manual), so it is outside `ci-ok`. The `pipelines-k8s.yml` row of §11 now says so; it no longer lists `helm/kind-action` (the build uses `dev/bootstrap.sh` and `dev/k8s/cluster.sh`), and nf-core/demo stays in `pipelines-real.yml`. The `helm install` of the chart waits for the chart.
9. **The `k8s-mini` row** (§4.2) listed SeaweedFS, the Snakemake Kubernetes executor and a runner Role. SeaweedFS and the Snakemake executor are not built: T4's prompt does not ask for them, and the row now marks them as planned. The runner Role is not installed by `up mini`: the scenarios apply `tests/k8s/rbac.yaml` themselves (CR-T4-03).
10. **Other spike findings:** `FailedScheduling: Insufficient cpu` is back-pressure (note item 6); task pods mounted the `default` token (note item 7), fixed here (SEC-T4-02); inbox #51's "cannot download artifacts" does not hold (note item 8), and this step's fixtures came from artifacts.

**Inputs for TRIAGE3 from the security review** (not fixed here):

- **SEC-T4-03:** whoever can create Jobs or Pods in the shared `spectio-work` can run as any ServiceAccount there, mount a hostPath, and delete another run's pods. Proposal: one namespace per run or per user, with PodSecurity `restricted` and a policy that pins `serviceAccountName`.
- **SEC-T4-05:** the `nf-k8s` 1.2.3 plugin is fetched by version, the Kueue controller image is referenced by tag, and the whole bootstrap runs in the job. Proposal: pin the plugin by checksum and the Kueue image by digest, and bootstrap only the tools the job uses.

**Open question.** Should `pipelines-k8s.yml` join `ci.yml` and `ci-ok`? It takes about 3 to 4 minutes, but kind adds a flake risk.
