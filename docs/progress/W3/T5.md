## What changed

- **`dev/scenario.py`,** one file, Python standard library only ([dev-environment §5](../../specs/dev-environment-and-testing.md#5-isolated-parallel-scenarios)):
    - `up <scenario> [--id N]` reads `tests/scenarios/<scenario>.yaml`, checks free memory, claims the ID by creating `.scenarios/N/` (so two parallel `up` never get the same ID), checks that the ports `20000 + 100·N` to `+99` are free, creates the Docker network `spx-N`, then the scheduler's cluster. It prints one JSON object with the names, ports, data directory, URLs and credentials, and keeps a copy in `.scenarios/N/scenario.json`.
    - `slurm-*` scenarios: `dev/bootstrap.sh` into the data directory, then `dev/slurm/cluster.sh up <profile>` with `SIND_REALM=spx-N` and `SLURM_DATA=.scenarios/N`. The cluster keeps its profile name, so two `slurm-mini` scenarios both hold a cluster `mini`, in different realms.
    - `k8s-*` scenarios: `dev/k8s/cluster.sh up <profile>` with `CLUSTER=spx-N`, `KUBECONFIG=.scenarios/N/kubeconfig`, the API server on port `20000 + 100·N + 1`, and the nodes on the network `spx-N` (`KIND_EXPERIMENTAL_DOCKER_NETWORK`). The JSON gives the API URL and the kubeconfig path.
    - `down N` needs no state: it deletes the sind realm `spx-N` and the kind cluster `spx-N` if they exist, the network, and the data directory.
    - `list` prints the scenario files and the environments that are up.
- **`dev/k8s/cluster.sh`:** `KIND_API_PORT`, when set, fixes the API server port (kind `networking.apiServerPort`); otherwise unchanged. **`dev/slurm/cluster.sh`:** a header line on `SIND_REALM`; no code change.
- **Scenario files,** `tests/scenarios/happy-local.yaml`, `happy-slurm-mini.yaml`, `happy-k8s-mini.yaml`: the fields of §5 (`deployment`, `scheduler`, `engine`, `fixture`, `params`, `gate`, `expect`). Only `scheduler` is used today.
- **Unit tests,** `tests/scenarios/test_scenario.py` (8 tests): the names, ports and paths of an ID, that no two IDs share any of them, the ID range, the YAML subset and what it refuses, the field and value checks, and that every scenario file loads.
- **The proof,** `tests/scenarios/parallel.sh`, and the workflow `.github/workflows/scenarios.yml`: one job, on a push to any branch that touches its paths, nightly and on manual dispatch, with `permissions: {}` at the top and `contents: read` for the job, actions pinned by SHA as in `pipelines-k8s.yml`, `persist-credentials: false`, no `${{ }}` in `run:`, a 30-minute timeout. `ci.yml` does not call it.
- **Spec,** [dev-environment §5](../../specs/dev-environment-and-testing.md#5-isolated-parallel-scenarios): a "Built in T5" bullet that lists how the build differs; [§11](../../specs/dev-environment-and-testing.md#11-ci-workflows): the `scenarios.yml` row.

**Deferred until there is product code,** said plainly: `up` creates environments, it does not run a scenario.

- The Compose project `spx-N` is a reserved name and port range in the JSON. Nothing is started, because there is no Compose file and no Spectio server. Port `k = 0` waits for Spectio.
- `engine`, `fixture`, `params`, `gate` and `expect` are read and checked, not used: running the engine through the runner, the gate script and the expected events and states all need the runner and the gates.
- The matrix of §5 and its PR smoke subset, the `bundle` / `compose` deployment, and Apptainer.
- The T3 and T4 harnesses (`tests/slurm/scenarios.sh`, `tests/k8s/scenarios.sh`) are not wired to scenario IDs. The SLURM one already follows `SIND_REALM`, `CLUSTER` and `SLURM_DATA`; the Kubernetes one writes to `.scenarios/k8s/`.

## How to test

Unit tests, anywhere (a cloud session included):

```bash
python3 -m unittest discover -s tests/scenarios -p 'test_*.py'
```

The proof, on a machine whose Docker runs on cgroup v2, with Java 21 on `PATH`:

```bash
bash dev/bootstrap.sh && bash tests/scenarios/parallel.sh
```

By hand: `python3 dev/scenario.py up happy-slurm-mini --id 1`, then `sind --realm spx-1 exec mini -u spx -- sinfo`; `python3 dev/scenario.py list`; `python3 dev/scenario.py down 1`. A `local` scenario (`up happy-local`) needs only Docker and works in a cloud session: there it was run by hand as `--id 7`, listed, refused a second `up --id 7`, and `down 7` removed the network `spx-7` and `.scenarios/7/`.

## Findings and open questions

**Differences with §5,** for triage (the §5 "Built in T5" bullet records them):

1. **Compose project not started.** §5 has `up` create a Compose project; there is nothing to compose yet, so the name and ports are only reserved.
2. **kind on the scenario's network** needs `KIND_EXPERIMENTAL_DOCKER_NETWORK`, which kind 0.33.0 prints as "Here be dragons! This is not supported currently" ([`provider.go:72-76`](https://github.com/kubernetes-sigs/kind/blob/v0.33.0/pkg/cluster/internal/providers/docker/provider.go#L72-L76)). Without it, every kind cluster joins the shared network `kind`, which `kind delete cluster` never removes, so `down` would leave it behind. If kind drops the variable, the fallback is to accept the `kind` network as shared host state.
3. **A port inside the range is used by a cluster:** `k = 1` is the kind API server.
4. **IDs are 1 to 99,** a limit §5 does not state.
5. **The memory check** uses rough per-scheduler estimates and is not atomic across parallel `up`.
6. **Two `k8s-kueue` scenarios in parallel** would both download `.scenarios/kueue-<version>.yaml` (`dev/k8s/cluster.sh`): not tested, and a likely race.
7. **sind's address pools:** each realm's mesh and each cluster take one Docker network from the daemon's default pools, which a stock daemon fills at about 30 networks ([sind realms, v0.15.0](https://github.com/GSI-HPC/sind/blob/v0.15.0/docs/content/configuration/realms.md)). A `slurm-*` scenario takes three networks (`spx-N`, mesh, cluster), so about 10 at once on a stock daemon.
