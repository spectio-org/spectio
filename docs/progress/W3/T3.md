## What changed

The [spike t3-ci](../../research/spike-t3-ci-2026-10-28.md) proved the approach on a GitHub runner; this step keeps its scripts in durable form and widens the scope to the three profiles, every failure mode and slurmrestd.

- **Cluster profiles,** [dev-environment §4.1](../../specs/dev-environment-and-testing.md#41-slurm-with-sind): `dev/slurm/cluster.sh up mini|site|rest`, `down mini|site|rest`, with the sind configs `dev/slurm/site.yaml` and `dev/slurm/mini.yaml`.
    - `slurm-site`: controller, db (slurmdbd), submitter, `worker-[0-1]` in `htc`, `worker-2` in `bigmem`; accounts `lab` and `capped` (`MaxJobs=1`), `AccountingStorageEnforce=associations,limits`, `ConstrainRAMSpace=yes`, `SlurmdTimeout=45`.
    - `slurm-rest`: the same plus sind's `api` node (slurmrestd with JWT).
    - `slurm-mini`: controller, submitter, one worker in `htc`, no db.
    - The data directory `$SLURM_DATA` (default `.scenarios/slurm`, gitignored) is mounted into every node at its own path. The tools are installed into it by `dev/bootstrap.sh` (pins of `dev/versions.env`: sind 0.15.0, node image by digest), so the engines run on the submitter as on a login node.
- **Scenarios,** `tests/slurm/scenarios.sh`. Each prints a `RESULT` line, writes its fixtures and exits 1 on an unexpected outcome.
    - `nextflow[:IDS]`, `snakemake[:IDS]`: the unchanged harness `run_scenarios.py` on the submitter, `-profile test,slurm` or `--workflow-profile profiles/slurm`. After each scenario, the `squeue` and `sacct` records of its first task job that did not end `COMPLETED` become fixtures.
    - Each engine scenario must leave at least one Slurm job, and every scenario but `happy` at least one job that did not end `COMPLETED`; the fixture job is the first that failed by itself (`FAILED`, `OUT_OF_MEMORY`, `TIMEOUT`, `NODE_FAIL`), not one the engine cancelled. On `slurm-mini`, which has no accounting, the jobs are counted with `squeue` and only `happy` runs.
    - `probes`: a real OOM, a time limit, an association limit, two-CPU jobs that must pend with `Resources` and `Priority`, `PartitionTimeLimit`, `Dependency`, `DependencyNeverSatisfied`, `JobHeldUser`, `JobHeldAdmin` (`scontrol hold`), a maintenance reservation, `NODE_FAIL` by a power cut, and pending jobs cancelled by root, which must read `CANCELLED by 0`. Every one of these must appear.
    - `heads`: the Snakemake harness inside `sbatch --wait` on `bigmem`.
    - `rest`: a token from `scontrol token`, then `GET` of `ping` (`v0.0.43` to `v0.0.45`), `jobs`, `nodes`, `partitions` and `slurmdb/jobs`, each of which must answer 200; a call without a token must get 401; spx's token sent with `X-SLURM-USER-NAME: root` must not cancel a held job of root's.
- **CI,** `.github/workflows/pipelines-slurm.yml`, five parallel jobs: `nextflow` (five scenarios, then the probes), `snakemake-a` (`happy`, `flaky_retry`), `snakemake-b` (`oom_fatal`, `timeout_fatal`, `tool_error_then_fixed_resume`, then the head in `sbatch`), `rest`, `mini` (`happy`). It runs on a push to any branch that touches its paths, nightly and on manual dispatch, with `permissions: {}` at the top and `contents: read` for the job, no secrets, a 40-minute timeout, actions pinned by SHA and no `${{ }}` in `run:`. Fixtures go to the `slurm-fixtures-*` artifacts. `ci.yml` does not call it, so it is not part of `ci-ok`.
- **Fixtures,** `tests/fixtures/slurm/slurm-26.05.5/`: 24 JSON files, 382 kB, from the `slurm-fixtures-*` artifacts of run [40680736055](https://github.com/weber8thomas/spectio/actions/runs/40680736055). ## How to test

On a machine whose Docker runs on cgroup v2 (not a Claude Code cloud session), from the repository root:

```bash
export SLURM_DATA=$PWD/.scenarios/slurm SPECTIO_HOME=$PWD/.scenarios/slurm/tools \
  SPECTIO_BIN=$PWD/.scenarios/slurm/tools/bin UV_PYTHON_INSTALL_DIR=$PWD/.scenarios/slurm/tools/python
mkdir -p "$SLURM_DATA" && bash dev/bootstrap.sh && bash dev/slurm/cluster.sh up site && \
  for s in nextflow:happy,oom_fatal probes snakemake:oom_fatal heads; do CLUSTER=site bash tests/slurm/scenarios.sh "$s" || break; done
```

Java 17 or later must be on `PATH` or in `JAVA_HOME`: `up` copies it into the data directory. Fixtures land in `.scenarios/slurm/fixtures/`. `bash dev/slurm/cluster.sh down site` removes the cluster. For slurmrestd, `up rest` and `CLUSTER=rest bash tests/slurm/scenarios.sh rest`. In CI, push a change under `tests/slurm/`, or dispatch `pipelines-slurm.yml` once it is on `main`.

3. **Snakemake status polling** dominates small runs: note item 3. The test arguments keep 5 s.

5. **The pending reason in `--json` is split in two fields,** and `sacct` keeps the last pending reason on a finished job: note item 5. New detail: of the eleven probe jobs, only the maintenance one has a non-empty `state_description`; for `AssocMaxJobsLimit`, `Resources`, `Priority`, `PartitionTimeLimit`, `Dependency`, `DependencyNeverSatisfied`, `JobHeldUser` and `JobHeldAdmin`, `state_reason` alone carries the reason.

7. **`NODE_FAIL` has exit 1, `ERROR`:** note item 7. Confirmed.
8. **New: a Nextflow task over its `time` on SLURM ends `FAILED 140:0`, not `TIMEOUT`** (§3.5 `timeout`: "`TIMEOUT`"). Nextflow adds `--signal B:USR2@30` to every task job unless the user set `--signal` ([`SlurmExecutor.groovy:71-75` at v26.10.4](https://github.com/nextflow-io/nextflow/blob/v26.10.4/modules/nextflow/src/main/groovy/nextflow/executor/SlurmExecutor.groovy#L71-L75)), and the task wrapper traps `USR2` ([`command-run.txt:192`](https://github.com/nextflow-io/nextflow/blob/v26.10.4/modules/nextflow/src/main/resources/nextflow/executor/command-run.txt#L192)); 140 is 128 + 12 (`USR2`).
