## Why

Prompt: [next-phase.md · P3](../../playbooks/next-phase.md#p3-execution). Step: `P3` in `docs/playbooks/pipeline.yaml` (wave W5, `kind: build`). [P2 §2](../../plans/P2-execution.md#2-m2-heads) starts Task 8 as soon as Task 2 (the store) is merged, beside Tasks 3 to 7; Task 9 needs its `Settings`.

**Task 8:**

- **The first command a user runs.** `spectio open` runs `spectio init` on first use, unattended (dev-env §15.3), so every option has a default and nothing prompts. The defaults are the split of "Where data lives": the data directory in the shared home, the database in a node-local temporary directory, the runs on the shared file system.
- **The engines run as the user runs them.** On a login node the engines come from modules or a conda environment. So `init` finds them through the login shell, with Spectio's own environment cleared (P1 Assumptions 13 and 14), and records the command.
- **A shared temporary directory is hostile ground.** Another user can create `$TMPDIR/spectio-<uid>` first. The store of Task 2 answers that with a `mkdtemp` fallback; round 1 found that recording the default in `spectio.toml` turned that fallback off (SEC-P3T08-01 (r1), [record](../../reviews/code/P3-t08.md)).
- **`spectio.toml` holds commands that run.** `doctor` runs the engine commands through `bash -lc`, and the head script will. So its directory must be the user's at 0700 (req. 5), and a render that would not load never replaces it (SEC-P3T08-02 (r2), SEC-P3T08-05 (r2)). Its own owner and mode are checked in P1 Task 15 (SEC-P3T08-03).
- **Local mode is Linux only in 0.0.1** ([inbox #73](../../reviews/inbox.md#73-assumed-spectio-init-local-refuses-to-run-off-linux), confirmed by Thomas), whatever layer asks for it (CR-P3T08-02 (r2)).

**Task 9:**

- **The first code that runs an engine.** Task 9 turns a `launch` command into a running head, and a `cancel` into signals. [P2 §2](../../plans/P2-execution.md#2-m2-heads) item 4 names it a security boundary (Review Focus 1 and 4, §15.3 Launch): the head script is shell, and its values come from a launch request.
- **The head outlives the server.** A login node's server stops and starts again; the head must not stop with it (schedulers §3.1.1, decided, inbox #35). So the head runs in its own session, writes its own PID and exit files, and the next server adopts it from them.
- **A signal must reach the right process.** PIDs are reused, and a run directory is on a shared disk. So a signal goes only to a head whose `head.pid` still names the same PID, start time, boot and host, and that leads its own group (§15.3 req. 11). Rounds 3 and 4 found three ways a stale or reused PID could be signalled (SEC-P3T09-02 (r3), SEC-P3T09-04 (r4), SEC-P3T09-08 (r4)).
- **The bridge runs inside every head.** nf-spectio is loaded by each Nextflow run of the user. A copy that someone else can write would run their code there, so the copy must be private (SEC-P3T09-06 (r4), CR-P3T09-R5-01).
- **The engines run as the user runs them.** The head clears Spectio's environment and runs the engine through `bash -l`, as `spectio init` found it (P1 Assumptions 13 and 14).
