### Task 25 · Pointer file in both bridges; the server finds and shows the run

Branch `autopilot/P3-t25`, base `232b399`, code head `d5e2193`; 6 commits, 42 files, +2447 −190 (of which `packages/*/src` +821 −87, the tests of `packages` and `engine-bridges` +1279 −19, the two bridges +307 −69, `web/` +22 −13). The behaviour is owned by [architecture §13.8](../../specs/architecture-plugins-and-packaging.md#138-runs-started-from-a-terminal) and [dev-env §15.3](../../specs/dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts) req. 12.

- **The bridges write a pointer.** Started with no `SPECTIO_*` variable, each bridge makes a run ID, writes its spool in `<launch dir>/.spectio/events/` under the terminal names, then `~/.spectio/observed/<run ID>.json` (0600, temporary name then rename). The pointer holds the run ID, launch directory, engine, versions, host and the PID fields of the head, and no environment or parameters. Every write is relative to a directory the bridge checked. With no `~/.spectio`, nothing is written and nothing is said; the run never fails. `run_local.sh --terminal` starts such a run.
- **The server finds it.** The runner scans `observed/` when its mtime changes, checks each pointer (symlink, owner, mode, size, strict schema, name equal to run ID, launch directory outside the runs root), adds the run with origin `cli-observed`, reads its spool, and moves the pointer to `observed/ended/` at the end. A rebuild reads `observed/` then `ended/`, so a run keeps its ID. Migration `0009_terminal_head` adds `launches.head_host`.
- **The screens say what is checked.** `GET /runs/{id}` gains `head.checked`: true only when the pointer's host name and boot ID are the server's (one `checkable` for the runner and the API). The run header says "Not checked (on <node>, started from a terminal)" otherwise. No Cancel, and a launch or cancel command for such a run is answered `failed` before any launcher is called.
- **A Snakemake terminal run ends from its spool** *(assumed, [inbox #113](../../reviews/inbox.md#113-assumed-how-a-snakemake-run-started-from-a-terminal-ends-p3-task-25) rule 1)*. Snakemake writes no terminal event and there is no exit code. When the head is seen gone (same host and boot), the run is `succeeded` if the last progress has done == total, no task failed and no error came after it; otherwise `failed`, `engine_fault`, "assumed" in the message. A Nextflow terminal run ends on its terminal event.
- **The workflow of a terminal run is its launch directory**, one engine per location *(assumed, inbox #113 rule 2)*: a Snakemake run in a directory that holds a Nextflow run is not shown.
- **File-system work is bounded.** The first build ran `realpath` of a pointer's directory inside the writer's transaction (SEC-P3T25-01 (r1), major). Now the writer checks the text only; the runner checks the resolved path in a file pool of its own with the read timeout, and a launch directory with a read in flight is not read again (CR-P3T25-03 (r2), major).
- **Inbox #109 rule 5 (a).** `NO_API` says the API is served only in local mode, on a machine only the user uses, because on a shared host other users could reach its port. The SLURM start text shows it too.
- **Review fixes** (the [record](../../reviews/code/P3-t25.md) has all of them, with the round): the blocker CR-P3T25-01 (r1) (the Snakemake end, above); the two majors above; the single "checked" test (CR-P3T25-05 (r1), SEC-P3T25-04 (r1)); the SLURM start text (CR-P3T25-04 (r2)); the one-shot claim that frees a busy file key (CR-P3T25-01 (r3)).
- **Spec and inbox:** notes of 2026-11-07 in [architecture §13.8](../../specs/architecture-plugins-and-packaging.md#138-runs-started-from-a-terminal) (Discovery and Its end), [dev-env §15.3 req. 12](../../specs/dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts) and [api §14.1](../../specs/api-and-data-model.md#141-driven-runs-001) (the terminal names, out of date since this step) and §5 (`head.checked`); [inbox #113](../../reviews/inbox.md#113-assumed-how-a-snakemake-run-started-from-a-terminal-ends-p3-task-25), assumed. ## Why

Prompt: [next-phase.md · P3](../../playbooks/next-phase.md#p3-execution). Step: `P3` in `docs/playbooks/pipeline.yaml` (wave W5, `kind: build`). [P2 §6](../../plans/P2-execution.md#6-m6-runs-from-a-terminal) lists M6 as Tasks 25 and 26, run in parallel and not waiting for M5.

- **0.0.1 also monitors runs that people start by hand** *(Thomas, 2026-10-28, [decision log](../../decisions/log.md#2026-10-28-001-also-monitors-runs-started-from-a-terminal-bridges-published-in-the-engines-catalogues))*. The server never started such a head, so it can neither signal it nor read its exit code. That is why the task is monitor only, and why the end of a Snakemake run is an assumption.
- **A pointer and a launch directory are input from other people.** The launch directory is often group-writable (architecture §13.8), so [req. 12](../../specs/dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts) applies to every read, and [P2 §6](../../plans/P2-execution.md#6-m6-runs-from-a-terminal) item 4 names Task 25 a security boundary. The reviewers found the writer stall (`security-reviewer`) and the stuck-pool starvation (`code-reviewer` and `security-reviewer`), which tests of the happy path did not show.
