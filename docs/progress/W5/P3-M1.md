## Why

Prompt: [next-phase.md · P3](../../playbooks/next-phase.md#p3-execution). Step: `P3` in `docs/playbooks/pipeline.yaml` (wave W5, `kind: build`). [P2 §1](../../plans/P2-execution.md#1-m1-events-in) runs Task 1 alone first, because it creates the workspace and the CI job that every later task uses.

- **The contract comes before its code.** Inbox #36 (a) let api §14 own the ingest contract and left its driven-run part for a later pass ([decision log](../../decisions/log.md#2026-10-29-api-14-driven-run-part-written-inbox-36-a)). [dev-env §15.3](../../specs/dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts) req. 6 needs that format to say what "validated and size-capped" means. P1 Task 1 writes it, as the spec of the first product code.
- **Allow-lists, not deny-lists.** Each event type keeps only the keys it lists. A field that a newer bridge adds is dropped until the list names it. This applies P1 Assumption 3: no `script`, `env` or command line is stored *(assumed — pending Thomas, [inbox #55](../../reviews/inbox.md#55-what-engine-events-may-carry-task-script-and-env-user-host-and-command-line))*.
- **The numbers** (64 KiB line, rotation at 32 MiB, 64 MiB per file) are P1 Assumption 12 *(assumed — pending Thomas, [inbox #28](../../reviews/inbox.md#28-assumed-engine-bridges-runner-and-scheduler))*.

**Task 2** runs after Task 1, in one of four parallel worktrees: 2 → 4 → 5, beside 3, 6 and 7 ([P2 §1](../../plans/P2-execution.md#1-m1-events-in)). The projector (Task 4) needs it, and Task 8 (M2) may start once it is merged.

- **The database is an index, not the source of truth.** It lives in a node-local temporary directory, and boot rebuilds it from the run directories when it is new ([dev-env §15.3](../../specs/dev-environment-and-testing.md#153-001-on-a-cluster-architecture-and-safety-without-accounts), "Where data lives", *(assumed — pending Thomas, inbox #64)*). Hence `default_db_dir()`, and the `created` flag of `open_db`.
- **A shared temporary directory is hostile ground.** Another user can create `spectio-<uid>` first, or swap a directory or a link between a check and a use. The checks of the figure answer the security review's majors: SEC-P3T2-01, -02, -03, -09 and -13 ([record](../../reviews/code/P3-t02.md)).
- **SQLite needs one writer and a local disk** ([architecture §7.2](../../specs/architecture-plugins-and-packaging.md#72-infrastructure-per-deployment), which cites sqlite.org): one writer with `BEGIN IMMEDIATE`, a refusal on a network file system, and the WAL-reset fix of [api §7](../../specs/api-and-data-model.md#7-database-schema).

**Task 3** runs beside Tasks 2, 6 and 7, after Task 1 ([P2 §1](../../plans/P2-execution.md#1-m1-events-in)). The projector (Task 4) consumes its batches.

- **Req. 6 says "validated and size-capped"; the reader is where that happens.** Task 1 fixed the format and the line and file caps. The reader applies them, and Task 1's review handed it the rest: the name grammar, `wrong_launch`, a cap on unended lines and on the number of files (SEC-P3T1-04), and a check of the import contracts in a fresh environment (SEC-P3T1-06) ([record](../../reviews/code/P3-t01.md)).
- **The spool sits on a shared file system.** The runner reads it from the login node while the bridges write it, and a project directory is often group-writable ([architecture §13.8](../../specs/architecture-plugins-and-packaging.md#138-runs-started-from-a-terminal)). So the reader trusts no path below the launch directory: it opens by descriptor, checks the owner and the mode, and counts what it refuses. This answers the security review's majors, SEC-P3T3-01 (a bounded cost per read) and SEC-P3T3-02 (owner and mode) ([record](../../reviews/code/P3-t03.md)).
- **Counted once, through the cursor.** The caller stores the events, the cursor and the counts in one transaction (P1 Assumption 11), so a refused file is marked in the cursor and is not counted again on the next read.

**Task 4** runs after Tasks 2 and 3 ([P2 §1](../../plans/P2-execution.md#1-m1-events-in)). Task 5 (the Snakemake mapping) adds its branch to `ingest`; Tasks 9 to 11 call `ingest` and `apply_head_report`.

- **The database is a projection of the log.** api §8.1 makes the event log the source and the run, task and attempt rows its projection. `ingest` writes both in one transaction, so `projected_seq` always equals `last_seq` (P1 Assumption 11), and a replay of the same batch changes nothing.
- **Order is not arrival.** Spooled events can arrive late or twice, and Nextflow 25.10.9 sent `onFlowComplete` twice in one run ([api §8.2](../../specs/api-and-data-model.md#82-ordering-cursors-and-clocks)). Hence the lattice: attempt states move forward only, a terminal run never moves, and a second end is only logged.
- **One bad event must not stop a run.** A spool line is untrusted (dev-env §15.3 req. 6). Round 1 found that one malformed `trace.exit` blocked a run's projection for good (SEC-P3T04-01 (r1)); hence one savepoint per event.
- **The projector holds the one writer.** Round 2 measured 24.75 s for one `onFlowComplete` on a 20k-task run (CR-P3T04-03 (r2)); hence the two indexes ([record](../../reviews/code/P3-t04.md)).
