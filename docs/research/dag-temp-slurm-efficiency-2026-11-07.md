## 1. What the bridges already carry

- **Snakemake logger plugin.** It turns each typed record into `snakemake.<event>` with an allow-list per event, and every untyped record into `snakemake.log` with its level only. One text is parsed: the SLURM plugin's submission line, into `snakemake.slurm_submitted` (`SLURM_SUBMITTED`, `to_events`). `job_info` keeps `is_checkpoint`, `threads`, `reason` and `resources` (a `Namedlist` made a map), minus `slurm_extra` (SEC-P3T1-11). `rulegraph` and `run_info` are kept.
- **nf-spectio.** It sends `onProcessCreate` and `onProcessTerminate` with the process name, and each task event with the task fields. The trace record is sent whole (its allow-list, `TRACE_KEYS`) only with `onTaskComplete`, `onTaskCached` and `onFlowError`; the other task hooks send only `native_id` and `workdir` (`WHERE_KEYS`). `enableMetrics()` returns `true`, so finished tasks carry `realtime`, `%cpu` and `peak_rss`. `onFlowCreate` sends `nextflow`, `resume` and `workDir`.

## 2. Snakemake: checkpoints, conditional rules, rules that never run

1. **Typed events.** The logger interface has 14 events: `RUN_INFO`, `WORKFLOW_STARTED`, `SHELLCMD`, `JOB_INFO`, `JOB_ERROR`, `JOB_STARTED`, `JOB_FINISHED`, `GROUP_INFO`, `GROUP_ERROR`, `RESOURCES_INFO`, `DEBUG_DAG`, `PROGRESS`, `RULEGRAPH`, `ERROR` (interface 2.1.0, `common.py:33-47`). None marks a DAG update, a temporary file or a job that will not run.
2. **A checkpoint job.** `JOB_INFO` carries `is_checkpoint=self.rule.is_checkpoint` ([`jobs.py:1096`](https://github.com/snakemake/snakemake/blob/v9.27.1/src/snakemake/jobs.py#L1096)); right after it, for a checkpoint rule, the untyped text "DAG of jobs will be updated after completion." ([`jobs.py:1106-1107`](https://github.com/snakemake/snakemake/blob/v9.27.1/src/snakemake/jobs.py#L1106-L1107)). So the rule is known as a checkpoint only once its first job is logged.
3. **The DAG update.** After a checkpoint job finishes, `update_checkpoint_dependencies` logs the untyped text "Updating checkpoint dependencies." only when jobs depend on it ([`dag.py:2217-2245`](https://github.com/snakemake/snakemake/blob/v9.27.1/src/snakemake/dag.py#L2217-L2245)). The docs: "Snakemake allows to re-evaluate the DAG after the successful execution of every job spawned from a checkpoint" ([Rules, data-dependent conditional execution](https://snakemake.readthedocs.io/en/stable/snakefiles/rules.html#data-dependent-conditional-execution)). The new total arrives with the next `PROGRESS` (`scheduling/job_scheduler.py:659`), as spike T2 saw (32 → 67 jobs in 12 steps; [T2 note](spike-engine-events-2026-10-28.md#differences-with-the-specs), row 18).
4. **Per-rule plan.** `RUN_INFO.stats` counts, per rule, the jobs that need to run plus those finished ([`dag.py:3252-3279`](https://github.com/snakemake/snakemake/blob/v9.27.1/src/snakemake/dag.py#L3252-L3279)). It is logged once, when the run starts ([`workflow.py:1475-1479`](https://github.com/snakemake/snakemake/blob/v9.27.1/src/snakemake/workflow.py#L1475-L1479)); it is not logged again after a checkpoint (*inferred*: no other call site for the run case). So after a checkpoint the per-rule counts are stale and only the total grows.
5. **The rule graph.** `RULEGRAPH` is built once from every job of the start DAG, `self.dag.toposorted()` over `dag.jobs` ([`workflow.py:1222-1272`](https://github.com/snakemake/snakemake/blob/v9.27.1/src/snakemake/workflow.py#L1222-L1272)), and `dag.jobs` is "All jobs in the DAG", those that need to run or not ([`dag.py:641-650`](https://github.com/snakemake/snakemake/blob/v9.27.1/src/snakemake/dag.py#L641-L650)). So a rule whose jobs are all up to date is in the rule graph and absent from `RUN_INFO.stats` (*inferred*). Rules created behind a checkpoint are in neither.
6. **Rules that never run.** A rule that no target needs is not in the DAG, and nothing is logged for it. Input functions and `branch()` ([`ioutils/branch.py:5-40`](https://github.com/snakemake/snakemake/blob/v9.27.1/src/snakemake/ioutils/branch.py#L5-L40); [Rules, the branch function](https://snakemake.readthedocs.io/en/stable/snakefiles/rules.html#snakefiles-branch-function)) decide inputs while the DAG is built, so a rule they leave out is simply absent. Spectio already has the list of defined rules: `snakemake --list-rules` into `.spectio/rules.txt`, or the rule files ([ui-spec §5.1.1](../specs/ui-spec.md#511-detected-stages), note 2026-10-31). A defined rule absent from the rule graph, from `RUN_INFO` and from every `JOB_INFO` is therefore "not needed in this run", unless a checkpoint is still open.
7. **"Nothing to be done".** With nothing to run, Snakemake logs `NOTHING_TO_BE_DONE_MSG`, "Nothing to be done (all requested files are present and up to date).", and no `RUN_INFO` ([`workflow.py:1481`](https://github.com/snakemake/snakemake/blob/v9.27.1/src/snakemake/workflow.py#L1481), `common/__init__.py:30-31`).
8. **`DEBUG_DAG`** records come only through `logger.debug` while the DAG is built (`dag.py:1190`, `1281`, `1287`, `1370`): candidates and selected producers, not "will not run". The plugin keeps them out (no allow-list).

## 3. Snakemake: `temp()`, `protected()`, `directory()`

1. **The docs.** "A protected file will be write-protected after the rule that produces it is completed. Further, an output file marked as temp is deleted after all rules that use it as an input are completed" ([Rules, protected and temporary files](https://snakemake.readthedocs.io/en/stable/snakefiles/rules.html#protected-and-temporary-files)). Checkpoint outputs read through `checkpoints.<rule>.get()` are not marked temporary ([data-dependent conditional execution](https://snakemake.readthedocs.io/en/stable/snakefiles/rules.html#data-dependent-conditional-execution)).
2. **The flags are not in the events.** `JOB_INFO` sends `output=format_files(self.output, as_output=True)` ([`jobs.py:1083`](https://github.com/snakemake/snakemake/blob/v9.27.1/src/snakemake/jobs.py#L1083)); `fmt_iofile` annotates only `pipe`, `service`, `nodelocal`, `update`, `before update`, `access` and storage, and returns a checkpoint target as `<TBD>` (`io/fmt.py:5-53`). `temp`, `protected` and `directory` are not shown.
3. **Deletion.** `handle_temp` removes, after each job, the temp outputs of its dependencies that no job still needs, and the job's own temp outputs unless it is a checkpoint or a target ([`dag.py:1013-1056`](https://github.com/snakemake/snakemake/blob/v9.27.1/src/snakemake/dag.py#L1013-L1056)). Each removal logs the untyped text `Removing temporary output <path>.` (`dag.py:1054-1056`), "Would remove temporary output <path>" in a dry run (`1048-1051`). Spike T2 saw each line logged twice ([T2 note](spike-engine-events-2026-10-28.md#differences-with-the-specs), row 19). With `--notemp` nothing is removed and only a debug line is logged (`dag.py:1015-1017`; options `notemp` and `all_temp`, `settings/types.py:242-243`).
4. **Protected.** `handle_protected` logs `Write-protecting output file <path>.` for each `protected()` output (`dag.py:932-936`).
5. **Directories.** A `directory()` output carries no mark in the events; Spectio can only see it is a directory when it reads the path.

## 4. Nextflow: conditional execution and processes that never run

1. **`when:`.** "The when section allows you to define a condition that must be satisfied in order to execute the process"; it is "Deprecated in version 26.10": "Implement conditional logic in the calling workflow (e.g. an if statement or filter operator), or use the process.when config setting to disable a process at runtime" ([Processes, When](https://docs.seqera.io/nextflow/process#when)).
2. **A task that fails its `when:`.** `TaskProcessor` builds the task, then `checkWhenGuard` returns `false` and the task is finalised without submission ([`TaskProcessor.groovy:692-694`](https://github.com/nextflow-io/nextflow/blob/v26.10.4/modules/nextflow/src/main/groovy/nextflow/processor/TaskProcessor.groovy#L692-L694), [`1908-1922`](https://github.com/nextflow-io/nextflow/blob/v26.10.4/modules/nextflow/src/main/groovy/nextflow/processor/TaskProcessor.groovy#L1908-L1922)); `finalizeTask0` binds outputs and counts the task as completed, and notifies no observer ([`1986-1997`](https://github.com/nextflow-io/nextflow/blob/v26.10.4/modules/nextflow/src/main/groovy/nextflow/processor/TaskProcessor.groovy#L1986-L1997)). So no event reaches `nf-spectio`, and Spectio cannot count the filtered tasks.
3. **A process with no task.** Its `onProcessCreate` came at the start, and `onProcessTerminate` comes when its inputs close (`TaskProcessor.groovy:2006`, `Session.groovy:1228-1230`) with no task between: `when:` false, `ext.when`, or an empty input channel. After a fatal error, processes downstream may never terminate (T2, row 2; [checking-scenarios §11.5](../specs/checking-scenarios.md#115-limits)).
4. **A process behind a Groovy `if`.** It is never invoked, so never created: no `onProcessCreate` and no name ([stage-detection spike](spike-stage-detection-2026-10-28.md#nextflow-where-the-stage-information-is); [ui-spec §5.1.1](../specs/ui-spec.md#511-detected-stages)). Spectio cannot list it without reading the script.

## 5. Nextflow: temporary files

1. **No per-output temporary marker.** The `path` output options are `arity`, `followLinks`, `glob`, `hidden`, `includeInputs`, `maxDepth` and `type` ([inputs and outputs](https://docs.seqera.io/nextflow/reference/process/inputs-outputs)).
2. **`cleanup`.** "Delete all files associated with a run in the work directory when the run completes successfully (default: false)"; it "will prevent the use of the resume feature" and "is not supported for remote work directories" ([unscoped config, `cleanup`](https://docs.seqera.io/nextflow/reference/config/unscoped)). In the code it is a boolean, skipped when the run was aborted, cancelled or failed, and it deletes each task directory recorded in the cache ([`Session.groovy:1375-1410`](https://github.com/nextflow-io/nextflow/blob/v26.10.4/modules/nextflow/src/main/groovy/nextflow/Session.groovy#L1375-L1410)). It runs in `ScriptRunner.shutdown`, after `session.destroy()` ([`ScriptRunner.groovy:260-265`](https://github.com/nextflow-io/nextflow/blob/v26.10.4/modules/nextflow/src/main/groovy/nextflow/script/ScriptRunner.groovy#L260-L265)), so after the observers' last events (*inferred*): `nf-spectio` cannot report it, but it can send the setting at `onFlowCreate`.

## 6. Requested SLURM parameters per job

**Snakemake with the SLURM plugin 2.8.0.**
- The resources map to `sbatch` flags in `get_submit_command` ([`submit_string.py:73-213`](https://github.com/snakemake/snakemake-executor-plugin-slurm/blob/v2.8.0/snakemake_executor_plugin_slurm/submit_string.py#L73-L213)): `runtime` → `-t`, `constraint` → `-C`, `qos` → `--qos`, `mem_mb_per_cpu` → `--mem-per-cpu`, else `mem_mb` → `--mem`, `nodes` → `--nodes`, `tasks` → `--ntasks` (1 by default), `cpus_per_task` → `--cpus-per-task`, else `threads` (jobstep 0.6.1 `get_cpu_setting`, `__init__.py:277-307`), `slurm_extra` appended raw (`submit_string.py:200-201`), `clusters`/`cluster`/`slurm_cluster` → `--clusters`. `gres` and `gpu`/`gpu_model` go through `set_gres_string` (`utils.py:339-390`). The docs' table names `slurm_account` → `--account` and `slurm_partition` → `--partition` ([catalogue page](https://snakemake.github.io/snakemake-plugin-catalog/plugins/executor/slurm.html)).
- **The effective account and partition may not be in `resources`.** Without `slurm_account`, the plugin warns "No SLURM account given, trying to guess." and uses a guessed account (`__init__.py:1626-1670`); without `slurm_partition` and with a partitions file, it picks the "best" partition (`__init__.py:1675-1720`, `get_best_partition`). `--slurm-qos` and `--slurm-reservation` are executor settings, not job resources (`submit_string.py:146-151`). So `job_info.resources` gives the rule's request; what SLURM ran with comes from `sacct`.
- **Naming.** Job name is the run's UUID, with `--slurm-jobname-prefix` in front; the comment is `rule_<rule>` or `rule_<rule>_wildcards_<wildcards>` (`__init__.py:472-495`, `1095-1103`). "Human readable information is stored in the comment of a particular job" ([catalogue page](https://snakemake.github.io/snakemake-plugin-catalog/plugins/executor/slurm.html)).
- **The plugin's own efficiency report** (`--slurm-efficiency-report`, at the end of the run only): `sacct --name=<run_uuid> --parsable2 --noheader --format=JobID,JobName,Comment,Elapsed,TotalCPU,NNodes,NCPUS,MaxRSS,ReqMem`, drops `batch` and `extern` rows, keeps the numbered steps, CPU efficiency = TotalCPU / (Elapsed × NCPUS) × 100, memory usage = MaxRSS / requested memory × 100, written to `efficiency_report_<run_uuid>.csv` ([`efficiency_report.py:44-171`](https://github.com/snakemake/snakemake-executor-plugin-slurm/blob/v2.8.0/snakemake_executor_plugin_slurm/efficiency_report.py#L44-L171)). It reads the rule name from `Comment`, which `sacct` shows only "when the AccountingStoreFlags parameter in the slurm.conf file contains 'job_comment'" ([`sacct(1)`](https://slurm.schedmd.com/sacct.html), Comment).
- **Measured values from the rule itself.** A `benchmark:` file has the columns `s`, `h:m:s`, `max_rss`, `max_vms`, `max_uss`, `max_pss`, `io_in`, `io_out`, `mean_load`, `cpu_time` ([`benchmark.py:28-40`](https://github.com/snakemake/snakemake/blob/v9.27.1/src/snakemake/benchmark.py#L28-L40)).

**Nextflow with the SLURM executor.**
- `getDirectives` writes `-J`, `-o .command.log`, `--no-requeue`, `--signal B:USR2@30`, `-c <cpus>` when above 1, `-t <time>`, `--mem` or `--mem-per-cpu`, `-p <queue>`, the `clusterOptions`, and `-A <executor.account>` ([`SlurmExecutor.groovy:57-112`](https://github.com/nextflow-io/nextflow/blob/v26.10.4/modules/nextflow/src/main/groovy/nextflow/executor/SlurmExecutor.groovy#L57-L112); `executor.account` is "Used only by the SLURM, LSF, PBS/Torque and PBS Pro executors", [`executor` config](https://docs.seqera.io/nextflow/reference/config/executor)). The `accelerator` directive is not turned into a SLURM flag there; GPUs on SLURM come through `clusterOptions` (*inferred* from the absence in `getDirectives`).
- Every trace record carries the request, from submission on: `queue`, `cpus`, `memory`, `disk`, `time`, `accelerator`, `accelerator_type`, `attempt` ([`TaskHandler.groovy:203-231`](https://github.com/nextflow-io/nextflow/blob/v26.10.4/modules/nextflow/src/main/groovy/nextflow/processor/TaskHandler.groovy#L203-L231)). `nf-spectio` cuts that record to `native_id` and `workdir` on every hook but the final ones, so the request reaches Spectio only when the task ends. The account and `clusterOptions` are not in the trace.
- **Measured.** `realtime` is the "Wall-clock time of the task script", `%cpu` the "Percentage of CPU used by the task, relative to a single CPU" (four busy CPUs ≈ 400 %), `peak_rss` the "Peak of real memory", from `VmHWM` ([`trace` config](https://docs.seqera.io/nextflow/reference/config/trace)).

## 7. SLURM accounting: the job ID, the fields, efficiency

- **Job ID ↔ `sacct`.** Snakemake: the ID of each submission is in the plugin's info text "Job <jobid> has been submitted with SLURM jobid <id> (log: <path>)." (`__init__.py:1224-1227`), which the logger plugin turns into `snakemake.slurm_submitted`, and in `job_error.aux.external_jobid`; an array element is `<id>_<index>` (`__init__.py:1032-1036`). Nextflow: the trace's `native_id`, `<id>_<n>` for an array element ([architecture §13.7](../specs/architecture-plugins-and-packaging.md#137-log-sources-per-engine)). `sacct -j <id>` accepts `JobID[.JobStep]` and `ArrayJobID_ArrayTaskID` ([`sacct(1)`](https://slurm.schedmd.com/sacct.html), JobID). The rows of one job are the allocation, `<id>.batch`, `<id>.extern` and one per `srun` step.
- **Fields** ([`sacct(1)`](https://slurm.schedmd.com/sacct.html)): `TotalCPU` "The sum of the SystemCPU and UserCPU time used by the job or job step"; for steps interrupted by a signal (scancel, timeout) it "may not include CPU time of child processes". `Elapsed` "The job's elapsed time". `NCPUS` "Total number of CPUs allocated to the job. Equivalent to AllocCPUS." `MaxRSS` "Maximum resident set size of all tasks in job" (per step). `ReqMem` "Minimum required memory for the job … This value is only from the job allocation, not the step." `Timelimit`, `Partition` ("the partition on which the job ran"), `Account`, `QOS`, `ReqTRES` and `AllocTRES` (the GPUs and other TRES), `NNodes`.
- **What `seff` computes** ([`seff`](https://github.com/SchedMD/slurm/blob/master/contribs/seff/seff), lines 71-81, 97-147, 170-193): CPU efficiency = the sum of every step's CPU time / (elapsed × allocated CPUs); memory efficiency = the largest per-step memory total (`tres_usage_in_tot`, "the sum of memory peaks of all tasks") / the requested memory (`tres_req_str`, × nodes when requested per node). On a running job it prints "WARNING: Efficiency statistics can only be obtained after the job has ended as seff tool is based on the accounting database data." (lines 199-201); on a pending one, "Efficiency not available for jobs in the PENDING state." (line 203).
- **So:** efficiency from accounting exists only after the job ends. During the job Spectio can show the request, the elapsed time against the limit, and nothing measured; `sstat` reads running steps, a later option **[to be validated]**.

## 8. What the engines cannot give (gaps)

| Gap | Engine | Consequence for Spectio |
|---|---|---|
| No typed DAG-update event; only untyped texts | Snakemake | the logger plugin parses two fixed texts, with a pattern versioned per Snakemake release |
| `RUN_INFO` per-rule counts are not re-sent after a checkpoint | Snakemake | rules behind a checkpoint appear with their first job; totals read "at least N" until the checkpoint has run |
| A rule is known as a checkpoint only from its first `JOB_INFO` | Snakemake | Spectio may mark it earlier from the rule files it already reads (`checkpoint <name>:`), *inferred* parser rule |
| No event for a rule left out of the DAG | Snakemake | "not needed" is derived: defined rules minus rule graph, `RUN_INFO` and jobs seen |
| `temp`, `protected`, `directory` flags are not in `JOB_INFO` | Snakemake | a temporary output is known only when its deletion text arrives; before that it is a plain output |
| No event for a task filtered by `when:` | Nextflow | no count of filtered tasks; a process with no task between create and terminate reads "no task" |
| A process behind a Groovy `if` is never created | Nextflow | it is absent from the list; only a static read of the script would show it (later) |
| No per-output temporary marker; `cleanup` runs after the last observer event | Nextflow | the setting is sent at `onFlowCreate`; files gone after success read "removed by `cleanup = true`" |
| Effective partition, account and QOS may differ from the request | both | the effective values come from `sacct` (or `squeue`, not polled for task jobs in 0.0.1) |
| `slurm_extra` and `clusterOptions` are raw `sbatch` text | both | not sent (SEC-P3T1-11); their effect shows in the `sacct` values |
| Accounting efficiency needs the job to end | SLURM | before: request, elapsed against the limit; Nextflow's trace and Snakemake's benchmark give measures at job end without `sacct` |
| `Comment` needs `AccountingStoreFlags=job_comment` | SLURM | Spectio keys jobs by ID, not by comment |
