# Spike t3-ci: T3 on a GitHub-hosted runner (2026-10-28)

**Question.** Can pipeline step T3 (mini SLURM with sind, [next-phase.md](../playbooks/next-phase.md#t3-mini-slurm-with-sind)) be done **CI-driven on GitHub-hosted runners**, as option (b) of [inbox #51](../reviews/inbox.md#51-t3-and-t4-cannot-run-in-a-claude-code-cloud-session-where-do-they-run) proposes? A Claude Code cloud session cannot run sind itself: its cgroup layout is hybrid v1 ([spike D2](spike-cloud-env-2026-10-26.md#result)). In order:
1. Does a sind cluster shaped like `slurm-site` (two partitions, slurmdbd) come up in a GitHub Actions job?
2. Do the synthetic pipelines run on it through `run_scenarios.py`: Nextflow `-profile slurm` and Snakemake `--workflow-profile profiles/slurm`, `happy` and one failure scenario per engine?
3. Can `squeue --json`, `sacct --json` and `sinfo --json` of a failed job be printed in the job log, size-limited and fenced, and extracted back as fixtures?
4. If time allows: `NODE_FAIL` by a power cut; a Snakemake head submitted with `sbatch`; a maintenance reservation and an association limit as pending reasons.

**Answer in one line.** **Yes, all four.** The fourth and last run is green in **14 min 32 s** of wall-clock time on a free runner. One loop costs about 15 minutes for the whole set, or about 3 to 6 minutes for a single scenario. The fixtures come back through the log byte-exact: each block's sha256 is checked. The spike also found **7 differences** with the specs and the harness (below).

**Step page:** none. This is a spike for inbox #51, not T3: no step is marked done, and `pipeline.yaml`, `docs/specs/` and the inbox are unchanged. Branch `spike/t3-ci` only. Time box: about 90 minutes, 4 push iterations.

### Fixtures through the log

- `fixture.py NAME --jobs IDS` keeps only the listed jobs (by `job_id` or array job id), indents the JSON (short lines survive the log), caps it at 48 KiB by dropping list entries from the end (then sets `_spike_truncated`), and prints:

  ```text
  ----- BEGIN SPECTIO FIXTURE name=sacct-probes bytes=40557 sha256=… -----
  { …indented JSON… }
  ----- END SPECTIO FIXTURE name=sacct-probes -----
  ```

- `extract_fixtures.py LOG OUT_DIR` strips the timestamp GitHub puts on each log line, rebuilds each block, and writes it only if its sha256 matches. On the logs of runs 2, 3 and 4 (downloaded with `gh api repos/{owner}/{repo}/actions/jobs/{id}/logs`) every block came back intact: 3, 10 and 10 blocks, 7–41 KB each, none truncated.
- Run 4 carries ten: `nextflow-{squeue,scontrol-job,sacct}-failed-task`, `snakemake-{…}-failed-task`, `sinfo`, `sinfo-node-down`, `squeue-pending-reasons` (three jobs: running, `AssocMaxJobsLimit`, `ReqNodeNotAvail`) and `sacct-probes` (`OUT_OF_MEMORY`, `TIMEOUT`, `NODE_FAIL`, the two pending-reason jobs).
- For T3, the extraction would add the Slurm version to each file name (`slurm-26.05.5/…`), as the test-architect rule wants, and redact what is site- or run-specific (`submit_line` holds full paths, temp names and base64 resources).
- No artifact and no write token are needed. The same blocks could also go to `actions/upload-artifact` for Thomas to download, which the GitHub tools of a cloud session cannot do.

## Differences with the specs and the harness

1. **Snakemake on SLURM hides the task exit code.** A task's Slurm job runs `python -m snakemake … --executor slurm-jobstep`, so a rule that exits 137 makes the **job** end `FAILED 1:0` (steps `batch` and `python` both 1). The 137 is only in the task's Slurm log file. The engine log says "SLURM-job '224' failed, SLURM status is: 'FAILED'. Reason: Unknown." `run_scenarios.py`'s Snakemake exit-code check therefore cannot pass on SLURM; `cluster.sh` accepts exactly that one error. For [`schedulers-and-monitoring.md`](../specs/schedulers-and-monitoring.md#35-turning-records-into-meaning) §3.5, "Tool error: `FAILED` with an exit code" gives 1 for every Snakemake task, whatever the tool returned.
2. **The synthetic `oom` mode is not an OOM for Slurm.** It exits 137 by itself, so Slurm records `FAILED 137:0`, not `OUT_OF_MEMORY`. Only `oom_real` (or the probe) produces the record §3.5 classifies as `oom`. The T3 scenarios need `oom_real` with `ConstrainRAMSpace=yes` to test classification.
3. **Snakemake SLURM status polling dominates small runs.** Plugin 2.8.0 waits `init_seconds_before_status_checks` (default 40 s) before the first check and after every check that sees a job finish, up to 180 s when nothing finishes ([`__init__.py:244-251`, `1611-1617`](https://github.com/snakemake/snakemake-executor-plugin-slurm/blob/v2.8.0/snakemake_executor_plugin_slurm/__init__.py#L1611-L1617)). `happy` took 762.6 s with the default and 222–338 s with 5 s. `profiles/slurm/config.yaml` should set it for tests (a sind-specific profile, since a real site may not want 5 s polling).
4. **Engine cleanup looks like an external cancel.** After a fatal failure, Nextflow cancels its own pending jobs; `sacct` shows `CANCELLED by 1001`, the submitting user's own uid. §3.5 maps `CANCELLED by <uid>` to `cancelled_external` "Cancelled by someone else": it must compare the uid with the run's user and the engine's cleanup moment.
5. **The pending reason in `--json` is split in two fields.** `squeue --json` gives `state_reason: "ReqNodeNotAvail"` and `state_description: "ReqNodeNotAvail, Reserved for maintenance"`. The text output (`%r`) shows the long form, which §3.5's table quotes. A JSON parser must read `state_description` to tell a maintenance window from other `ReqNodeNotAvail` cases. Also, `sacct --json` keeps the last pending reason on a finished job (`COMPLETED`, `reason: AssocMaxJobsLimit`), which is history, not a current state.
6. **`sacct -s FAILED,… -S <time>` returned nothing** in run 2 while three `FAILED` jobs existed in the window; the same query without `-s`, filtered afterwards, found them in runs 3 and 4. Why is **[to be validated]** against the [sacct state-filter semantics](https://slurm.schedmd.com/sacct.html). The runner should filter states itself, not rely on `-s`.
7. **`NODE_FAIL` exit code.** The job record carries `return_code 1, status ERROR` and the step `CANCELLED`: classification must use the state, not the exit code (§3.5 already says so; this is the first observation).

## Verdict on option (b)

**Feasible.** Every T3 item that this spike touched runs on a free `ubuntu-24.04` runner: the `slurm-site` shape with slurmdbd and limits, both engines through the unchanged harness, a failure scenario per engine, real `OUT_OF_MEMORY`, `TIMEOUT`, `NODE_FAIL`, the two pending reasons, both heads in `sbatch`, and fixtures out of the log with an integrity check.

**Cost per loop.**
- **Money:** zero. Standard runners are free and unlimited on public repositories ([GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). If the repository became private, a 2-CPU / 8 GB runner would need a smaller cluster, and minutes would count against the plan **[to be validated]**.
- **Time:** a fixed 1.5 min per loop (job start, `bootstrap.sh --ci` 40–51 s, cluster 8–10 s), plus the scenarios: about 1–2 min per Nextflow scenario and 1.5–6 min per Snakemake scenario. The whole set here is 14.5–18 min. One focused loop (one engine, one scenario, one fixture) is 3–6 min. Locally the same loop would be seconds for setup and the same scenario time, since the scenarios are bound by Slurm and engine polling, not by the runner.
- **Agent overhead:** each loop is a commit, a push and a wait. Logs can be read only after the job ends, so a hung step costs its whole step timeout (run 1). Four iterations were enough for this scope; a full T3 (three profiles, every failure mode, slurmrestd) would be roughly 10–20 loops **[estimate]**.

**Compared with (a),** a local machine remains faster to iterate on, as the inbox says. But (b) is not blocked: it needs no new permission (logs carry the fixtures), and the profiles and scripts here are reusable as they are. A practical split: write and debug T3 in CI from a cloud session now, and let Thomas re-run the same workflow, or the same `cluster.sh` locally, when he wants faster loops.
