# Real-pipeline corpus on GitHub runners — T7 results (2026-10-27)

**Question.** Why was `pipelines-real.yml` red (18 of 23 jobs failed in the nightly run on `main`, run 40463254070; 5 of 9 in the PR tier on weber8thomas/spectio#16, run 40535210648)? What does it take to make the PR tier pass, and what do the runners actually leave to the pipelines?

**Answer.** Three causes, none in Spectio's code, plus a few corpus fixes:
1. **Runner disk.** 9 failures across 7 nf-core entries (rnaseq and molkart failed in both runs) were `No space left on device`. Freeing unused toolchains and Docker images before each job raises free space on `/` from 15 GB to 46 GB, and every nf-core entry now passes.
2. **Strict config parser.** viralrecon 3.0.0 and methylseq 4.2.0 include config files that their release tags do not contain. Nextflow 26 rejects them, so they run with `NXF_SYNTAX_PARSER=v1`.
3. **Upstream breakage in catalog workflows.** Six Snakemake entries move to `manual` (details in §2):
   - dna-seq-gatk-variant-calling and chipseq: old conda pins (samtools 1.10, cutadapt 2.10) no longer solve;
   - cyrcular-calling: its RepeatMasker download URL is dead (404);
   - ONT-AmpSeq: its conda env lacks pandas;
   - rna-seq-kallisto-sleuth: Ensembl archive timeouts;
   - single-cell-rna-seq: unmaintained since 2019, never run.

Corpus fixes: chipseq's `tag: main`, varlociraptor's missing `--configfile`, single-cell-rna-seq's `Snakefile` path, and two arguments ampliseq needs under Nextflow 26.10's typed params (§2).

After the fixes, the PR tier is green (7 of 7, run 40555936925). In the nightly tier (run 40562495868), all 13 nf-core entries passed. Of the Snakemake entries, 2 passed and 3 failed: two now sit in `manual`, and one, rna-seq-star-deseq2, hit a conda-forge 502 error. Afterwards, the PR tier was cut to two light entries; the five heavier ones run nightly (§3). The corpus file is `tests/pipelines/real/corpus.yaml`; the owning spec is [dev environment §10.2](../specs/dev-environment-and-testing.md#102-real-pipelines-testspipelinesrealcorpusyaml).

## 1. Runner measurements

Runner: `ubuntu-latest`, which resolved to the `ubuntu-26.04` image (version 20261025.179.1, from the job log's "Runner Image" group), for this **private** repository. The figures below come from the "Free runner disk" and "Sample free memory and disk" steps of `pipelines-real.yml` and from Nextflow's `.nextflow.log`. They are identical across the 25 jobs of both runs, to within 0.1 GB.

| Quantity | Value | Source |
|---|---|---|
| CPUs | 2 | `nproc` |
| `MemTotal` | 7.75 GB (8 122 096 kB) | `/proc/meminfo` |
| `MemAvailable` before the run | 6.84–6.96 GB | `/proc/meminfo`, first sample |
| Swap | 3 GB | `SwapTotal` |
| Memory Nextflow's local executor allows | 7.7 GB | `.nextflow.log`: `Creating local task monitor for executor 'local' > cpus=2; memory=7.7 GB` |
| Free disk on `/` at job start | 15 GB of 72 GB | `df -h /` |
| Free disk on `/` after freeing | 45.5–47 GB | `df -h /` |
| Time spent freeing | 115–233 s | step duration, run 40555936925 |

**Why 7.7 GB and not the free memory.** The local executor takes its memory capacity from `OperatingSystemMXBean.getTotalPhysicalMemorySize()` unless `executor.memory` is set (`LocalPollingMonitor.configMem`, [nextflow v26.10.3, lines 119-120](https://github.com/nextflow-io/nextflow/blob/v26.10.3/modules/nextflow/src/main/groovy/nextflow/processor/LocalPollingMonitor.groovy#L119-L120), read 2026-10-27). So it accepts a 7 GB task even when only 6.9 GB is free. The earlier comment in `corpus.yaml` ("avail: 5.8 GB") came from this cloud session, not from a runner.

**`runner_limits.private` stays at 2 CPU / 6 GB / 2 h.** 6 GB is under the 6.9 GB that is free before a run, which leaves room for the Nextflow JVM and the Docker daemon. Because the executor sums task requests against 7.7 GB, two 6 GB tasks never run at the same time. viralrecon's `FREYJA_BOOT` reached a 6.7 GB peak RSS, above the 6 GB cap, and still finished. Whether Docker enforced any memory limit on that container is **[to be validated]**.

**`runner_limits.public` (4 CPU / 15 GB) is not measured.** This repository is private, so no public runner ran. The value stays **[to be validated]**.

**Note, 2026-10-28: public runners measured.** The repository went public on 2026-10-28. Nightly run 40649538349 on `main` ran on public runners: 4 CPU, `MemTotal` 16366644 kB (15.6 GB, against 7.75 GB above), 14.66 GB available at start (against 6.9 GB), and a highest run peak of 8.35 GB (viralrecon). `runner_limits.public` is now 4 CPU / 13 GB / 2 h ([dev-env §10.2](../specs/dev-environment-and-testing.md#102-real-pipelines-testspipelinesrealcorpusyaml)).

**Disk use per job.** The table in §3 gives each entry's minimum free disk. molkart dropped to 16.1 GB free and viralrecon to 12.3 GB, so each used about 30–34 GB. Neither would fit in the 15 GB the image leaves free. The freeing step removes:
- `/usr/local/lib/android`, `/usr/share/dotnet`, `/opt/ghc`, `/usr/local/.ghcup`, `/opt/hostedtoolcache/CodeQL`, `/usr/share/swift`, `/usr/local/share/boost`, `/usr/local/share/powershell`, `/usr/local/julia*`, `/opt/az` and `/opt/microsoft`;
- every preloaded Docker image (`docker image prune -af`).

The jobs use none of these. The step is plain `rm`, with no third-party action.

## 4. Changes made in T7

The workflow, script and corpus changes are listed on the [T7 Progress page](../progress/W3/T7.md). Two choices belong here:
- **One probe script.** Both jobs call `tests/pipelines/real/runner_probe.sh` (`free`, `sample`, `summary NAME`). This replaces copies of the three steps in each job, which had already drifted apart, and avoids YAML anchors, whose support in zizmor is beta ([zizmor usage docs](https://docs.zizmor.sh/usage/#yaml-anchors)).
- **Corpus validation.** `run_corpus.py --matrix TIER` validates `corpus.yaml` first: refs must be release tags or 40-hex SHAs, so an entry cannot silently track a branch, and paths and `args` must be plain tokens, because these values end up in workflow inputs and command lines.

**Not changed.**
- `pipelines-real.yml` still pins `nf-core/setup-nextflow` to `26.10.3`, while `dev/versions.env` pins 26.10.4. Aligning them is inbox #42.
- `corpus.yaml` `versions.nextflow.current` also says 26.10.3.
- No required check was renamed.

**Follow-ups (to the inbox).**
- SEC-T7-01: pin every corpus entry by commit SHA, kept current by Renovate.
- SEC-T7-04: replace `snakemake/snakemake-github-action`, a composite action that wraps an unpinned `setup-miniconda@v3` and the latest Miniforge.
